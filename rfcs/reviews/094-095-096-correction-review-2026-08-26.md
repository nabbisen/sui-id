## A1 — `ReadConn` sufficiency (B-094-1) — measured, not reasoned about

I did not write a review of the RFC's claim. I built the thing and ran it.

**Method.** A throwaway `#[test]` added to `crates/sui-id-store/src/lib.rs`
(temporarily wired via `#[cfg(test)] mod tests_scratch_readonly;`) using
`rusqlite::Connection::open_in_memory()` at the pinned workspace version
(`rusqlite 0.40.1`, confirmed via `Cargo.lock`). For each statement: prepare
it, call `Statement::readonly()`, record the verdict. Removed both the file
and the `mod` line afterward; `git diff` confirms no residue.

**Result:**

| Statement | `readonly()` |
|---|---|
| plain `SELECT` | `true` |
| `SELECT` with scalar subquery | `true` |
| `INSERT` | `false` |
| `UPDATE` | `false` |
| `DELETE` | `false` |
| `REPLACE` | `false` |
| `PRAGMA user_version` (read) | `true` |
| `PRAGMA user_version = 1` (write) | `false` |
| `PRAGMA journal_mode = WAL` | `false` |
| `CREATE TABLE` | `false` |
| `DROP TABLE` | `false` |
| `ALTER TABLE ... ADD COLUMN` | `false` |
| `ATTACH DATABASE ':memory:' AS aux` | **`true`** |
| `DETACH DATABASE aux` | **`true`** |
| `BEGIN` | **`true`** |
| `COMMIT` | **`true`** |
| `ROLLBACK` | **`true`** |
| `SAVEPOINT sp1` | **`true`** |
| `WITH ins AS (INSERT ... RETURNING id) SELECT * FROM ins` | prepare-error: syntax error (SQLite does not accept a DML statement inside a `WITH` clause in this position) |
| `INSERT ... RETURNING id` (bare) | `false` |
| `UPDATE ... RETURNING id` (bare) | `false` |

**Direct answer to the question asked.** `sqlite3_stmt_readonly` correctly
flags every DML form named in B-094-1, including the specific
`UPDATE … RETURNING` bypass the finding was about. That part of the fix is
real, not asserted.

**But six forms SQLite itself reports as read-only are not benign to let
through a security boundary: `ATTACH`, `DETACH`, `BEGIN`, `COMMIT`,
`ROLLBACK`, `SAVEPOINT`.** None of these change *row data*, so they don't
contradict the RFC's literal "changes durable state" framing — but `ATTACH`
in particular changes what the *connection* can see (a second database
becomes queryable), and transaction-control statements change what the
*connection's* commit/rollback boundary is, independent of anything
`ReadConn`'s call site intended. This is exactly why the RFC requires the
static category-based denial list as a second, independent control — and
this measurement is the first place that requirement is backed by evidence
rather than assertion.

**One place the RFC's fixture wording should be tightened.** RFC 094 line
397 groups `ATTACH` into the same sentence as other cases that "must fail to
compile or be rejected as non-read-only before execution." For `ATTACH`
specifically, that second path does not exist — my measurement shows
`readonly()` reports `true` for it. `ATTACH` can only be caught by the
**static** string/category check, never by the runtime interrogation. If a
future implementer reads that sentence as "either control catches this,"
they could ship `ReadConn` with only the runtime check and an `ATTACH`
statement would sail through. **Suggested correction:** split that sentence
so it's explicit which fixtures the static list alone must catch (`ATTACH`,
`DETACH`, PRAGMA, transaction control) versus which the runtime check alone
must catch (`UPDATE`/`INSERT`/`DELETE`/`REPLACE` and their `RETURNING`
forms).

**Application-defined functions / virtual tables.** Not tested directly —
there is nothing to register one against. Independently confirmed via
`cargo tree -e features -i rusqlite`: the resolved feature set is `bundled,
cache, chrono, default, ffi-sqlite-wasm-rs, hashlink, modern_sqlite`.
`functions`, `vtab`, `load_extension`, `window`, `series`, `array` are all
absent, matching the RFC's claim.

**One inaccuracy in the RFC's own "verified" list, worth a one-line fix, not
blocking.** RFC 094 line 352 states the resolved feature set is "exactly
`bundled, cache, chrono, default, hashlink, modern_sqlite`" — my
independent `cargo tree` run shows a seventh feature, `ffi-sqlite-wasm-rs`,
also resolved (it's part of rusqlite's own `default` set, gating an
optional WASM-target dependency; it does not enable `functions`/`vtab`/
`load_extension`, so the security claim itself still holds). The list is
incomplete, not wrong in substance — worth correcting so the next person
who re-runs this check isn't confused by a mismatch.

**Sixth CTE case, noted since it wasn't in the original list.** A
`WITH ... AS (INSERT ... RETURNING ...) SELECT ...` CTE-wrapped write does
not parse in this SQLite build (bundled, per `Cargo.toml`). Reported for
completeness, not because it changes the verdict.

## A2 — deferred AST gate, reachability (B-094-2) — a real path exists

**The question was executable-checkable, and I checked it against the
actual codebase rather than the RFC's description of itself.**

`grep`-ing the workspace: `Database::with_conn`/`with_tx` (the general
async raw-connection/transaction closures item 1 says must go away from
production repository/domain modules) are called **192 times across 34
files** today. The sync variants (`with_conn_sync`/`with_tx_sync`) add
another 21 calls across 8 files, including **`crates/sui-id-core/src/oidc/key_rotation.rs:108`** — a caller *outside* `sui-id-store` entirely, reaching
straight past the repos layer for signing-key rotation (K01/K02/K03,
priority-wave M2a work).

RFC 094 phases conversion across two milestones: M2a converts 4 of 8 waves
(user administration; credential/consent/session security; token/
registration security; signing keys); M2b converts the remaining 4 (settings;
pending settings; federation configuration; client administration
metadata). **Every unconverted M2b-wave repository function must still be
able to write to the database throughout the entire M2a period** — the
application cannot stop supporting settings changes while M2b is pending.

`migration-checklist.md` (Stage 1, lines 37-44) makes a specific claim: **"A
new bare write in M2a therefore cannot compile outside the reviewed module
list."** I could not find, in the RFC text, the handoffs, or the codebase,
what mechanism makes that true for the ~28 files/170+ call sites that remain
unconverted through the whole of M2a. Two readings are both consistent with
the RFC's wording, and they have opposite answers to A2's question:

1. **If "the reviewed module list" means all of `sui-id-store::repos`** (i.e.,
   the privacy boundary is crate-level: `with_conn`/`with_tx` become
   inaccessible outside `sui-id-store`, but individual repo files inside it
   keep raw access until their own wave converts) — then the compiler
   capability closes the *cross-crate* path (which `key_rotation.rs`
   currently uses) but does **not** prevent an unconverted repo file from
   adding a new bare write today. The structural coverage gate (available
   from Stage 2, before M2a) would need to independently detect that, and its
   own description ("fails if... an unapproved raw-write module exists")
   sounds like exactly the AST check's job — but item 7 explicitly says that
   check (the one that rejects `with_conn`/`with_tx`/execute calls by module)
   is the **M2b** deliverable. What mechanism performs "an unapproved
   raw-write module exists" detection during M2a, if not that check, is not
   stated.
2. **If "the reviewed module list" means only the specific functions already
   converted** — then `with_conn`/`with_tx` would need to be restricted
   per-caller, which Rust's module-privacy system cannot express, and the
   claim in migration-checklist.md would be an overclaim.

**I could not resolve which reading is correct from the artifacts available
to me**, and I don't think it's mine to guess — a wrong guess here is exactly
B-094-1's shape (confident reasoning about what a control "really" enforces,
unverified). **Reachable path, stated plainly: yes, today, and by
construction throughout the entire M2a period, for every unconverted
repository module** — `key_rotation.rs` already demonstrates a caller
outside the module boundary the RFC describes, and it is scheduled to
convert only as part of M2a's own wave 4, meaning at minimum the interval
between M2a's start and wave-4 landing has this exact path open.

**This is not necessarily wrong as a design** — RFC 094 already accepts that
partial conversion leaves a residual (line 794-804, "no unconverted command
may be described as Class-A atomic"). But B1's acceptance question in the
governing request ("is shipping M2a with the AST gate deferred to M2b
acceptable") can't be answered honestly until the RFC states, precisely,
what stops (or merely detects, after the fact) a new bare write in an
unconverted module during M2a. **Required correction, addressed to the
RFC's author, not to me:** state explicitly, in `migration-checklist.md`
Stage 1 and RFC 094's own M2a section, exactly what mechanism (if any) is
active against unconverted modules during M2a, and whether "cannot compile
outside the reviewed module list" is a claim about all of `sui-id-store`, a
claim about only converted functions, or an aspiration that only becomes
true once M2b's AST gate lands.

## A5 — the 096-B1/B2 split inference — attacked hardest, as instructed

**Both questions, answered from the inventory, with the exact rows.**

**1. Does federated session establishment appear inside M2a's
session-security wave, or is it distinct and absent from M2a's inventory?**

`command-inventory.md`'s "Users, credentials, MFA, and sessions" table
(the actual session-security wave: U01-U36) contains no F0x row. F01-F06
live in a separate section, "RFC 096 federation login commands (accepted
amendment)" (lines 124-182), explicitly outside the U-table.

RFC 094 itself now says so directly (§"Phase assignment for F01-F06,"
added 2026-08-12, corrected 2026-08-26): **"F01–F06 are not part of an RFC
094 conversion wave. They appear in neither M2a's priority waves... nor
M2b's remaining waves... That omission was an oversight, not a deliberate
silence."** The RFC's own text and the inventory's own section boundaries
agree, independently. **Answer: distinct, absent from M2a's inventory** —
the original amendment's premise (session establishment falls inside the
session-security wave) was wrong, and the 2026-08-26 correction (re-pointing
096-B1's prerequisite to "M2a's runner foundation" instead) is the right
fix for what this question actually found.

**2. Is a durable login-attempt row Class-A, or Protocol/Operational? If
not Class-A, does 096-B1 depend on the RFC 094 seam at all?**

Quoting the F01-F06 table directly: F01, F02, F03, F05, F06 are Class
**P** (Protocol). Only **F04** ("First federated provisioning and direct
login") is Class **A**. The attempt-state row itself
(`federation_login_attempt`) is mutated *within* each of these — it is not
an independently classed command; its class follows whichever command
touches it (mostly P, once A for F04's first-provision path).

So: **most login-attempt transitions are Protocol-class, but 096-B1 as a
whole is not** — it bundles F01-F06 together (per the split note in RFC
096: "096-B1 (login-path completion — attempt state, one-time nonce
consumption, session establishment)"), and F04 is genuinely Class-A. RFC
094's own foundation table confirms both runners are required for this set:

```
| WriteTx<Protocol> runner — F01, F02, F03, F05, F06 | M2a foundation |
| WriteTx<AtomicAudit> Class-A runner — F04           | M2a foundation |
```

**Answer: 096-B1 does depend on RFC 094's Class-A seam — not incidentally,
through F04, one of its own six constituent commands.** If the question
were asked about F01/F02/F03/F05/F06 alone, the answer would be
"Protocol-class, and technically the Class-A runner isn't needed for those
five" — but 096-B1 is not five commands, it's six, and F04 is Class-A. The
split does not fail on this question the way it failed on question 1.

**A real, separate problem found while attacking this: stale justification
text survives in two places, describing the *old, now-rejected* inference
as if it were still the open question.**

`rfcs/accepted/096-upstream-oidc-federation-validation.md:115-122`, the
096-B2 section's footnote (dated "Added 2026-08-12," never updated for the
2026-08-26 correction):

> "**This split is proposed, not settled**: it rests on the inference that
> federated session establishment falls inside M2a's session-security wave,
> which the correction round must confirm against RFC 094's command
> inventory."

But the 096-B1 section three lines above it (lines 93-99, correctly updated
2026-08-26) already says the opposite: the dependency is on "M2a's **runner
foundation**, which precedes the conversion waves, not on membership of a
wave. RFC 094 now states this." The RFC contradicts itself between two
adjacent sections about the same split.

`rfcs/handoffs/096-upstream-oidc-federation/README.md:35-36` has the same
problem, unfixed since 2026-08-12: "**096-B1** (attempt state, nonce
consumption, session establishment) requires amended RFC 094 **M2a**
Implemented **with the applicable user/session fixtures passing**." "User/
session fixtures" is the old session-security-wave framing this correction
round replaced — the RFC's own commit (`98b02ce`) touched only
`rfcs/proposed/094-*.md` and `rfcs/proposed/096-*.md`; this handoff file was
never in scope for that commit, and it shows.

**Required correction:** update both locations to state 096-B1's dependency
as "RFC 094 M2a's runner foundation (sealed `declare_write_command!`,
`ReadConn`, command manifest, `WriteTx<Protocol>`, `WriteTx<AtomicAudit>`)
plus the F01-F06 commands this stage implements against it" — matching the
already-correct wording in the RFC's own 096-B1 section — and delete the
"proposed, not settled... must confirm" framing, since this review is that
confirmation and question 1's answer settles it.

**One genuine gap found within what I did read.** RFC 094's structural
gate depends on `cargo +stable xtask audit-structure --locked --policy
ci/write-authority.toml --commands ci/write-commands.toml` (line 679-680).
None of `ci/write-authority.toml`, `ci/write-commands.toml`, or an `xtask`
workspace member exist today — expected, since RFC 094 is unimplemented,
not a defect by itself. But this project's entire CI-gate convention (RFC
093, this milestone's own subject) dispatches shell/Python scripts through
`scripts/ci-gate.sh` reading `ci/gate-inputs.toml`, not a `cargo xtask`
binary. RFC 094 doesn't say whether `audit-structure` becomes a new Gate
Matrix lane (requiring `ci/gate-inputs.toml` registration and the
completeness rule M1b just finished building) or an out-of-band check. This
is a real cross-RFC integration question an implementer will hit on day one
of Stage 2, and it's not answered by either RFC.
