## Independence and lifecycle limitation

I formed the findings before reading the amendment author's reasoning files named by the request. This is an independent technical review of the Anthropic-authored amendments.

It is not, by itself, the vendor-independent acceptance review required by the governing RFCs for 094 and 096. Both RFC 094 and RFC 096 say that the reviewer of record must be outside the vendor that authored **and implemented** the RFC, and expressly say that OpenAI Codex may review but cannot alone satisfy that condition ([RFC 094](../accepted/094-transactional-audit-registry.md) lines 16–17; [RFC 096](../accepted/096-upstream-oidc-federation-validation.md) lines 15–17). The request's narrower, authoring-vendor reading conflicts with those normative headers. A corrected 094 or 096 therefore still needs a reviewer outside OpenAI for its acceptance metadata. RFC 095's expressly stated role-independence rule is different and does not have this vendor limitation.

## RFC 094 findings

### B-094-1 — `ReadConn` can execute a write on a read path

**Blocking.** RFC 094 limits `ReadConn` to `query_row`, `query_map_collect`, and `query_optional`, and says it statically rejects a list of dangerous forms ([RFC 094](../accepted/094-transactional-audit-registry.md) lines 279–302). The list does not reject `INSERT`, `UPDATE`, `DELETE`, or `REPLACE`; it also defers SQLite's per-statement read-only interrogation to a successor (lines 304–310).

A call such as `query_row("UPDATE ... RETURNING ...")` is still a query-shaped operation that returns rows, but it changes durable state. It would bypass the sealed `WriteTx` constructor, command manifest, transaction runner, typed event construction, and failure-injection evidence. Consequently it violates the claimed property that raw write authority is private and reopens the mutation/audit gap RFC 094 is intended to remove.

**Required correction.** Before M2a starts, either enforce `sqlite3_stmt_readonly` for every prepared `ReadConn` statement and test its failure path, or replace arbitrary SQL query entry points with a reviewed query representation that permits only a demonstrably read-only grammar and rejects DML, including `… RETURNING` forms. The negative fixture set must include `INSERT … RETURNING`, `UPDATE … RETURNING`, `DELETE … RETURNING`, and `REPLACE … RETURNING`, besides the existing PRAGMA, ATTACH, multi-statement, raw-handle, and indirect-helper cases. A successful ordinary `SELECT` remains the control fixture. Deferring this control is not safe while arbitrary SQL remains callable by read paths.

### B-094-2 — governing RFC and handoffs disagree about the same boundary

**Blocking.** The amendment says runtime read-only checking is deferred and the `syn` AST boundary gate arrives in M2b ([RFC 094](../accepted/094-transactional-audit-registry.md) lines 304–310 and 670–684). In contrast, the handoff says `ReadConn` validates SQLite read-only status internally ([architecture](../handoffs/094-transactional-audit/architecture.md) lines 126–130), the migration checklist requires read-only statements and an AST failure observation ([migration checklist](../handoffs/094-transactional-audit/migration-checklist.md) lines 28–36), and the verification contract treats prepared-update rejection as already mandatory ([verification](../handoffs/094-transactional-audit/verification.md) lines 23–38).

An implementer cannot tell whether M2a must deliver the runtime guard and AST fixtures, or must defer them. The correction for B-094-1 must be reflected consistently in the RFC, architecture, migration checklist, verification contract, and generated test plan. If the AST boundary remains an M2b authority switch, the M2a contract must say exactly what mechanical manifest/reconciliation control is blocking during the interim.

### M2a/M2b conclusion

The conversion split itself need not create a weaker intermediate state. A command converted in M2a can gain the Class-A transaction guarantee while an unconverted command retains its pre-existing behavior, provided the documentation names the set exactly and never calls an unconverted command atomic. RFC 094's partial-conversion requirement is directionally correct ([RFC 094](../accepted/094-transactional-audit-registry.md) lines 689–696 and 770–784).

That conclusion is conditional on closing B-094-1 and B-094-2. The converted set must come from the checked-in inventory/registry, and the M2a gate must verify generated documentation against that set. A prose-only conversion list is not a claim-suppression control.

Deferring the AST gate is conditionally acceptable only after the `ReadConn` escape is closed: the sealed capability and reviewed raw-module boundary then provide a meaningful M2a control, while the later AST check detects a newly added unregistered authority path. It cannot compensate for an already permitted write through `ReadConn`.

## RFC 095 finding

### B-095-1 — the handoff has the old, stricter prerequisite

**Blocking for re-acceptance.** RFC 095 now requires RFC 094 **M2a** with C15 rollback evidence and explicitly says M2b is not required ([RFC 095](../accepted/095-dynamic-client-registration-transaction.md) lines 5–10). The handoff entry gate still says RFC 094 must be “Implemented” ([handoff README](../handoffs/095-dynamic-client-registration/README.md) lines 19–32). Thus the governing design and executable handoff specify different implementation authorization rules.

**Required correction.** Change the handoff and search its companion documents for the stale full-RFC prerequisite. State one synchronized condition: RFC 094 M2a is implemented on the recorded clean baseline, C15's guarded consume/client-create/typed-event transaction has observed rollback and exactly-once evidence, RFC 095 has been accepted, and the owner has authorized implementation.

Subject to that correction and the RFC 094 fixes, M2a/C15 is genuinely sufficient for RFC 095. The RFC 095 design depends on the C15 transaction seam—not on the M2b federation/settings/client-metadata conversion waves—and its own authorization path is explicitly bound to the C15 context ([RFC 095](../accepted/095-dynamic-client-registration-transaction.md) lines 389–425). No M2b-only mechanism is identified as a correctness dependency.

## RFC 096 findings

### B-096-1 — 096-A's no-mutation rule conflicts with the delivery stages

**Blocking.** The amended RFC defines 096-A as discovery, transport, JOSE/claims, nonce, cache, and hostile-input work, and prohibits every durable provider/link mutation and session establishment ([RFC 096](../accepted/096-upstream-oidc-federation-validation.md) lines 44–59). The retained “Implementation stages and ownership” section instead permits stages 1–3 before RFC 094, while stage 3 includes schema migration, repository types, and provider preflight/versioning (lines 818–833). The migration itself adds durable provider, attempt, pending-MFA, and ceremony state (lines 789–810); the next stage begins durable attempt start and callback claim (lines 820–825).

The handoff repeats the contradiction by calling stages 1–3 “pure” while listing migration, provider preflight/versioning, and audited enablement in that delivery sequence ([handoff README](../handoffs/096-upstream-oidc-federation/README.md) lines 19–33 and 75–88).

A one-time callback nonce cannot be implemented as a production callback flow without durable attempt state; a durable attempt, migration, provider-state update, or audited enablement is 096-B work under the amendment's own rule. 096-A may produce pure validation/transport libraries and hostile-provider tests, but it must not route live federation traffic, create state, or claim that the shipped callback defect is closed until 096-B is complete. The RFC and handoff must replace the old numbered stages with an unambiguous mapping to 096-A and 096-B.

### B-096-2 — the stated 096-B prerequisite is impossible under RFC 094's stages

**Blocking; owner choice required.** RFC 096 says 096-B begins after RFC 094 M2a with the C17/C18/C23 seam proven ([RFC 096](../accepted/096-upstream-oidc-federation-validation.md) lines 7–9 and 61–65). RFC 094, however, places federation configuration in its M2b “remaining conversion waves” ([RFC 094](../accepted/094-transactional-audit-registry.md) lines 670–677). C17/C18/C23 cannot simultaneously be a required M2a seam for 096-B and remain scheduled as M2b federation configuration.

There is no purely technical choice between the two valid schedules. The accountable owner must choose one of these material changes:

1. promote the full, reviewed C17/C18/C23 foundation needed by 096-B into RFC 094 M2a, revising M2a scope, acceptance criteria, inventory, evidence, and roadmap; or
2. retain RFC 094's M2b scope and make 096-B wait for M2b.

After that choice, update RFCs 094 and 096, both handoff packages, and ROADMAP in the same reviewable change. Until then, neither 096-B nor an implementation-start authorization can truthfully name its prerequisite.

### B-096-3 — the preparatory split has no accountable owner or equivalence proof

**Blocking.** The amendment correctly recognizes that a shared `handlers/federation.rs` permits cross-lane security regressions ([RFC 096](../accepted/096-upstream-oidc-federation-validation.md) lines 67–77). Calling the prerequisite change “owned by neither lane” leaves no person or RFC responsible for its scope, review, or proof of zero behavior change.

The split is a real prerequisite, not a convenience: it creates the isolation needed for concurrent validation and mutation work. Assign an accountable owner and narrow preparatory change record, enumerate the files moved, and require observational-equivalence coverage for routing, existing provider operations, and all currently reachable callback outcomes. That record must be independently reviewed before 096-A or 096-B implementation begins.

## Required resolution order

1. Correct RFC 094's read-only execution control and synchronize its handoffs.
2. Correct RFC 095's stale entry gate.
3. Obtain the owner's 096-B sequencing decision; then rewrite the 096-A/096-B work map and assign/review the preparatory split.
4. Submit the corrected RFCs and handoffs for a new review. For RFCs 094 and 096, obtain the separate vendor-independent reviewer required by their own headers before recording an accepted state.
