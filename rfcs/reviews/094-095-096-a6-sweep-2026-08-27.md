## 1. RFC 094 — sections read this pass

`Class-B emission`, `Mechanically complete durable-write universe`'s
negative-fixture grouping (re-read after `8d1d9f7`'s correction),
`Conditional Class-A outcomes` and its two subsections, `Structural

`Signing-key rotation`, `Master-key rotation — out of scope`, `Data model
and compatibility`, `Test plan`, `Security considerations`, `Rollback`
(the last three were adjacent to the assigned range and read along with

**`Class-B emission` is thin but not broken.** One paragraph, no example
call site, no test list of its own — but its behavior (`emit_must_attempt`,
must-attempt semantics, failure telemetry) is fully pinned down by every
Class-B command's usage elsewhere in the RFC (F01/F02/F03/F05/F06, U24,
T09) and by the `Test plan`'s own bullet ("Class-B tests prove primary
denial remains effective and append failure emits structured error
telemetry"). An implementer has enough to build it; noted, not blocking.

**The negative-fixture regrouping (`8d1d9f7`) holds up under a second
read.** The three-way split — runtime-rejected, static-list-only, compiler
-rejected — matches the measured table from Part A §A1 exactly, and the
in-text note now correctly explains *why* the old wording was wrong rather
than just stating the new grouping. No residual trace of the old "fail to
compile or be rejected as non-read-only" phrasing anywhere in this section.

**`Conditional Class-A outcomes`, both subsections, is dense but
consistent.** I specifically checked the numbers that looked like they
could drift apart on a re-read and found no contradiction:

- C17's `0 <= guard_at - observed_at < 600s` (line ~473) matches the
  validation-matrix's independently-written "age 0–599.999s" (line 69 of
  that file) — same boundary, two documents, no drift.
- F03's `failure_count` "constrained 0–5" and "counts 1–4 remain pending,
  exactly 5 exhausts" are the same range described two ways, not two
  different ranges.
- F01–F06's phase-assignment table (already verified in Part A §A5) is
  unchanged and still consistent with the F0x class list given here.

**Signing-key rotation, Master-key rotation, Data model and compatibility**
are all short, self-contained, and implementable as written. No issues.

**Test plan** is a checklist, not new specification — every bullet maps to
a mechanism already described in the sections above it. One line (897,
"prepared UPDATE/writable PRAGMA/ATTACH/backup/indirect helper through
`ReadConn` fail CI or runtime read-only validation") uses the same
disjunctive phrasing that was wrong when it was a *specific mandatory
fixture's* requirement (the `ATTACH` case fixed in Part A). Here it's a
summary bullet over a mixed set where the "or" is genuinely true item-by-
item (some fail CI, some fail runtime validation, none needs to do both) —
not a repeat of the defect. Flagged as read and checked, not as a finding.

## 2. The multi-source lane ownership mechanism — under-specified

This is the substantial finding, and it is exactly what §2 of the request
asked me to attack: is the mechanism `62c2680` commits RFC 094 to
delivering "described concretely enough to implement, since nothing like
it exists yet"? **No.**

RFC 094's `Structural coverage gate` section (current text) states the
requirement precisely:

> "each lane in `[gates]` is validated against the table of the RFC that
> **owns** it, not against RFC 093's table unconditionally; every lane must
> have exactly one owning RFC."

That is a correct requirement. It is not a design. Three questions an
implementer hits immediately have no answer anywhere in RFC 094, its
handoffs, or the current `scripts/check-gate-inputs.sh`:

1. **How is ownership declared?** `check-gate-inputs.sh` currently derives
   RFC 093's lane table by parsing its literal `## Gate Matrix v1` markdown
   table. RFC 094 has **no such table** — its own new lane (the structural
   coverage gate / `audit-structure`) is described in prose, one lane, no
   markdown table at all. Does RFC 094 need to grow a Gate Matrix table
   shaped like RFC 093's (even for a single row), or does the ownership
   mechanism need a wholly different declaration shape for a
   single-lane-owning RFC? Neither is stated.
2. **How does the checker discover which RFC file owns a given `[gates]`
   key?** Today `--rfc` takes one path (confirmed:
   `scripts/check-gate-inputs.sh` usage string, `--rfc <path>`, singular).
   Becoming "multi-source" means either a list of RFC paths to scan, or a
   new manifest table mapping lane ID → owning RFC path, checked directly
   in `ci/gate-inputs.toml`. The RFC doesn't say which, and the two are not
   equivalent: a list-of-RFCs design still needs an explicit tie-break rule
   if two RFCs' tables both claim the same lane ID (see next point);
   a manifest table sidesteps that by making ownership an explicit,
   single-writer field.
3. **What happens when ownership conflicts?** The RFC's own completeness
   promise — "every lane must have exactly one owning RFC" — implies there
   is a conflict case to detect (two RFCs' tables both defining, say, `G13`)
   and a defined failure mode for it. No such check is described. Given
   this project's own recent history (RFC 093 vs 095's stale-prerequisite
   defect, the 096-B1/B2 footnote left stale after a correction) is exactly
   "wrote the intent, didn't sweep every place it needed to hold," an
   unspecified conflict rule is a plausible place for the same shape of
   defect to recur, invisibly, the first time two RFCs' lane tables happen
   to collide.

**This is not a hypothetical gap I'm inferring** — I checked whether
`check-gate-inputs.sh` already has any of this machinery (`git log`
confirms it hasn't been touched since `afc999e`, well before `62c2680`),
and whether RFC 094 or its handoffs describe a manifest schema anywhere
(they don't — `grep -n "lane_owner\|lane-owner\|owning_rfc"
rfcs/proposed/094-*.md rfcs/handoffs/094-*/*.md` returns nothing).

**Why this blocks more than a documentation nit would.** RFC 094's own text
says "the lane must be registered before this gate is relied on as M2a exit
evidence" — meaning M2a cannot honestly close without this mechanism
existing, and the mechanism cannot be built from what's written today
without an implementer making the three design calls above unilaterally.
That's a requirements gap, not an implementation-detail gap: whoever
answers questions 1–3 is choosing the shape of a project-wide governance
primitive (how any future RFC registers a CI lane), not just this RFC's own
lane.

**Smaller, related, and lower-severity:** the new `rusqlite`-dependency
gate check (`c3e3a45`'s last checklist item, "add the gate check that fails
if `rusqlite` appears in any `[dependencies]`/`[dev-dependencies]` table
outside `sui-id-store`") doesn't say what dispatches it either — a new
script, a new condition inside `cargo xtask audit-structure`, or a
Gate-Matrix lane of its own. Unlike the lane-ownership question, this one
has a low-risk default inference (fold it into the same `xtask
audit-structure` job that already lists several unrelated failure
conditions in one sentence), so I'm noting it rather than blocking on it —
but naming the mechanism explicitly would remove even that inference.

## 3. `c3e3a45`'s owner-decision content, read as an implementer

Beyond the gate-check placement above, the rest of `c3e3a45`'s checklist
items are concrete and buildable: converting `audit_guard.rs`'s
`audit_and_tx`, `forgot_password.rs`, `key_rotation.rs`, and `index.rs`'s
health probe are each named with an exact target shape (`ReadConn` or the
sealed capability). The one open item it correctly marks as open — where
`crates/sui-id/src/backup/` belongs — points at an **already fully
specified** artifact for its resolution: RFC 096 lines ~157–165 define
"observational-equivalence record" concretely (exact file-move list,
coverage of routing/every provider operation/every callback outcome,
no-meaning-change confirmation, reviewer-other-than-implementer). I
checked this because "the same hazard as the RFC 096 federation split" is
exactly the kind of cross-reference that turns out to point at nothing —
here it doesn't; the definition is real and reachable.
