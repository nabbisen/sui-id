# RFC 112 — independent design review

**Date:** 2026-09-25
**RFC:** [RFC 112 — Refuse to run against a database this build does not understand](../../accepted/112-schema-version-fail-closed.md), Proposed; **handoff** `rfcs/handoffs/112-schema-version-fail-closed/README.md`; **request** `rfcs/handoffs/112-schema-version-fail-closed/design-review-request.md`.
**Reviewer:** mid-capability model, implementation role. I authored neither the RFC nor its handoff.
**Baseline:** `2adf796` (contains `d59bc44`). **Read-only: no repository file changed.** Everything I ran ran in a **throwaway `git worktree` at that commit** (a scratch integration test, a scratch debug build of the binary, a scratch database directory), removed afterwards; the probe is described in §3 so it can be reproduced.
**Outcome: accept with changes.** The rule is right and refusing is right. But the RFC as written would **leave the measured damage path open for a populated database with no version row, would not deliver "nothing is written on refusal"**, and would not deliver its "one-line message" without more than a new error variant. Two high findings, four medium, three low, and no blocker. They are all fixable inside this RFC's scope.

## 2. Findings, ranked

### High

**H1 — "Missing row → version 0, as now" leaves the damage path open for any populated database.** The RFC and handoff keep `QueryReturnedNoRows` as "a fresh database". But a row can be missing from a *populated* one (deleted, or the file is not a sui-id database at all). Measured (§3): **row deleted from a populated database → `open` fails with `duplicate column name: allowed_scopes` and leaves the stored version `1`** (it was 43), so the next start fails the same way. And a **foreign SQLite file** (a table `ledger` with one row) → `open` returns `Ok`, adds **26 tables** to it and keeps `ledger`: sui-id "migrates" another application's database. "Fresh" must mean *no application tables*, not *no row*. **Fix:** version 0 only if the database has no tables other than `sui_meta`; otherwise `SchemaVersionInvalid` ("no schema version is recorded, but the database has N tables"). This is the same defect as the RFC's defect 2 by a different door, and the closure prerequisite ("a failed version read is a refusal, not a re-run") is false without it.

**H2 — "Nothing is written on refusal" is not expressible as `Database::open` is ordered.** `db.rs:32-38` runs `PRAGMA journal_mode = WAL` **before** `migrations::run`, and `run` runs `CREATE TABLE IF NOT EXISTS sui_meta` before it reads the version. Measured: a **rollback-journal** database stamped 44, `Database::open` → header bytes 18–19 `[1,1]` → `[2,2]`, main file not identical: the too-new database is converted to WAL, **written to, before any check could refuse it**. On a database already in WAL (production's normal state) the main file is identical (§3), so the defect is real but narrow; the RFC's own requirement ("no `PRAGMA` write, no WAL side effect") would not hold on the first open of a legacy or restored file. **Fix:** the check goes **first**, on a read-only connection (`SQLITE_OPEN_READ_ONLY`) that reads the version without creating anything and without touching the journal mode; the pragmas and `run` follow only if it passes. Measured: that read-only pre-check leaves the main file identical in both journal modes. It **does** leave empty `-wal`/`-shm` files beside a WAL database (the connection cannot delete them), so the test must not assert their absence (item 10).

**H3 — The "one-line message" does not reach the operator through a new variant alone.** Traced (item 12): `serve` and all seven CLI operations wrap `Database::open` in `.context("opening database")?` and return through `main() -> anyhow::Result`, so the operator sees, measured on the real binary:

```
Error: opening database

Caused by:
    0: database I/O error
    1: duplicate column name: allowed_scopes
```

The new variant would sit on line 4, under "Caused by", after a first line that says nothing. Exit code is `1`, the same as any failure. `serve` initialises tracing before opening (`startup.rs:138`, the first line of `prepare`; the open is at `:164`), but **this error is not logged through it** (so a JSON log shipper never sees it), and the CLI never initialises tracing at all. Under the shipped unit (`docs/src/guides/deployment.md:227-228`, `Restart=on-failure`, `RestartSec=2s`) a refusing binary is restarted until systemd's start limit trips. **Fix:** handle the refusal at one place (a helper both `startup::prepare` and the CLI openers call), print the line **first and alone** to stderr, emit one `tracing::error!` with `found` and `supported` fields where tracing exists, and exit with a **distinct code** so `RestartPreventExitStatus=` can be set. Say which code in the RFC.

### Medium

**M1 — Two other readers already have their own, weaker, definition of "the stored version".** (Request item 14.) `backup/ops.rs:120-133` (backup *create*) reads it with `.unwrap_or(0)` twice (once on the query, once on `parse`), so a snapshot whose version cannot be read is stamped `schema_version: 0` in its manifest, passes `restore`'s check, and is then re-run from 0001 on open, i.e. **defect 2 in a second place**. RFC 106 F1 will add a third reader (the snapshot's own `sui_meta`, for manifest-less archives). `http/handlers/settings.rs:327` shows `MAX_SCHEMA_VERSION` under the label "schema version" on Settings → Advanced: the binary's ceiling, not the database's stored value. **Fix:** one function, `migrations::read_stored_version(&Connection) -> Result<StoredVersion, SchemaError>`, and one `migrations::check_supported(v)`, used by `run`, backup create, restore, verify and (RFC 106) the manifest-less path; the settings page shows the real stored value or says it is the ceiling. RFC 112 must land the shared function so 106 does not write a second.

**M2 — The error taxonomy has a hole and a mislabel.** (Item 9.) `found` is `i32` and the parse is `i32`: a stored `99999999999` **overflows and is reported `SchemaVersionInvalid`** when it is unmistakably *too new* (measured, case F). Parse as `i64` (or `u64`) and classify overflow as too new; keep `found: i64`. A migration that **fails to apply** (a lower stored version whose SQL cannot run) surfaces today as `StoreError::Db` whose Display is **"database I/O error"** (measured above): an operator reading it looks at their disk. Add `MigrationFailed { version, source }`. Empty text, `-1` and a non-integer are correctly `Invalid`; `+43` parses and is accepted today (harmless; a canonical-form check would refuse it, low).

**M3 — The message cannot say *which* binary, because nothing records it.** (Item 11.) A database stamped 44 tells the operator nothing about which release produced it. Migrations write only `schema_version` (`migrations.rs:257-263`). One extra `sui_meta` key written in the same transaction as the stamp, `last_migrated_by = <CARGO_PKG_VERSION>`, costs one line and no schema change, and lets the too-new message name the release ("stamped by sui-id 0.79.0"). If the key is absent, the message says "a newer sui-id". I recommend it; it is the difference between "run a newer binary" and "run 0.79.0".

**M4 — The docs say something this RFC makes false, and the RFC's `Touches` omits them.** `docs/src/guides/upgrade.md:94-98`: "An older binary **starts without complaint** against a database that a newer binary has migrated: it does not check for a newer schema. Running it that way is unsupported." After this change it refuses; the sentence must become the refusal and its recovery (the handoff already says to update `upgrade.md`; the RFC's header `Touches` lists only `deployment.md`, `migrations.rs`, `errors.rs`, and none of `startup.rs`, `cli.rs` or the message plumbing H3 needs). `deployment.md:483-506` sends the operator to `journalctl | grep -i migrat` after an upgrade: the refusal line should contain the word so that grep finds it. `docs/src/guides/upgrade.md:26` ("each migration runs once") is fine.

### Low

**L1 — Two processes starting at once race.** `run` reads the version and then migrates without a lock, so two new binaries starting together can both decide to apply migration N; the loser fails with `duplicate column`. Reading the version inside `BEGIN IMMEDIATE` (which this RFC needs anyway to make "read, decide, refuse" one step) closes it. Not in the RFC; cheap while the function is open.

**L2 — `+43`** parses. See M2.

**L3 — The handoff's line numbers** (`278–303` at `9f6acdb`) have moved to `298–322`. Cite by function.

## 3. The measured result of item 4 (this sets defect 2's severity)

Method: a scratch integration test in the store crate (never committed): populate a file database through `Database::open` and `repos::users::create` (one user row), return it to rollback-journal mode, stamp `sui_meta.schema_version` (a raw `rusqlite` connection), run `Database::open` again, then compare **every table's row count, `sqlite_master`, the file bytes and the stored version** before and after. `MAX_SCHEMA_VERSION` = 43.

| Stamp | `Database::open` | Stored version after | Rows / schema |
|---|---|---|---|
| `garbage` (text) | **Err** `duplicate column name: allowed_scopes` | **`1`** (was 43) | unchanged |
| row deleted | **Err**, the same | **`1`** (row re-created) | unchanged (+ the new `sui_meta` row) |
| `44` (**too new**) | **`Ok`** | `44` | unchanged |
| `43` stored as a **BLOB** | **Err**, the same | **`1`** | unchanged |
| `-1` | **Err**, the same | **`1`** | unchanged |
| `99999999999` | **Err**, the same | **`1`** | unchanged |
| `` (empty) | **Err**, the same | **`1`** | unchanged |
| `+43` | `Ok` | `+43` | unchanged |

**What the re-run does:** migration 0001 is **all `CREATE TABLE IF NOT EXISTS`**, so it succeeds silently on an existing database and **stamps the version `1`**; migration 0002 then fails on `ALTER TABLE … ADD COLUMN` (`duplicate column name`), and the runner returns that error. So at this baseline **no data and no schema is damaged** (row counts and `sqlite_master` are identical), which is the answer to "does 0001 fail, drop or corrupt": it **silently succeeds, and it is the migrations after it that fail**. **The damage is to the metadata:** the real version (43) is **overwritten with `1` and lost**, the database is now **permanently unstartable** (every later start re-fails at 0002), and the error the operator reads is "database I/O error / duplicate column name". Recovery needs a hand-written `UPDATE sui_meta` by someone who knows the number was 43. **Severity: an availability and information-loss defect today, not a data-corruption one, and it depends on 0001 and 0002 staying idempotent-then-failing**: a future edit to either turns this into silent damage. I read 0001 and 0002: neither contains an `INSERT`, `UPDATE` or `DELETE` statement (only DDL), which is why row counts were unchanged.

**The real binary, measured** (scratch debug build at `2adf796`, a real config, `sui-id admin unlock-user` and `serve`): stamp 44 → the CLI runs and the server **starts and serves** (it printed its setup banner); stamp `garbage` → `Error: opening database … 0: database I/O error 1: duplicate column name: allowed_scopes`, **exit 1**, stored version now `1`, and the second run fails identically.

**Journal-mode write (H2):** rollback-journal database stamped 44 → `open` → header bytes `[1,1]` → `[2,2]`, file not identical, `journal_mode` afterwards `wal`. A database already in WAL: main file identical, no side files. **Read-only pre-check:** main file identical in both modes; leaves empty `-wal`/`-shm` beside a WAL database; on a foreign database it errors `no such table: sui_meta` and on a missing path `unable to open database file`, which is the classification H1 needs.

## 4. Answers to items 5–16

**5. Every path that opens a database.** `Database::open`: server start `runtime/startup.rs:164`; `--dev` pinned database `runtime/dev_mode.rs:370`; CLI `run_admin_unlock_user` (`cli.rs:139`), `run_admin_reset_mfa` (`:178`), `run_admin_issue_recovery_link` (`:228`), `run_admin_rotate_key` (`:358`), `run_setup` (`:506`), `run_admin_rotate_metrics_token` (`:774`), `run_admin_issue_registration_token` (`:828`). **All nine would be refused** under the proposed rule, and should be: each reads or writes tables of a shape the binary does not know. `open_in_memory` (`db.rs:44-49`, fresh every time) is unchanged. **Not `Database::open` and therefore unaffected:** `backup` (raw `rusqlite::Connection::open`, `ops.rs:108`), `verify-backup` and `restore` (staged temp files, `ops.rs:240`), `--version`, `--help` and `--print-sample-config` (answered in `main.rs:26-42` before any database). Test-only: `run_up_to` callers (`tests_rfc021/103/115`) call the runner directly and are not affected.

**6. The trade.** *The case against:* a rolled-back deployment is the standard reason; expand/contract practice says an older binary should keep working against an additive schema, and `docs/src/guides/upgrade.md:70-78` records that migrations 0033–0038 are additive ("backwards-compatible"). A blue/green pair sharing one database file, or an operator who cannot reach the newer binary at once, is stranded by a refusal that a tolerant check would not impose. *Why refusal is still right:* additive is a property of some migrations, not of the runner. Five migrations drop or rebuild tables (0013, 0019, 0021, 0022, 0043: `DROP TABLE` / `DROP COLUMN`), and 0043 dropped `credentials.must_change` (RFC 115): a binary from before it would fail **on every credential operation at runtime**, not at start. "Starts without complaint" is the silent half of the failure, and it is the worse half for an identity provider: the operator finds out from users. The runner cannot tell additive from destructive, so integrity dominates. *The 3 a.m. route forward exists and is short:* run the binary that migrated it (M3 makes the message name it), or `sui-id restore --from <pre-upgrade backup> --force` (`upgrade.md:88-93`, `deployment.md:494-500` already document exactly this). Refusal without a route would fail the "does not confuse its operator" half; with M3 and H3 it does not. I recommend **no override flag**: it recreates the hazard the RFC removes, and a supported recovery already exists.

**7. Which commands must still work.** Unaffected today and to stay so: `backup` (a file-level `VACUUM INTO` snapshot: read-only, no schema assumption), `verify-backup`, `restore`, `--version`, `--help`. **They are safe to exempt because none of them constructs a `Database`.** Two cautions: `backup` must **not** stamp `schema_version: 0` when it cannot read the version (M1): it should refuse, or record the real value; and a `restore` onto a too-new live file works today and should. A small read-only `sui-id` command that prints the stored version and the binary's ceiling would let an operator *read a version* without a refusal in the way; optional, and only if it uses the shared reader from M1.

**8. Startup-only check.** Yes, it leaves the hole: the newer binary migrates while the older one already runs; the older one has passed its check and (one `Arc<Mutex<Connection>>`, `backend.rs:78-91`) keeps writing to tables it does not know. **It is not closable by this RFC** and I would not try to widen it. What would close it: re-reading the stored version on the existing background tick (`gc::spawn` in `main.rs`) and refusing further writes with the same error; or a lock file. Recommend recording it in the RFC as a stated non-goal and in `deployment.md` as "one binary version per database at a time", and giving it its own RFC if the owner wants it. (L1's `BEGIN IMMEDIATE` covers two *new* binaries starting together, not this.)

**9. Taxonomy.** Two variants are the right *start*; three cases fall outside them: **overflow** (should be `TooNew`: M2), **a migration that fails to apply** (today "database I/O error": add `MigrationFailed`), and **"no row, populated database"** (H1: `Invalid`). A fork's number collision is `TooNew` when the fork is ahead (correct) and undetectable when it collides below the ceiling (out of scope: a version number is not identity). A row present but empty is `Invalid` (measured: today it re-runs).

**10. Nothing is written on refusal.** **Expressible, but only with the ordering H2 gives, and not as the RFC words it.** Required: read-only connection first; no `CREATE TABLE`; no `BEGIN` on the refusal path; no `PRAGMA user_version` (sui-id does not use it: the version is in `sui_meta`); no journal-mode change. **What the test should assert** (all measured feasible): for a database in **rollback-journal** mode *and* one in WAL mode, stamped `MAX + 1`, `Database::open` returns `SchemaTooNew`, and afterwards the **main file's bytes are identical**, `sqlite_master` and every table's row count are identical, and `sui_meta.schema_version` is unchanged. **Do not assert** the absence of `-wal`/`-shm` (a read-only connection leaves empty ones). Mutation: move the check after the pragma, and the rollback-journal case must fail.

**11. The operator's line.** Draft (one line to stderr, first and alone; wrapped here for reading):

`sui-id: refusing to start: the database at /var/lib/sui-id/sui-id.sqlite is at schema version 44, but this sui-id 0.78.0 understands up to 43 (it was last migrated by sui-id 0.79.0). Run sui-id 0.79.0 or newer, or restore the pre-upgrade backup with "sui-id restore --config <config> --from <backup.tar> --force". Nothing was changed. Do not edit or delete the database, and do not run migrations by hand.`

For `SchemaVersionInvalid`: `sui-id: refusing to start: the schema version recorded in the database at <path> is unreadable ("garbage"), or missing from a database that has 26 tables, so migrations were not run. Nothing was changed. Restore the most recent backup with "sui-id restore …", and keep this file for inspection.` Both name the path (an operator with two instances needs it), contain the word "schema" and "migrat" for the `grep` in `deployment.md`, and end with what *not* to do.

**12. Does it reach the operator?** Traced: `Database::open` → `StoreError` → `.context("opening database")?` in `startup::prepare` (`startup.rs:164`) and all seven CLI functions → `main() -> anyhow::Result` prints anyhow's debug format, **multi-line, first line "Error: opening database"**, **exit 1**. Swallowed or buried: the cause is under "Caused by:"; not logged through tracing on either path; identical exit code to every other failure. See H3 for the fix. **Wrapped:** `.context()`. **Logged at a level nobody sees:** not logged.

**13. Is a refusal recorded?** It cannot be an audit row (the audit log is in the refused database, and writing it would be a write the RFC forbids). **A log line is enough, at `error`**, one event with `found`, `supported`, `db_path`, from the shared handler, in `serve` where tracing is initialised (it is, before the open); the CLI has none and stderr is its record. RFC 094's contract covers commands that write an audit row in a transaction; a refusal precedes every command, so it is outside that contract, and the analogy that fits is RFC 102 ("a sign-in that cannot be audited does not succeed"): fail closed when the system cannot vouch for what it is about to do.

**14. Interaction with RFC 106 and the other readers.** See M1: **three readers today** (server `run`, backup create with `unwrap_or(0)`, restore on the manifest), a fourth planned (106 F1), and a display (settings) that shows the wrong number. They must share `read_stored_version` and `check_supported`; RFC 112 should land them so 106 consumes them. 106's "a snapshot with no readable version is refused" is exactly H1's rule applied to a snapshot, and its message should be the same message.

**15. Threats.** *Who can write the version row:* anyone with write access to the SQLite file (the process owner, `root`, a backup restore) and a newer binary's migrator. Someone who can write the file can already delete tables, corrupt rows or truncate it, so the refusal adds **no capability** that boundary did not have; it makes one existing denial a one-`UPDATE` action. **A tension to state in the RFC:** `startup.rs:171` deliberately does **not** refuse on an audit-chain mismatch because that "would let an attacker DoS the IdP by corrupting one row". Refusing on a version stamp is consistent because the two differ in kind: a chain mismatch means data is *suspect but its shape is known*; a too-new stamp means *the shape is unknown and continuing writes into it*. Say that in one sentence so the two decisions do not look contradictory. *Missed:* the recovery from an attacker- or fault-set stamp is a backup restore, so the message must not teach editing the row (it does not, in §11). *Introduced by H1's fix:* none.

**16. What cannot be built as described, or is better another way.** As written: (a) "missing row → 0" (H1); (b) "nothing is written" (H2); (c) "a one-line message" via a variant alone (H3). Better another way: one shared reader and checker (M1) rather than a guard inside `run` only. **What the RFC does not mention and should:** the journal-mode order, the exit code and restart behaviour, `last_migrated_by`, the backup-create `unwrap_or(0)`, the settings page, the concurrency non-goal, and `upgrade.md:94-98`. **Docs that change:** `docs/src/guides/upgrade.md` (the "starts without complaint" paragraph; a short "what the refusal looks like" note) and `docs/src/guides/deployment.md` (§11's downgrade sequence: state that an older binary now refuses, that the `restore` step is the route, and the exit code if H3's distinct code is adopted; the `Restart=on-failure` stanza at `:227`, which would restart a refusing service until the start limit). Both already contain statements this makes false or incomplete.

## 5. Recommendation

**Accept with the changes named:**
1. **H1:** `0` only when the database has no application tables; otherwise `SchemaVersionInvalid`.
2. **H2:** the check first, on a read-only connection, before the pragmas and before `CREATE TABLE IF NOT EXISTS`; the test asserts main-file bytes, `sqlite_master` and row counts in **both** journal modes.
3. **H3:** one handler for the refusal, the line first and alone on stderr, a `tracing::error!` where tracing exists, a distinct exit code and the `RestartPreventExitStatus=` note; the RFC names the code.
4. **M1:** land `read_stored_version` / `check_supported` and route backup create, restore, verify and the settings page through them; RFC 106 consumes them.
5. **M2, M3, M4:** `i64` parse with overflow as too new, `MigrationFailed`, `last_migrated_by`, and the `upgrade.md` / `deployment.md` changes; add `startup.rs`, `cli.rs`, `backup/ops.rs` and `settings.rs` to `Touches`.
6. State the concurrency limit (item 8) and the audit-chain distinction (item 15) as one sentence each.

**Severity, stated so the RFC's framing is not overstated or understated:** at this baseline the garbled-stamp case **destroys the version and makes the database unstartable but does not damage data**, and the too-new case **runs silently**. The RFC's case for acceptance is sound; its case that the current behaviour "corrupts" is not what I measured, and the closure prerequisites should say what was measured.
