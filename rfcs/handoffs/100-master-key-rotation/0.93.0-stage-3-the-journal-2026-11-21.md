## What this stage is, and is not

**It builds the journal as a module, tested on its own. The live rotation
does not use it yet.** The rule *"recovery lands before the thing it
recovers"* forbids it: a rotation that created a workspace today would leave
one, after a crash, that no recovery reads. Stage 4 builds that recovery,
and stage 5 wires the journal into the rotation. Stage 2's P3 already
refuses a leftover workspace, so nothing in between can trip over one.

**Not here:** new-key and backup publication (stage 5, which uses this
protocol), recovery (stage 4), and any change to the live rotation's
sequence.

## §1 — what the adapter and the simulator lack, measured on `79ed9c5`

- **The adapter cannot make a directory.** `KeyFileOps`
  (`runtime/key_adapter.rs:39`) has `create_new`, `write_all`, `sync_file`,
  `rename`, `publish_no_replace`, `sync_dir`, `read`, `remove` and
  `metadata`, and nothing for directories. Add **`create_dir(point, path)`**:
  mode `0700`, the current owner, failing if anything exists at the path, a
  symlink included. Add **`remove_dir`** too. In `Real`, use
  `std::fs::DirBuilder` with the mode set, never a create-then-chmod.
- **The simulator models one directory** (`simulated.rs:35`, *"One directory's
  worth of durable state"*). The workspace is a directory **inside** the key
  file's directory, so it must model two, with the durability rules a real
  filesystem has:
  - the workspace's **own existence** becomes durable only when its
    **parent** is synced;
  - an entry **inside** the workspace becomes durable only when the
    **workspace** is synced;
  - after a power loss, a workspace whose own entry was not yet durable is
    gone, and everything that was in it with it.

  Power-loss enumeration and materialization must cover both. **Stop and
  return** if this needs the simulator restructured beyond adding a second
  directory level (say what, and why), rather than modelling it loosely.

## §2 — the journal's content, and its tags

**The body** binds, as RFC 100 lists it:
- the rotation ID;
- the old and new key **fingerprints** (stage 1's format);
- the canonical active, workspace, next and backup paths, and **every
  reserved temporary path** (the intent temporary, the update temporary,
  the new key's and the backup's temporaries);
- the expected owner and mode;
- the requested **backup disposition**: `RetainUntil { review_at,
  custody_reference }` or `RemoveAfterVerified { verification_reference }`
  (`implementation.md`, stage 5; a required field, so stage 5 cannot forget
  it);
- the **state**: `Intent`, `NextTempVerified`, `NextPublished`,
  `BackupTempVerified`, `BackupPublished`, `Prepared`.

**No key material, ever**: no key, no part of one, no derived value but a
fingerprint or a tag.

**The format** is JSON: a version, the body, and two tags. The body is a
struct with a fixed field order and no maps and no floats, so serializing it
is deterministic. **A test round-trips a body and requires byte-identical
output.**

**The tags** are `HMAC-SHA256(key, "sui-id/rotation-journal/v1/old" || 0x00 || body)`
under the old key, and the same with `…/v1/new` under the new key: domain
separated from each other and from the fingerprint's label. Put this in
`sui_id_store::crypto` beside the fingerprint, which already has `hmac`.
**Verification with one key** reports which role it holds, *old* or *new*,
if either tag matches, and neither otherwise. That is what lets recovery
authenticate the journal with whichever key opens the sentinel.

## §3 — the protocol (RFC 100, exactly)

- **The lock.** Create `<active>.rotation-work` with `create_dir`, then sync
  its parent. Its existence is the lock: if it exists, refuse.
- **The intent.** Inside the workspace, write `intent.write` (checked write,
  sync), read it back and verify both tags, **publish without replacement**
  to `intent.json` (`publish_no_replace`), then sync the workspace. A crash
  before publication leaves only `intent.write`, which is non-authoritative.
- **Each state advance** goes through the reserved update temporary: write,
  sync, read back and verify both tags, **atomically replace** `intent.json`
  (`rename`), then sync the workspace. A crash leaves the prior
  authenticated state or the new one, never a mixture.
- **States only move forward.** An advance to an earlier or equal state is
  refused.
- **Reading a journal** for recovery reads only `intent.json`, never a
  `*.write` temporary, and returns the verified body and which key role
  verified it.

## §4 — tests, in all three modes where a file is touched

`implementation.md`'s list, each a named test:
- **the lock**: a second creation refuses, and changes nothing;
- **tags**: the old key verifies as *old* and the new as *new*; a third key
  verifies as neither; a body changed by one byte verifies as neither;
- **a partial `intent.write` is non-authoritative and safely deletable**:
  after a crash at every point before publication, reading the journal finds
  none, and the temporary can be removed;
- **every state advance is atomic, in all three modes**: in the power-loss
  mode, materialize every state the simulator enumerates for each advance.
  Each holds either the prior authenticated journal or the new one, and
  never an unauthenticated or mixed file at `intent.json`;
- **the workspace's own durability**: a power loss after `create_dir` but
  before the parent's sync can lose the workspace entirely, and the
  simulator says so (the case §1 adds);
- **no key material**: the published journal's bytes contain neither key,
  in raw bytes or in base64;
- **monotonic**: advancing backward refuses.

**Mutation:** drop the workspace sync after an advance; the power-loss test
finds a state where the new journal is not durable.
