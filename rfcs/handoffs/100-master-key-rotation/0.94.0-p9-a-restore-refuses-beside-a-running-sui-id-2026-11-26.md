## §1 — the gap, measured at `4070e73`

`sui-id backup restore --force` overwrites the database file and the key file whether or not sui-id has them open:
- `cli/handlers.rs`, `run_restore`, reads the passphrase, then calls `backup::run_restore`;
- that calls `sui_id_store::backup::ops::run_restore`, which takes no lock;
- without `--force`, it refuses only because the files exist.

**Beside a running server**, the server keeps its open connection and the old key in memory. What it writes afterwards goes
to the replaced file, or into the restored database under a key that may not be the restored one. **Nothing reports anything.**
That is exactly what P7 closed for the rotation. The guide says only that `--force` is *"if you really mean it (typically
only when recovering onto a fresh host)"*.

## §2 — the fix: the same lock, taken the same way

- **`backup restore` takes the liveness lock exclusively, always**, not only with `--force`:
  - it uses P7's lock, `<key_file>.rotation-lock`, through the same adapter;
  - it holds the lock through the whole write, and releases it after.

  **One rule**: a command that replaces the database or the key wholesale holds the lock exclusively. An exception for
  "no `--force`" would be a second rule an operator has to know.
- **The refusal comes first.** The lock is taken **before the passphrase prompt** (with `--decrypt`) and before the source is
  read. P7's review lesson applies: an operator must not type a passphrase and then be refused.
- **The sentence names the command.** `take_rotation_lock` says *"refusing to rotate: …"*. Generalize it so each caller states
  its own verb, for example a `take_exclusive_lock(adapter, paths, label, Action::Restore)`. Then the restore says:
  *"refusing to restore: sui-id is running -- the server, or another sui-id command -- and has this database open (<lock
  path>). Stop it, then restore."* The rotation's text stays exactly as it is now, and P7's tests still pin it.
- **Nothing in `sui-id-store` changes.** Moving the guard into the store's own `open` is RFC 009 stage 1's design, and must
  happen once, there.
