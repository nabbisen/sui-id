## What is wrong, measured on `ec1de8c`

- **A key is generated before the database is looked at.**
  `keyring::resolve_impl` (`runtime/keyring.rs:42-80`) generates and writes a
  new key whenever the key file is missing (`:66-75`). Startup calls it at
  `runtime/startup.rs:168`, and only then opens the database (`:192`). A key
  file lost over a sealed database therefore gets a **new** key, and the
  sealed columns become unreadable: prefix 2 of the crash matrix.
- **Nothing checks the key at startup.** A wrong key is first noticed when a
  signing key is unsealed at token issuance (RFC 100 *Refresh*, *Detecting the
  wrong key*).
- **Eleven places resolve the key**: startup (`startup.rs:168`) and ten in
  `cli.rs` (`:312`, `:354`, `:407`, `:605`, `:814`, `:1151`, `:1207`, `:1346`,
  `:1376`, `:1620`), counted with `git grep -c`, not by eye.

## §1 — the migration: the sentinel, and the rotation row

Migration **0052** (the last is `0051_…`), two singleton tables:
- **`master_key_sentinel`**: `id` (`CHECK (id = 1)`), `sealed` (BLOB, not
  null), `key_fingerprint` (TEXT, not null), `written_at` (TEXT, not null).
- **`master_key_rotation`**, unused until stage 6: `id` (`CHECK (id = 1)`),
  `rotation_id`, `old_fingerprint`, `new_fingerprint`, `state`
  (`CHECK (state IN ('db_committed_pending_activation', 'complete'))`),
  `started_at`, `updated_at`, `backup_filename`, `custody_disposition`. Only
  the columns `implementation.md` names; no others.

## §2 — the fingerprint

RFC 100 requires *"non-secret key fingerprints"* and fixes no format. **This
dispatch fixes it, once, in the store's crypto module:**
`HMAC-SHA256(key, "sui-id/master-key-fingerprint/v1")`, its first 8 bytes in
lowercase hex (16 characters). Keyed and domain-separated: it identifies a
key, and reveals nothing usable about it. Add `hmac = { workspace = true }`
to `sui-id-store`. It is already a workspace dependency and in `Cargo.lock`,
so **no new crate is built**; confirm that `Cargo.lock` does not change.
**Test:** two keys give two fingerprints; the same key gives the same one; a
known test key gives a known value (a vector, computed independently and
written in the test).

## §3 — the sentinel

A fixed plaintext, `b"sui-id master key sentinel v1"`, sealed with
`crypto::seal` under the AAD `b"sui-id/master-key-sentinel/v1"`, stored with
the sealing key's fingerprint. **The key opens the sentinel, or it is the
wrong key.**

## §4 — the decision, made before anything is written

**Read the database read-only first**, with `migrations::open_preview_connection`
(`sui-id-store/src/migrations.rs:529`, an `immutable`, read-only connection),
before `Database::open` runs any migration. Then decide, from two facts:

- **the key**: present (from `SUI_ID_MASTER_KEY` or the key file), or
  **missing**. Reading must no longer generate;
- **the database**: no file; a sentinel; no sentinel but sealed rows in any
  of the six tables K07 reseals (`commands.rs:6773-6787`: signing keys,
  refresh tokens, user TOTP, WebAuthn credentials, the SMTP configuration,
  the email outbox); or no sentinel and no sealed rows. A table that does
  not exist in an old schema counts as empty.

| Database | Key present | Key missing |
|---|---|---|
| no file | use it; write the sentinel after migration | **generate**; write the sentinel after migration |
| **sentinel** | it must open the sentinel, or **refuse** | **refuse**: never generate |
| **no sentinel, sealed rows** (an upgrade) | it must open **one** sealed row, or **refuse**; then write the sentinel | **refuse**: never generate |
| no sentinel, no sealed rows | use it; write the sentinel | **generate**; write the sentinel |

This is the confirmed upgrade rule: *"never infer 'never sealed' from a
missing sentinel alone."*

**Opening one sealed row** uses that table's own opening code and AAD, the
ones its `reseal_all` uses. Try the six in a fixed order and stop at the
first row found.

**Write the decision as one pure function** over those two facts, returning
an enum of the outcomes above, and have the code act on its result. **Test
the chooser itself** (each of the eight cells), not only the actions.

**A refusal** happens before readiness and before any migration. It names
fingerprints, never key bytes, and says what to do. For example:

> *the master key in ./sui-id.key (fingerprint 3f9a…) does not open this
> database, whose sentinel was written under fingerprint 81c2…; restore the
> matching key file, or set SUI_ID_MASTER_KEY to it.*
>
> *no master key file at ./sui-id.key, but this database holds data sealed
> under a master key (fingerprint 81c2…). Generating a new key would make it
> unreadable. Restore the key file.*

The second form names the sentinel's fingerprint when there is one. In the
upgrade case there is none to name, so it says so plainly.

**The sentinel is written after migration and before readiness**, in its own
transaction. If a power loss takes that write, the next start finds sealed
rows and no sentinel, and the upgrade rule verifies the key and writes it
again. **So it needs no stronger durability than that**; do not add a
checkpoint for it. Log one `INFO` line naming the fingerprint. **No audit
event**: the audit contract (RFC 094) is not changed by this stage.

## §5 — one way in, for all eleven

**One function opens the database with its key checked.** Startup and every
`cli.rs` caller use it, the rotation command's old-key load (`cli.rs:605`)
included. **`keyring::resolve` is no longer called anywhere else.** Add the
guard `implementation.md`'s rules imply: a source scan that fails if
`keyring::resolve(` appears outside the keyring module and its tests.
**Mutation:** add one call in `cli.rs`; red.

## §6 — tests, in all three modes where a file is touched

`implementation.md`'s list, each a named test:
- a wrong key refuses before readiness, and before any migration;
- a missing key file over a sealed database refuses, and **writes nothing**:
  no key file, no migration (in Simulated: no operation recorded on the key
  path);
- a missing key file over a never-sealed database generates one;
- the upgrade path, both ways: sealed rows the key opens (the sentinel is
  then written), and sealed rows it does not open (refused);
- migration up, on a database from `0.92.0`: build one with the `0.92.0`
  schema, migrate, and check both tables exist and the sentinel is written
  under the existing key.

**And the end-to-end refusal, through the real binary:** set up an instance,
stop it, replace `sui-id.key` with another key, start it again. It must exit
non-zero, print the refusal with both fingerprints, and leave the database
file byte-identical (compare a hash before and after).
