## Two decisions (2026-11-21)

The architect asked; `@nabbisen` answered each with the option named below.

1. **A rotation that stopped before the database was resealed is cleaned,
   and the service starts.** RFC 100 allows "resume or clean". The answer
   was *"Clean and start (Recommended)"*. Recovery verifies every leftover
   against the authenticated journal, removes only what the journal binds,
   says exactly what it removed, and continues on the old key. **Resume is
   not built**: to rotate, the operator runs `admin rotate-key` again.
2. **A pre-rotation backup found during that cleanup is removed, after
   verification.** The answer was *"Remove it, verified (Recommended)"*.
   The backup is a copy of the key that is still active. It is removed only
   once its decoded key's fingerprint equals the active key's, and never on
   the strength of its filename. Keeping it would leave an untracked second
   copy of the live key once the journal that recorded its disposition is
   gone (M5).

## What this stage is, and is not

**It recovers every state the preparation prefix can leave**: the
recovery table's rows 1–7, and row 11, *fail closed*. Nothing writes a
workspace yet (stage 5 wires the journal into the rotation), so every state
here is built directly or materialized from the simulator.

**Rows 8–10 are not here, and that is a scoping change, made here.** They
read *"DB new and pending"* and *"complete"*, which are the
`master_key_rotation` row, and they run K05. Stage 6 builds both, so those
rows land **in stage 6, recovery first within it**. Until then, a workspace
beside a database the active key does not open **fails closed** and
preserves every file. That is row 11's outcome, and it is safe: nothing is
removed that might be the only key the database opens with.
`implementation.md` is updated to say so.

**Not here:** resume; rows 8–10; K05; any audit event (recovery writes
none); any change to what `admin rotate-key` does once its preconditions
pass.

## §1 — what exists, measured on `445a97e`

- **The hook is `database::open_checked`** (`runtime/database.rs:208`). It is
  the one open that startup (`startup.rs:180`) and every `cli/handlers.rs`
  command go through. Recovery runs **first in it**, before
  `resolve_checked`.
- **`admin rotate-key` (not `--check`) runs the same recovery** before its
  preconditions. It resolves its key through `keyring::resolve_checked`
  directly, not `open_checked`, so call recovery there explicitly. It is
  the command most likely to meet its own leftover.
- **`--check` never runs recovery.** It changes nothing (stage 2's rule). P3
  still reports the leftover workspace, with new text (§4).
- **The sentinel check already exists.** `resolve_checked_impl`
  (`keyring.rs:122`) uses `sui_id_store::master_key_check::{inspect,
  decide, sentinel_opens}`. Reuse it; don't write a second one. Measure
  what it opens and how before you call it.
- **The simulator's `remove` is not durable-modelled.** It changes only the
  live view and records no op, so a power loss can never bring a removed
  file back. Recovery is made of removals. Add **`Op::Unlink(path)`**, which
  becomes pending on `remove` and durable on a `sync_dir` of its parent,
  exactly like `Link`, and include it in power-loss enumeration. **Stop and
  return** if that needs more than one new op and its `apply`/`owning_dir`
  arms.

## §2 — one derivation for every path

Stage 3's body binds eight paths, and its test sample built them ad hoc
(`with_extension("ready")` turns `t.key` into `t.ready`). Before recovery
can check that a journal binds *the right* paths, they need one source.

Add **`RotationPaths::for_key_file(key_file)`** beside
`preconditions::workspace_path`, built from `sibling_with_suffix`. Every
field is derived from the key file:

| Field | Path |
|---|---|
| `active` | `<key_file>` |
| `workspace` | `<key_file>.rotation-work` (unchanged; P3 uses it) |
| `next` | `<key_file>.next` |
| `backup` | `<key_file>.pre-rotation` |
| `intent_temp`, `update_temp`, `next_temp`, `backup_temp` | `intent.write`, `update.write`, `next.write`, `backup.write` inside the workspace |

**Backup: one name, not a timestamp.** Only one rotation can be in progress
at a time (the workspace is the lock). A *retained* backup's lifetime past
`Complete` is stage 7's to name, and stage 7 renames it on completion if
it needs to. Make `workspace_path` a call into `RotationPaths`, so there is
one derivation. Make `sample_body` use it as well.

## §3 — recovery, as a procedure

Add `runtime/rotate/recovery.rs`:
`pub fn recover(adapter: &dyn KeyFileOps, key_file: &Path, db_path: &Path) -> anyhow::Result<Recovered>`.
`Recovered` is `Nothing` or `Cleaned { removed: Vec<PathBuf> }`. Every file
operation goes through the adapter (stage 3's walking guard already scans
`rotate/`).

**Classification, in this order. Any failed check fails closed: change
nothing, name what mismatched, and exit non-zero before readiness.**

1. **No workspace** (`metadata` says not found): `Nothing`. Row 1. The
   adapter records no file operation.
2. **The workspace itself**: a directory, not a symlink, owned by the
   current uid, mode `0700`. Otherwise fail closed.
3. **The active key**:
   - read from `key_file` through the adapter;
   - **file origin only**: an environment-supplied key beside a workspace
     is a mismatch, since rotation refuses `Env`;
   - it must **open the sentinel**.

   Otherwise fail closed. This is where rows 8–10's states land until
   stage 6.
4. **No `intent.json`** (row 2): every entry is a regular file named
   `intent.write` or `update.write`, and nothing else. Any other entry, a
   directory or a symlink fails closed. Otherwise clean them (step 7).
5. **`intent.json` present**:
   - `journal::read` with the active key must return role **Old**;
   - `body.old_fingerprint` must equal the active key's fingerprint;
   - **all eight bound paths** must equal `RotationPaths::for_key_file`'s;
   - every workspace entry is one of the bound temporaries or
     `intent.json`.

   Role **New** with the active key means activation already happened,
   which is stage 6's row 9, so fail closed.
6. **The artifacts outside the workspace**, rows 3–7. If `next` exists, it
   must:
   - be a regular file, not a symlink;
   - have the expected owner and mode, from the body;
   - decode to a key whose fingerprint is `body.new_fingerprint`.

   If `backup` exists, it must meet the same three tests, except that its
   key's fingerprint must be **the active key's** (decision 2). A mismatch
   on either fails closed. Bound temporaries inside the workspace may be
   partial, so they are removed without decoding.
7. **Clean, in this order, each removal through the adapter:**

   | Step | Action | Why |
   |---|---|---|
   | a | `backup`, `next`, then sync the key's directory | Published artifacts go first, while the journal that binds them still exists (M3, read backward) |
   | b | `next.write`, `backup.write`, `update.write`, `intent.write`, then sync the workspace | |
   | c | `intent.json`, then sync the workspace | After (b) is durable, never in the same sync. A power loss after (c) then leaves an empty workspace, never row 2 with a `next.write` in it, which step 4 refuses |
   | d | `remove_dir` the workspace, then sync its parent | |

   Every removal tolerates `NotFound`, so a re-run after a crash at any
   point finishes the job. `removed` lists what *this* run removed.
8. **Report it.** In the server's log, at warn, and on stderr for a CLI
   command, before anything else that command prints:
   - one line saying a stopped rotation was cleaned and sui-id continues on
     the active key (with its fingerprint);
   - then one line per removed path;
   - then how to rotate again.

   Fingerprints only, never a key.

**Fail-closed text** says, in words an operator can't misread:
- what was found;
- which check failed, naming the path;
- that **nothing was changed**;
- not to remove the workspace by hand;
- where the operator documentation will describe manual recovery (stage
  7 writes that; for now, name the workspace and the key files to keep).

## §4 — the texts that stage 5 would make false

- **P3's `leftover_workspace_text`** says the workspace "holds no key
  material, only the in-progress journal", and invites removal by hand.
  From stage 5 it holds `next.write`, a key. Replace it: name the
  workspace, say that starting sui-id or running `admin rotate-key` lets
  recovery check it and either clean it or refuse and say why, and say
  not to remove it by hand.
- **`journal::lock_workspace`'s refusal** gets the same correction.

## §5 — tests

Every row is entered deterministically, and observed rather than reasoned
about (`crash-matrix.md`).

- **Row 1:** no workspace. `Nothing`, and Simulated records no operation.
- **Row 2:** every subset of `{intent.write, update.write}`, including
  empty. The result is clean, and `removed` is exact. An unexpected entry
  fails closed with every file unchanged, byte for byte: try `notes.txt`, a
  subdirectory, and a symlink named `intent.write`.
- **The workspace check:** a symlink fails closed, and so does mode `0755`.
  **Owner:** a real file with another owner needs root, and root is not
  asked for. Test the owner comparison through a `metadata` that reports
  another uid (a small test adapter, as stage 3's `RespellingReads` is).
- **Rows 3–7:** a journal in each state, `Intent` through `Prepared`. Each
  carries the artifacts that state allows, partial temporaries included.
  Each cleans to row 1, `removed` is exact, and the database still opens
  with the active key afterwards. Separately, each of these fails closed
  and changes nothing:
  - a `backup` whose key is not the active one;
  - a `next` whose fingerprint is not `new_fingerprint`;
  - a `next` that is a symlink.
- **Binding:** a journal sealed with the right keys but binding another
  workspace or `next` path fails closed.
- **Authentication:** a tampered journal fails closed, and so does a journal
  sealed under keys that do not include the active one.
- **Role New, and the database not opening with the active key,** each fail
  closed (stage 6's rows), with every file preserved.
- **Recovery survives its own crash.** Run `recover` under Simulated.
  **Use paths inside a real temporary directory**, so the bound paths are
  real. Take every point, every power-loss state and the kill state;
  materialize each into that directory beside a real database sealed
  under the active key; run the real `recover` again. It ends at row 1 with
  the database opening, and never fails closed on a state its own cleanup
  left. (Recovery only removes, so a short write does not apply: say so.)
- **Entry from preparation.** Run stage 3's `lock_workspace`,
  `write_intent` and every `advance` under Simulated, with real-directory
  paths again. Every point's power-loss and kill states, materialized
  beside the database, must recover to row 1.
- **End to end, the real binary.** With a row 3 state built beside a real
  database, `sui-id serve` starts. Its log names each removed path, and an
  `admin` command's stderr does too. With a `backup` of the wrong key, it
  exits non-zero before readiness, and every file is byte-identical
  afterwards. Hang guards are generous (`tests/e2e/key_rotation.rs` shows
  how).
- **`--check` with a leftover workspace** changes nothing (Simulated: no
  operation) and prints P3's new text.

**Mutations, each run and reverted, each caught:**
- merge steps 7b and 7c into one sync, so the recovery-crash test finds a
  state it then refuses;
- skip the backup fingerprint check;
- skip the bound-path comparison;
- make `remove` in the simulator non-durable again (the old behaviour), so
  the recovery-crash test loses its power-loss coverage. Show that it does.
