## What this stage is

**`admin master-key rotate` stops using the old sequence.** Today the
old sequence stages `<key>.new`, runs K07, renames the old key to a
timestamped `.bak`, then renames `.new` into place, with a best-effort
`rotated` append after it. Instead, it runs RFC 100's whole protocol,
using what stages 3–4 and P1 built. **Every crash point it can reach
already has its recovery.** That is why P1 came first.

**Not here:**
- custody *enforcement*: removing a verified backup, and the overdue
  finding (stage 7, P3);
- the operator documentation, and the "not yet crash-safe" warning, which
  goes only in P3.

## §1 — the liveness lock, before anything else

Stage 4 reads "the workspace exists" as "a rotation stopped". A running
rotation must be told apart from a stopped one, or recovery started by
another process (an `admin` command, or the server) deletes `next` and
the journal under it. K08 would then reseal under a key that no longer
exists.

**One lock, one file, taken first by both sides.** The file is
`<key_file>.rotation-lock`, added to `RotationPaths`: permanent, empty,
mode `0600`, and never deleted.
- **The rotation** opens it (creating it if absent) and takes an
  exclusive `flock` **before it checks preconditions or creates the
  workspace**. It holds the lock until it returns, on success or on
  error. The kernel releases it if the process dies, which is exactly
  the difference between "running" and "stopped".
- **Recovery** opens the same file (creating it if absent; an empty file
  is harmless) and takes the lock **non-blocking**, before it classifies
  anything. If the lock is held, recovery **fails closed**, saying *"a key
  rotation is running in another process"* and naming the file. It
  changes nothing, and the caller exits non-zero before readiness.
- **Why a separate file, and not the workspace:** locking the workspace
  itself leaves a window between `create_dir` and `flock`. Recovery
  starting in that window would see an empty, unlocked workspace, take it
  for row 2, and remove it under the running rotation. The lock file
  exists before the workspace does, so there is no window.

**The adapter** gains `lock_exclusive(point, path, blocking) ->
io::Result<LockGuard>`, with the guard releasing the lock on drop:
- **`Real`**: `rustix::fs::flock` (the `fs` feature is already enabled);
- **`Failpoint`**: delegates;
- **`Simulated`**: models held locks in its state, so that one simulated
  rotation holding the lock makes a simulated recovery refuse. It records
  a point, like every primitive.

The "only path to the key files" guard must see `flock` used only inside
the adapter.

## §2 — the custody choice, required before `Intent`

The rotate command takes exactly one disposition. **There is no
default**: the choice is the operator's.
- `--retain-backup-until <RFC 3339 instant> --custody-reference <text>`,
  or
- `--remove-backup-after-verified --verification-reference <text>`.

Use a required `clap` argument group, so a missing or mixed choice is a
**usage error (exit 2)**, with text that names both forms. `review_at` is
parsed here, into P1's typed `RotationDisposition`, and must be in the
future. **`--check` does not require it**, because it creates nothing. It
says whether a rotation could start. It also names the flag a real run
will need, so `--check` is still a complete preview.

## §3 — the sequence, as RFC 100 words it

In order, each step through the adapter:

1. **Lock** (§1).
2. **Preconditions**: stage 2's `check`. Every failure is named, and
   nothing is created. Keep P3's refusal of a leftover `.new`: a crash of
   a pre-`0.94.0` rotation can still leave one.
3. **The workspace**: `journal::lock_workspace`.
4. **`Intent`**: `journal::write_intent`. The body binds every
   `RotationPaths` path, both fingerprints, the expected owner and mode,
   and the disposition. Take stage 3's body type to P1's typed
   disposition, so `review_at` is not a `String`. Update stage 3's tests
   for it.
5. **The new key**: write `next_temp` (`create_new`, `0600`, checked
   write, `sync_file`), read it back, decode it, and check its
   fingerprint. Then `advance(NextTempVerified)`. Then
   `publish_no_replace(next_temp → next)`, and sync **both** directories,
   the workspace and the key's directory. A cross-directory rename is
   durable on POSIX only when both are synced; this is stage 3's carried
   item. Then `advance(NextPublished)`.
6. **The backup**: the same, from the active key's bytes, into
   `backup_temp`, then `backup`. Its fingerprint must be the **old** key's.
   Then `BackupTempVerified` and `BackupPublished`.
7. **`Prepared`**.
8. **K08** (P1): the reseal and the pending row, durable.
9. **Activation**: `rename(next → active)`, never remove-then-rename,
   then sync the key's directory. This is row 8's own primitive;
   **share one function** with recovery's row 8, so the two cannot drift.
10. **K05** (P1), with the database opened under the new key: the row
    `complete`, `admin.master_key.rotated` Class A, durable.
11. **The clean**: stage 4's step 7 order for the workspace and its
    temporaries. **The backup stays**, under its disposition, until P3.
12. **Release the lock**, then print success. **Success prints only after
    K05 is durable.**

**Remove what the old sequence did:**
- the `.new` staging;
- the two renames;
- the timestamped `.bak` path;
- `rotate_key_files`'s old body;
- **the best-effort `admin.master_key.rotated` append**
  (`cli/handlers.rs:524`), since K05 is now its only writer. Update the
  coverage matrix's row, which P1 changed to "two writers", back to one.
- **K07** (`reseal_master_key`) loses its last production caller. If
  nothing else calls it, retire it with its descriptor. Say what you
  found, measured.

## §4 — tests, in all three modes

**Every injection point** in `crash-matrix.md`'s preparation list,
points 1–7, plus points 8–10:
- **power loss:** materialize every state the simulator enumerates and
  run the real `recover`;
- **termination:** use the kill state, and **the real binary** with
  `SUI_ID_FAILPOINT` for the points a child process can reach, as stage
  0's e2e does;
- **short write:** at each write.

The outcome the table requires:
- **every prefix before K08** returns to `OldReady`, with the database
  opening under the old key and nothing left but the backup's absence;
- **every prefix from K08 onward** reaches `Complete`: the database
  opens under the new key, the row is complete, and `rotated` is
  recorded once.

**No prefix fails closed** on a state the rotation itself left.

**The lock:**
- recovery while a (simulated or real) rotation holds the lock fails
  closed and changes nothing;
- a second rotation while one holds it is refused;
- after the holder dies (a real child process killed), recovery proceeds.

**The custody choice:** missing, mixed, or a `review_at` in the past,
each a usage error with exit 2. `--check` works without it.

**End to end:** a full rotation on the real binary. The service starts
on the new key, and the audit log holds `resealed`, then `rotated`, once
each.

**Mutations, each run and reverted, each caught:**
- recovery ignores the lock;
- the cross-directory publication syncs only one directory;
- activation by remove-then-rename;
- success printed before K05;
- the disposition made optional.
