## A — make the staged key, and the renames, durable

**The defect.** `write_key_file` (`crates/sui-id/src/runtime/keyring.rs:73`)
creates the file `create_new`, mode `0600`, and returns after `write_all`
(`:90`). It never calls `sync_all`, and nothing fsyncs its directory.
Rotation (`crates/sui-id/src/cli.rs`) stages the new key with it at `:621`.
Then K07 commits at `:626`. So a power loss after the commit can leave the
database sealed under a key that never reached the disk.

> **Corrected 2026-11-14.** This said *"SQLite fsyncs that commit"*. It does
> not: WAL with `synchronous=NORMAL` (`sui-id-store/src/db.rs:43-44`) makes a
> commit durable only at the next checkpoint. So the reverse can happen too,
> and part **A2** is added for it —
> [`0.91.0-stage-1-addendum-the-reseal-is-not-durable-on-return-2026-11-14.md`](0.91.0-stage-1-addendum-the-reseal-is-not-durable-on-return-2026-11-14.md).

The doc comment at `cli.rs:484` and the comment at `:616` both call the
staged file *"the only durable copy"*. It isn't yet.

**The fix.**
1. In `write_key_file`, after the last `write_all`: `f.sync_all()`, and
   propagate its error. Then fsync the parent directory: open it read-only
   as a `File` and `sync_all` it. Propagate that error too, because a
   failed directory sync means the file's name may not survive.
2. In `run_admin_rotate_key`, after each of the two renames (`cli.rs:648`,
   `:655`), fsync the key file's directory. Use the same helper as step 1,
   since both renames stay in that directory. A failure here must not
   claim success. Report it, keep the files where they are, and exit
   non-zero. The rotation's database half has committed, so the message
   must say where the new key is now, as the existing rename-failure
   messages do.
3. **Make the comments true.** `:484` and `:616` should say what the code
   now does: the key is written and synced to disk, with its directory,
   before the reseal.
   - `grep -rn 'durable' crates/sui-id/src/cli.rs crates/sui-id/src/runtime/keyring.rs docs/src`,
     and correct any claim that is still false.
   - Grep the descriptions, not only the code.

`resolve`'s generate branch (`keyring.rs:59-60`) also calls
`write_key_file`, so a first-start key gets the same durability. That is
intended.

**Do not change the rename order.** Today the active path is renamed away
before the new key is renamed in, which RFC 100 records as an open crash
prefix. Closing it needs RFC 100's design, not this stage.

**Tests.** Durability can't be observed from a test, so test the parts that
can be:
- the directory-sync helper succeeds on a real directory, and returns an
  error for a path that doesn't exist;
- `write_key_file` still creates the file `0600`, `create_new` (a second
  call on the same path fails), with the same contents;
- the existing rotation tests (`crates/sui-id/tests/e2e/key_rotation.rs`)
  pass unchanged.

**In the return, quote the new `sync_all` calls by `file:line`.** That is
how the review will check them.

## B — refuse to rotate a key that came from the environment

**The defect.** `resolve` takes `SUI_ID_MASTER_KEY` before the key file
(`keyring.rs:31-32`). Rotation reads the old key through it (`cli.rs:592`)
and never checks `resolved_old.origin`. With the variable set, rotation
reseals under a new key and writes that key to the file. But the next start
reads the variable first, so it runs with the old key against a database
that no longer opens with it.

**The fix.** In `run_admin_rotate_key`, immediately after `resolve`, and
**before `database::open`**:
- if `resolved_old.origin == KeyOrigin::Env`, refuse;
- exit non-zero;
- write nothing: no `.new`, no audit row, no database change.

The message must say, in plain words:
1. that the key came from `SUI_ID_MASTER_KEY`;
2. that rotation writes the key *file*, which the server would ignore while
   the variable is set;
3. what to do: unset the variable and point `key_file` at a file holding
   the current key, or rotate the key in the deployment system that sets
   the variable.

Put it in the CLI's i18n catalogue if the rotation command's other messages
are there; otherwise beside them, in the same style.

**Order matters.** The check runs after `resolve`, because only `resolve`
knows the origin. It runs before the database is opened, so a refusal
touches nothing.

**Tests**, in `key_rotation.rs`, through the binary as the existing tests
run it (`:70`), with `SUI_ID_MASTER_KEY` set **on the child process only**,
never with `std::env::set_var` in the test process:
- the command exits non-zero, and its stderr names `SUI_ID_MASTER_KEY`;
- no `.new` exists afterwards, and the key file's bytes are unchanged;
- the database has no `admin.master_key.resealed` row, and its sealed rows
  still open with the original key;
- **the mutation:** delete the origin check and record that this test goes
  red.

**Out of scope, and why.** With no variable and no key file, `resolve`
*generates* a key (`KeyOrigin::GeneratedNew`), and rotation would then run
against it. That is RFC 100's change 3, *"generate only for a database that
has never been sealed"*. It needs the sentinel, so leave it alone here, and
say in the return that you saw it.

## C — the record

`CHANGELOG.md` `## [Unreleased]`, `### Fixed`, two entries, operator-facing:
- **Rotating the master key now syncs the new key to disk, and its
  directory, before re-sealing.** Before, a power loss just after the
  re-seal could leave the database sealed under a key that was never
  written to disk. Name the range this affects: from `0.87.1`, which moved
  the staging before the re-seal without syncing it. Establish that from
  the code's history rather than assuming it.
- **`admin rotate-key` refuses when the key comes from
  `SUI_ID_MASTER_KEY`.** Before, it rotated the key file, which the server
  then ignored, so the next start used a key that no longer opened the
  database.

Update `docs/src/guides/operators.md`'s rotation section if it describes
either behaviour. Don't touch `## [0.90.0]`, the versions, the RFCs or the
ROADMAP.
