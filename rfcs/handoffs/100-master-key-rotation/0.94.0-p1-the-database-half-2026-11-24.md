## §1 — the `master_key_rotation` row: migration 0053 gives it its full shape

**Measured: the table already exists.** Migration 0052 (stage 1,
`0052_master_key_sentinel.sql`) created `master_key_rotation` beside the
sentinel. It is a singleton (`id INTEGER PRIMARY KEY CHECK (id = 1)`),
with `rotation_id`, the two fingerprints, and `state` checked to
`db_committed_pending_activation` or `complete`. It has shipped since
`0.93.0`, and **nothing has ever written to it**. Its shape is weaker
than RFC 100's *State machine*:
- only `started_at`/`updated_at`, where the RFC names *prepared*,
  *committed* and *completed* timestamps;
- `custody_disposition TEXT NOT NULL`, free text with no structure and no
  check.

**Migration 0053 rebuilds that empty table to the full shape.**
- **First it proves the table is empty.** If it holds any row, the
  migration refuses with a clear message and changes nothing, since no
  release ever wrote one. Use SQLite's table-rebuild sequence (new table,
  drop, rename) inside the migration's transaction.
- **The columns:**
  - `rotation_id`, and the two fingerprints;
  - `state`, with its `CHECK`;
  - `prepared_at` and `committed_at` (`NOT NULL`), and `completed_at`
    (null until K05; a `CHECK` ties it to `state = 'complete'`);
  - `backup_filename`, which is `RotationPaths::backup`'s file name;
  - **the disposition, structured**: `disposition_kind`, checked to
    `retain_until` or `remove_after_verified`. Then `review_at` and
    `custody_reference`, or `verification_reference`, with a `CHECK` that
    exactly the fields of its kind are present. That matches the
    journal's `BackupDisposition`.
- **Keep the singleton.** A second rotation replaces a `complete` row,
  and is refused while one is pending.

**`review_at` is typed** (stage 3's carried item): an RFC 3339 instant,
parsed and validated where the disposition is constructed, and stored as
the store's timestamp type. It is not free text.

**Migration evidence:**
- the upgrade test from `0.93.1`'s schema, with the empty table;
- a test that a non-empty table (constructed directly) makes 0053 refuse
  and leaves it byte-identical.

Measure the existing migration tests' shape first, and follow it.

## §2 — K07 extended: the reseal writes the row, pending

A **new** Class-A command beside `reseal_master_key` (leave that one
alone): for example,
`reseal_master_key_for_rotation(db, new_key, record: RotationRecord)`.
In **one** transaction it:
- reseals every sealed column **and the sentinel** under the new key, as
  today's K07 does;
- writes the row as `db_committed_pending_activation`, with the record's
  fingerprints, ID, disposition and backup name;
- appends `admin.master_key.resealed`, whose note states the rotation ID
  and that activation is pending (M4: it claims only the database phase).

It then checkpoints, so it is **durable before it returns**, exactly as
today's K07 is (`0.91.0` A2: `RotationNotDurable`, `commands.rs:6844`).

**It refuses before writing anything:**
- if a row is already pending;
- if the record's old fingerprint is not the database's current key.

## §3 — K05: completion, Class A and durable

A Class-A command `complete_master_key_rotation(db, rotation_id)`,
opened **with the new key**. In one transaction it:
- marks the row `complete`, with `completed_at`;
- appends `admin.master_key.rotated`, the event today written
  best-effort outside any transaction (`sui-id/src/cli/handlers.rs:524`).
  That append is **not** removed here; P2 replaces it.

It is durable before it returns, as K07 is.

- **Idempotent** (crash-matrix row 9, and *"K05 run twice"*). On a row
  already `complete` with the same `rotation_id`, it returns success and
  appends **nothing**: no duplicate event.
- **No row, or another `rotation_id`**, is a refusal, not a success.
- **M5:** K05 cannot complete a row whose disposition is missing. The
  `CHECK` makes that unrepresentable. Show it with a test that tries to
  insert such a row directly.

## §4 — recovery rows 8–10

Stage 4's `recover` (`rotate/recovery.rs`) fails closed today when the
active key does not open the sentinel, and when the journal
authenticates the active key as role **New**. These three rows replace
those two refusals **only in the states the RFC names**. Every other
mismatch still fails closed, as row 11 requires.

| Row | Observed | Recovery |
|---|---|---|
| **8** | The workspace and journal exist; the active key opens neither the sentinel nor the journal as New. The bound `next` key **opens the sentinel**, authenticates the journal as role **New**, and has the journal's `new_fingerprint`. The row is pending, with this `rotation_id` and these fingerprints | **Activate**: atomically replace the active key path with `next` (`rename`, never remove-then-rename), then sync the directory. Then K05. Then clean the workspace as stage 4's step 7 does |
| **9** | The active key opens the sentinel and authenticates the journal as role **New**; the row is pending with this `rotation_id` | Activation already happened: K05, then the clean |
| **10** | As 9, but the row is `complete` | Only the clean: remove the matching stale workspace |

**K05 needs an open database.** `recover` runs before the database is
opened, so make it return what is still owed, for example
`Recovered::Activated { rotation_id }` or `NeedsCompletion { rotation_id }`.
`database::open_checked` then runs K05 right after opening with the now
active key, **before it returns the database to its caller**. The
service must not become ready on a pending row.

Fail closed when any of these is true:
- the row is missing;
- the row's `rotation_id` or fingerprints disagree with the journal's;
- `next` is missing in row 8;
- anything in row 8 fails to verify.

Nothing is changed in those cases.

**Report.** Reported as stage 4's report is: the server log at warn,
then stderr. It says what was found, *"a rotation was completed at
start"*, and names the files it changed, with fingerprints only.

## §5 — tests

The simulator modes apply where a file is touched.

- **The row:**
  - the `CHECK`s refuse a disposition of the wrong shape, and a second
    pending row;
  - migration 0053 upgrades a `0.93.1`-shaped database.
- **K07 extended:**
  - one transaction: a failpoint between the reseal and the row
    insert, and between the insert and the commit, leaves the database
    exactly as before, with no row and no event (RFC 094's rollback
    evidence, in the established shape);
  - durable on return;
  - refused while a row is pending, and on a fingerprint mismatch.
- **K05:**
  - rollback evidence as above;
  - durable on return;
  - **run twice, one event**;
  - refused for an unknown `rotation_id`.
- **Rows 8, 9 and 10**, each with its state built directly. Each
  recovers to `Complete`: the database opens with the new key, the row
  is `complete`, the workspace is gone, and `admin.master_key.rotated`
  appears **once**.
- **Each refusal:** row 8 without `next`; a `next` of the wrong key; a
  row/journal `rotation_id` mismatch; a missing row. Each leaves every
  file and the database byte-identical.
- **Activation's crash safety (row 8)**, in the power-loss mode: every
  state the simulator enumerates around the replacement and its sync.
  The real `recover`, re-run, reaches `Complete` and never fails closed
  on a state its own activation left.
- **The service is not ready on a pending row**: an e2e test through
  `open_checked` with a row 9 state. The database is returned only after
  K05.

**Mutations, each run and reverted, each caught:**
- K05 appends its event even when already complete;
- activation by remove-then-rename;
- `open_checked` returns before K05;
- row 8 accepts a `next` whose fingerprint isn't the journal's.
