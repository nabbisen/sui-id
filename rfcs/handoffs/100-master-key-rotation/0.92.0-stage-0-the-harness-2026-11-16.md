## A — the adapter, and the only path to the key files

A module in `crates/sui-id` (beside `runtime/keyring.rs`) with one trait for
key-file operations, holding exactly what the design names:
- `create_new` (mode `0600`, refusing an existing path);
- `write_all`, `sync_file`;
- `rename` (atomic replacement);
- `publish_no_replace` (`hard_link`, then remove the temporary);
- `sync_dir`, `read`, `remove`;
- `metadata` (owner, mode, whether a path is a symlink).

Add two calls that mark the database's durability, which rotation makes and
the Real implementation ignores:
- `db_committed(label)`, called after K07's transaction commits;
- `db_durable(label)`, called after K07 has made it durable (its checkpoint).

Today both are one return of `reseal_master_key`, so the CLI calls them one
after the other. Keep them separate anyway: they are separate events, and the
Simulated implementation treats them as such.

**Move today's rotation onto it, behaviour unchanged.** Every key-file
operation in `runtime/keyring.rs` and in `run_admin_rotate_key`
(`crates/sui-id/src/cli.rs:512`, including the two renames at `:703` and
`:731`) goes through the trait. `resolve` and `write_key_file` keep their
public signatures, using the Real implementation by default. Every existing
rotation test passes unchanged.

## B — three implementations

| Implementation | Built | It |
|---|---|---|
| **Real** | always | `std` only: no new dependency, no `unsafe`. `publish_no_replace` is `std::fs::hard_link` (which refuses an existing name) then `remove_file`. `sync_dir` opens the directory and calls `sync_all` |
| **Failpoint** | `test-support` only (the feature exists: `crates/sui-id/Cargo.toml`) | wraps Real. Reads `SUI_ID_FAILPOINT=<point>:<action>`, **only** under that feature. Actions are `abort` (`std::process::abort()`), `error` (the operation returns an error), and `short-write` (writes half, then errors). Points are named per call site, for example `rotate.stage.write`, `rotate.stage.sync_file`, `rotate.rename.1`, `rotate.sync_dir.after_rename.1`. List them in one place in the source |
| **Simulated** | `#[cfg(test)]` and `test-support` | records every operation, per inode and per directory entry, and what each sync made durable: the prototype's model, on the real trait. Treats `db_committed` as pending and `db_durable` as making it durable. **Enumerates** every disk a power loss could leave at each point, with a write that persisted possibly persisting only as a prefix (the design's crash model; the prototype lacked that one). **Materializes** a state into a real temporary directory |

## C — the oracle for stage 0, and why it is not yet "start the binary"

The design's oracle is the real binary starting against each materialized
state. **Until stage 1 adds the sentinel, startup does not check the key at
all**, so a start proves nothing. Stage 0's oracle is therefore direct:
- for each materialized state, take the database snapshot it implies: the one
  before K07 if K07's commit did not persist, the one after if it did. Take
  both snapshots with `VACUUM INTO`, around a real K07;
- **does the key at the configured path open that database?** Unseal one
  signing key with it;
- **does any file in the directory hold a key that opens it?** (M2)

Stage 1 replaces the first check with *"the binary starts, or refuses before
readiness"*, once a start can tell.

## D — tests: the prototype's properties, against the real code

The real code's operations are finer than the prototype's model (for
example, `write_key_file` writes the key and then a newline). **So do not
expect the prototype's counts. Assert its properties**:

1. **Today's order (stage 1 with A2), power-loss mode:**
   - M2 holds in every state at every point;
   - after the command reports success, the active path opens the database
     in every state.
2. **Remove each sync, one at a time** (in a test-only copy of the sequence,
   never in production code). The power-loss mode must find at least one
   violation for each, **except the directory sync after the first rename**,
   which the prototype found not load-bearing. Record what you actually
   find for that one. If it also finds a violation, that is new evidence:
   say so.
3. **Remove the `db_durable` step** (i.e. K07's checkpoint), and the
   power-loss mode must find the state where the reseal rolled back under
   the new key file.
4. **The `0.90.0` order** (no syncs, no checkpoint, as a test-only sequence):
   - the power-loss mode finds violations;
   - **the kill-only mode finds none.**

   Name that test so it says what it shows: the blindness the harness exists
   to close.
5. **Failpoint, through the real binary**:
   - for every listed point, `abort` leaves a directory in which M2 holds,
     since a kill loses nothing written;
   - `short-write` at the staging write leaves the old key active and the
     database untouched.
6. **The only path:** a test fails if `std::fs` touches a key path outside
   the Real implementation. Scan `runtime/keyring.rs` and the body of
   `run_admin_rotate_key` for `rename`, `write`, `OpenOptions`,
   `File::create`, `remove_file` and `hard_link` outside the adapter.
   **Mutation:** add one such call, and the test fails.
7. Every new test is mutated once to show it can fail, and the mutation
   recorded.
