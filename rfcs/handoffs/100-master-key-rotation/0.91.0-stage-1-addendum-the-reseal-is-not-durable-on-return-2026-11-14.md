## Why: stage 1's premise was wrong, and the error was the architect's

Stage 1 said K07 *"commits at `:626`, and SQLite fsyncs that commit"*.
**It does not.** `crates/sui-id-store/src/db.rs:43-44` opens every connection
with `journal_mode=WAL` and `synchronous=NORMAL`. SQLite's documentation for
that pair (`https://www.sqlite.org/pragma.html#pragma_synchronous`): a
commit *"might roll back following a power loss or system crash"*. It is
durable across a killed process, and becomes durable across a power loss only
at the next checkpoint.

`cli.rs` reseals at `:626`, then renames the key files at `:648` and `:655`,
with the database still open. So once stage 1's fsyncs make the new key
durable, this sequence is possible:
1. K07 commits into the WAL;
2. the new key is renamed into place, and fsynced;
3. power is lost before any checkpoint;
4. the database comes back sealed under the **old** key, with the **new** key
   at the active path.

The old key is still at `.bak.<stamp>`, so it can be recovered by hand. But it
is a wrong-key start, and nothing detects one today (RFC 100's refresh,
*Detecting the wrong key*).

**Measured, not argued.** The harness prototype (cycle M, D1) models every
state a power loss can leave. On stage 1's order, the state above is the one
state it finds wrong after the command reports success. With A2's checkpoint
after K07, it finds none. A model that only kills the process, as RFC 100's
test plan does, finds none in either case.

## A2 — make K07 durable before it returns

**Where.** In `sui_id_store::commands::reseal_master_key`
(`crates/sui-id-store/src/commands.rs:6755`), **after** the Class-A
transaction has committed, and **before** the function returns. Its one
production caller is `cli.rs:626`. Placing it in the command, not in the CLI,
makes the contract *"committed and durable when this returns"*. Nothing that
relies on K07 can then run ahead of the durability.

**What.** On the same database, run `PRAGMA wal_checkpoint(TRUNCATE)` and read
its one result row, `(busy, log, checkpointed)`:
- `busy != 0`: return an error. The reseal **has committed**, and the error
  must say so, and say that the key files have **not** been touched. With the
  checkpoint inside the command, `cli.rs` will not have reached the renames.
- otherwise, return `Ok`. A completed checkpoint syncs the WAL before it, and
  the database file after it, so the reseal is now durable.

Use a store-internal connection (`with_conn`, or what the seam provides after
commit). Do not add a public API for this. **If the Class-A seam makes running
a statement after commit impossible, or the structural gate refuses it, stop
and return to the architect.** Don't work around the gate.

**`TRUNCATE`, not `FULL`,** so that a test can observe it: on success, the
`-wal` file is zero bytes.

**In-memory databases** (tests) are not in WAL mode. There the pragma returns
`(0, -1, -1)`. Treat that as success.

**The comment at `cli.rs:623-624`** says the reseal *"commit[s] in one
transaction"*. Add that it is durable on return, and why: WAL with
`synchronous=NORMAL`.

## Tests

In `crates/sui-id-store/src/commands/tests/runner/master_key.rs`, where K07
is already tested, on a **file** database. Read how the existing tests build
theirs, and use a file database for this one:

- **after `reseal_master_key` returns `Ok`, the `-wal` file beside the
  database is zero bytes long** (or absent);
- **the mutation:** delete the checkpoint, run the test, record that it fails,
  and quote the failure. Without the checkpoint, the WAL holds the reseal's
  frames (well under SQLite's 1000-page auto-checkpoint);
- **the `busy` branch:** hold a read transaction open on a second connection
  across the call, if that makes `TRUNCATE` report `busy = 1` (measure it),
  and assert the error text says the reseal committed and no key file was
  touched. If you can't make `busy` happen, say so, and say what you tried.
  Don't fake it.
