## §1 — what P2 left, measured

- **The backup is kept** at `<key>.pre-rotation` under its disposition.
  The `master_key_rotation` row records the disposition (P1).
- **A kept backup blocks the next rotation.** P2's review added the
  refusal (the P3 precondition): *"the last rotation's pre-rotation backup
  is still at …"*. Until this stage, the operator's only way past it is
  to move the file by hand. **This stage gives that a supported, audited
  path**, and must end in a state where the next rotation starts.
- **Nothing raises a finding** when a kept backup's `review_at` passes.

## §2 — custody, by disposition

Two commands, both Class A, both audited, and both run from the CLI
only. The CLI is where rotation runs, offline.

- **`sui-id admin master-key backup remove`**, for either disposition.
  RFC 100: removal *"unlinks the file only after the referenced
  pre-rotation backup is retired or re-encrypted"*. The command
  therefore requires the operator to state that, explicitly, with
  `--confirm-retired-or-reencrypted`, and records:
  - the row's `verification_reference` (for `RemoveAfterVerified`), or a
    `--verification-reference` given now (for `RetainUntil`);
  - **the time and the operator**, measured against the precedent and
    then extended. The CLI form of `issue-recovery-link` records **no
    actor**, only `via=cli` (`docs/src/reference/audit-events.md`,
    `user.recovery_link.issued`). RFC 100 asks more: *"a removed backup
    records timestamp and operator identity"*. On the command line, the
    only identity sui-id truthfully has is **the OS account that ran
    the command**. Record `via=cli`, the account's uid
    (`rustix::process::getuid`; the `process` feature is already
    enabled), and the name `/etc/passwd` gives for that uid, if any.
    Read the file, with no new dependency: `rustix` has no uid-to-name
    lookup. Label it as
    what it is: the attribute says `os_user`, never just `operator`, and
    the documentation says sui-id did not authenticate it.

  Before unlinking, it verifies that the file is the row's backup:
  - the name and the old fingerprint match;
  - it is a regular file, not a symlink, with the expected owner and
    mode.

  Then the unlink and a directory sync. The row records the removal.
  **"No secure-erasure claim"** (RFC 100): say so in the command's
  output, once.
- **`sui-id admin master-key backup renew --until <RFC 3339> --custody-reference <text>`**,
  for `RetainUntil` only. It moves `review_at` forward (future only) and
  records the new reference, audited.

**What "settled" means for the next rotation:** P2's refusal of a kept
backup stays exactly as it is. A file at `<key>.pre-rotation` still
blocks. So the two ways forward are:
- `backup remove`;
- **moving the file to its custody location**, outside the key's
  directory. The command line cannot see the destination, so this needs
  no command: the next rotation's precondition passes once the file is
  gone. A later `backup remove`, run against an absent file, records
  nothing and says so.

## §3 — the finding

**A `RetainUntil` backup past its `review_at` raises a finding,
repeatedly, until it is renewed or removed.** It is a finding only,
never an automatic removal (RFC 100's proposed answer 2, accepted). It
appears in:
- **at every start**: one `WARN` naming the file, its `review_at`, its
  custody reference, and the two commands that settle it. This follows
  the federation provider's "requires review" warning
  (`runtime/startup.rs:426`);
- **`admin master-key rotate --check`**, which reports it beside its own
  precondition lines.

**Not a console card yet.** RFC 149's dashboard (cycle Q) is where a
console finding belongs. Add *"the kept-backup finding"* to RFC 149's
carried list (`rfcs/handoffs/149-…/README.md`), so it is not forgotten.

**A kept backup is never a startup key candidate** (RFC 100). Measure
that `keyring` reads only the configured key file, and pin it with a
test that a database sealed under the backup's key, with the backup
present and the active key wrong, still refuses.

## §4 — what the operator reads

All of this ships with P2 in `0.94.0`, so it must be true at the tag:
- **`docs/src/guides/operators.md`, the rotation section, rewritten.**
  - The old five steps (`.new`, `.bak.<timestamp>`, two renames) are
    gone.
  - Its example runs `rotate` with no custody flag, now a usage error.
  - Describe the protocol, the custody choice, `--check`, the lock, and
    what an interrupted rotation does at the next start, for each kind of
    crash.
  - Custody: the two dispositions, the finding, `backup remove` and
    `backup renew`.
- **The "not yet crash-safe" warning goes in this change**, the one that
  closes M2c's build (`implementation.md`, stage 7). That is the
  `operators.md` caveat that begins *"A failure or power loss between
  steps 4 and 5 can still leave nothing at the configured path"*.
  Replace it with **the recovery procedure**:
  - what recovery does unaided;
  - what it refuses, and why;
  - what to do when it refuses;
  - which files to keep, and never to remove by hand.
- **`docs/src/reference/audit-events.md`**: the `admin.master_key.rotated`
  row still says *"best-effort … archived"*. It is now K05's Class-A
  record. The `resealed` row gains `rotation_id`, and the new custody
  events get rows.
- **The CLI reference** regenerates from `cli/help.rs`, as P2 did.

## §5 — tests

- **Rotate, settle, rotate again**, end to end on the real binary, for
  both dispositions:
  - `RemoveAfterVerified`, then `backup remove`, then a second rotation:
    exit 0;
  - `RetainUntil`, then the file moved away, then a second rotation:
    exit 0.

  The audit log has every event once.
- **`backup remove`** refuses each of these, changing nothing:
  - no `--confirm-retired-or-reencrypted`;
  - a file whose fingerprint is not the row's old one;
  - a symlink;
  - no row.

  It records the time and the operator. Run on an absent file, it reports
  that and records nothing.
- **`backup renew`**: a past instant, or a `RemoveAfterVerified` row, is
  refused; a valid instant moves `review_at`.
- **The finding**: past `review_at`, every start logs it, and
  `--check` reports it; renewed or removed, it stops. Use the
  simulated clock where the store's types allow it. Measure first:
  Class-A timestamps use `Utc::now()` directly.
- **Never a candidate**: §3's test.

**Mutations, each caught:**
- `backup remove` without the confirmation flag;
- the finding raised before `review_at`;
- the backup tried as a startup key.
