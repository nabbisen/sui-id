## §1 — half one: a rotation must not run beside a running sui-id

**Proved on the shipped build:**
1. start `sui-id serve`;
2. run `admin master-key rotate --yes …`: **"Rotation complete"**, and the
   server is still running.

The server holds the old key in memory. Everything it seals from then on
(a refresh token, a TOTP enrolment, a passkey) is sealed under the old
key, in a database now resealed under the new one. After the next
restart, those rows cannot be read. **That is M1** (*"never … columns
sealed under different keys"*), broken by one forgotten
`systemctl stop`, with no error anywhere. The only guard is a sentence,
*"Make sure the server is stopped"* (`cli/handlers.rs:527`).

**The fix uses the lock P2 built** (`<key>.rotation-lock`), in two modes:
- **Every sui-id process that opens the database holds the lock
  *shared*, for as long as it has the database open.** That is the
  server, for its whole life, and every CLI command that goes through
  `database::open_checked`. Return the guard with the `Database` (for
  example, a struct holding both), so it cannot be dropped early by
  accident.
- **A rotation takes it *exclusive*, non-blocking, before anything
  else** (P2 already does this). On contention it refuses, with a cause
  that is now true: *"refusing to rotate: sui-id is running — the server,
  or another sui-id command — and has this database open (`<lock
  path>`). Stop it, then rotate."* The banner's *"Make sure the server is
  stopped"* stays as advice, but it is no longer the only protection.
- **Recovery takes it shared, non-blocking.** It still refuses while a
  rotation holds it exclusive (*"a key rotation is running in another
  process"*), and it coexists with a running server.
- **Inside the rotation**, its own recovery pass runs while the rotation
  already holds the exclusive lock. `flock` locks belong to the open
  file, so a second `open` in the same process conflicts with the first.
  Pass the held lock to `recover` (for example, as a parameter meaning
  "the caller holds it exclusive") rather than letting `recover` lock
  again.
- **The adapter** gains a shared mode beside `lock_exclusive`: `Real`
  through `rustix::fs::flock` (`LockShared`), `Failpoint` delegating, and
  `Simulated` modelling shared holders and an exclusive holder.
- **Stated limit, in the guide:** a sui-id older than `0.94.0` takes no
  lock, so a rotation cannot detect one. Upgrade every process together.

**Tests:**
- **a rotation refuses while a real `sui-id serve` child runs**, and
  changes nothing: the key file, the database and the directory are
  byte-identical, apart from the lock file;
- a rotation refuses while an `open_checked` caller holds the database
  (Simulated, or two real opens);
- once the server stops, the rotation proceeds;
- recovery still refuses while a rotation holds the lock exclusive;
- two CLI commands, and a command beside a running server, coexist.

**Mutation:** the server does not take the shared lock, and the
rotation-beside-a-server test fails.

## §2 — half two: what the operator reads

Every finding below was seen on the real binary.

1. **Project jargon in operator text.** Several strings and help texts
   cite *"RFC 100"*, and an operator does not know what that is. Write
   what is meant instead:
   - the help for `--retain-backup-until`, `--custody-reference`,
     `--remove-backup-after-verified`, `--verification-reference` and
     `backup remove`. These are `///` comments in `cli.rs`; clap turns
     them into `--help`;
   - *"no old-key custody choice was given (RFC 100's Old-key custody
     requires one)"* (`cli/handlers.rs:422`);
   - *"RFC 100: this runs the full journalled rotation protocol."*
     (`:523`).

   **A guard, so it stays fixed:** a test that renders every command's
   help, as the CLI reference renderer already does, and fails on
   `RFC `. Code comments keep their RFC references.
2. **`--remove-backup-after-verified` removes nothing.** The backup stays
   until `backup remove` is run. An operator reading the flag believes
   the old key is gone. **Rename it**, as the owner chose, for example to
   `--discard-backup-once-verified`. Nothing has shipped under the old
   name (`0.94.0` is unreleased), so **keep no alias**. The help says,
   plainly: *the old key is kept until you have checked nothing needs it,
   then removed by `sui-id admin master-key backup remove`.* Update every
   use (about 34 across `crates/`, `docs/` and `CHANGELOG.md`) and
   regenerate the CLI reference. The stored disposition kind is internal
   and may keep its name.
3. **The success message says *"kept under the bound disposition"***,
   which means nothing to an operator. It also **does not say that the
   next rotation will refuse** until the backup is settled, or which
   command settles it. Say, by disposition:
   - **once verified:** *"The old key is kept at `<path>`. When you have
     checked that nothing needs it, run `sui-id admin master-key backup
     remove …`. Until then, the next rotation refuses."*
   - **until a date:** *"The old key is kept at `<path>` until `<date>`
     (`<reference>`). After that date, sui-id warns at every start until
     you renew or remove it. Until it is gone, the next rotation
     refuses."*
4. **The kept-backup refusal does not name the way out.** It ends with
   *"remove it once you have verified that nothing needs it"*. Name both
   commands: `backup remove`, and `backup renew` for a dated one.
5. **`--confirm-retired-or-reencrypted` blurs two different backups.**
   Its text says *"the backup is retired or re-encrypted"*. RFC 100 means
   the **copies of the database taken before that rotation**, which only
   the old key can read. Those must be retired, or re-encrypted under the
   new key, before the old *key* is removed.
   - **Measured:** a `sui-id backup create` tarball carries its own key
     (*"a SQLite snapshot of the database, a copy of the master key"*,
     `docs/src/guides/operators.md`, *Backup and restore*). So the copies
     that matter are the ones without a key: a filesystem snapshot, or a
     copied `.sqlite` file.
   - Say exactly that, in the flag's help, its refusal, and the guide.
     The flag's name may stay; its words must not blur.
6. **`<key>.rotation-lock` is undocumented.** It is a permanent, empty
   file beside the key. Say in the guide what it is, that it stays, and
   **never to remove it**, since removing it while sui-id runs would break
   the guarantee in §1.

**Tests:**
- the renamed flag works, and the old name is an error (exit 2);
- the success message, per disposition, names the next step and that
  the next rotation refuses;
- the refusal names both commands;
- the `RFC ` guard over every help page.

**Mutation:** put one `RFC 100` back into a help text, and the guard fails.
