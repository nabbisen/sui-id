## What exists, measured on `92b3d01`

- **The top-level parser is hand-written**: `crates/sui-id/src/main.rs`, a
  match on the first non-flag argument (`backup`, `restore`, `verify-backup`,
  `preview-upgrade`, `admin`, `setup`), falling through to `serve`, with
  `--version`/`-V`, `--help`/`-h`, `--print-sample-config` and `--dev`
  checked by scanning `args`, and a list of value-taking flags so a value is
  not taken for a command. That list is RFC 107's bug class.
- **`admin`'s nine actions** dispatch by hand in `cli.rs:268` and onward:
  `unlock-user`, `reset-mfa`, `issue-recovery-link`, `rotate-key`,
  `rotate-metrics-token`, `issue-registration-token`,
  `revoke-registration-token`, `list-registration-tokens`,
  `legacy-dynamic-candidates`, with `ADMIN_SUBACTIONS` kept beside them.
- **`clap` is not in `Cargo.lock`.** The MSRV is 1.95 (`Cargo.toml:23`).

## §1 — `clap`, added carefully

Add `clap` 4 to the workspace with **`default-features = false`** and only
the features this needs: `std`, `derive`, `help`, `usage`, `error-context`,
`suggestions` (for *"did you mean"*, RFC 148 §5). **No `color`**: the output
is plain text. In the return:
- list **every crate `Cargo.lock` gains**, with its version;
- run `cargo audit` (the advisory lane's tool, `.github/workflows/audit.yml`)
  and quote its result;
- confirm each new crate's MSRV is at most 1.95, and that the pinned 1.95
  lane builds.

## §2 — the registry is the type

**One `clap` derive tree is the registry** (RFC 148 §3). The command enum
*is* the list, and the dispatch is an exhaustive `match` on it, so a command
without a dispatch arm does not compile. `ADMIN_SUBACTIONS`, the hand list
of value-taking flags, and the scanning of `args` are **deleted**.

The tree is exactly RFC 148 §1's: *Getting started* (`setup`, `serve`;
`init` arrives in O2b, so **reserve no stub for it here**), *Running it*
(`backup create|restore|verify`, `upgrade preview`, `config sample
[--production]`, `config check`), *Administering* (`admin user …`,
`admin master-key rotate`, `admin metrics-token rotate`, `admin
registration-token …`), *Developing* (`dev`), *Help* (`help [COMMAND …]`,
`version`). `--config PATH` is one **global** option.

**Behaviour does not change.** Each new leaf calls today's function with
the same effect. Where a function takes `&[String]` today, adapt it to the
parsed values; **do not** re-parse.

**`config check`** validates a configuration and changes nothing: `Config::load`
and its validation, and nothing that opens the database. **`config sample
--production`** prints the production template (`sui-id.example.toml`'s
content, kept in step with it by RFC 147 §4's test).

## §3 — every old form still works, with one notice

RFC 148 §2's list, each kept as an alias **until `1.0`**:
- `sui-id` with no command (and `--config …`, or a configuration present)
  **serves**: the documented service unit runs exactly that
  (`docs/src/guides/deployment.md:240`). **This case prints no notice**: it
  is the documented form, and a service log should not gain a line on every
  start;
- `--print-sample-config`, `--dev`, `--version`, `--help`;
- `backup`, `restore`, `verify-backup`, `preview-upgrade`;
- each of the nine `admin` actions under its old name.

Every alias except bare `sui-id` prints **one line to stderr, never
stdout**, as RFC 148 §2 shows. So `sui-id --print-sample-config > sui-id.toml`
writes exactly what it writes today. **Aliases are hidden from `help`.**

## §4 — help, short first

RFC 148 §5: `sui-id help` and `--help` fit one screen, grouped as §1; `sui-id
help COMMAND` carries every option, the environment variables the command
reads, an example, and its reference link. An unknown command names the
nearest known one, then points to `sui-id help`. **Documentation is named by
URL** with the existing `sui_id_web::github_doc_url!` (pinned to this
binary's release, N1), never by a repository path.

## §5 — the reference page, generated

A new `docs/src/reference/cli.md`, **rendered from the registry** (`clap`'s
`Command` tree), and listed in the book's `SUMMARY.md`. A test renders it
afresh and fails if the committed page differs, so the documentation
cannot drift (RFC 148 §3). Provide the way to regenerate it (an `xtask`
subcommand, say) and name it in the test's failure message.

## §6 — tests, through the binary, each mutated

- **Every old form works, and prints its notice to stderr only**: one e2e
  per alias family, asserting the effect and that stdout is unchanged.
  `sui-id --print-sample-config` writes byte-identical stdout to `sui-id
  config sample`. **Mutation:** route one alias to the wrong command; red.
- **Bare `sui-id --config PATH` serves, and prints no notice.**
- **A flag's value is never taken for a command** (RFC 107): `sui-id
  --config backup` reads a configuration named `backup`, and `sui-id admin
  user unlock --username serve` unlocks a user named `serve`.
- **Help and the registry cannot diverge**: every leaf in the registry
  appears in `sui-id help`, and `sui-id help LEAF` succeeds for each. Built
  by walking the registry, not a hand list.
- **The reference page** matches a fresh render. **Mutation:** edit one line
  of `cli.md`; red.
- **An unknown command** suggests the nearest, and exits non-zero.

**RFC 107 closes with this.** State in the return how each of its closure
conditions (`rfcs/accepted/107-cli-help-completeness.md:10`) is met, and by
which test.
