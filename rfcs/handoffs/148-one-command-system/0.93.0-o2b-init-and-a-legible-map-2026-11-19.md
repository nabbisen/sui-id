## §1 — `sui-id init` (RFC 148 §4)

`sui-id init [--production] [--output PATH]`, under *Getting started*:
- **It never overwrites.** Open the destination with `create_new`. An
  existing file is refused, naming its path, and exits non-zero, so `init`
  cannot destroy a configuration. The default destination is
  `./sui-id.toml`.
- **The local-trial profile by default; the production template with
  `--production`.**
- **Both profiles are commented, and generated from the same definitions
  as `config sample`.** `sui-id init` writes byte-for-byte what `sui-id
  config sample` prints, and `init --production` what `config sample
  --production` prints. One function produces each; `init` and `config
  sample` both call it.

**Measured on `ff1a9f5`:** the local-trial sample (`config sample`) has **no
comments at all**: 28 lines, none starting with `#`. Give it comments, one
short line per section and per key an operator might change, saying what the
key is for. **A test parses the commented text back and requires it to equal
`Config::sample()`**, so a comment can never hide a value that differs. The
production template is `sui-id.example.toml`, already commented and held to
`Config::sample()`'s keys by RFC 147 §4's test.

On success, print what was written and the next step (RFC 148 §4's example:
*"wrote ./sui-id.toml (local trial). Next: sui-id serve …"*).

## §2 — the first run asks, but only in a terminal (RFC 148 §4)

**When:** `sui-id` with no command (or `sui-id serve`), **no `--config`
given**, and no file at the default `./sui-id.toml`.
- **stdin and stderr are both terminals** (`std::io::IsTerminal`, so no new
  crate): ask as RFC 148 §4 shows: `[l]` local trial, `[p]` production
  template, `[n]` not now. Write through §1's `init` path. `n`, an empty
  answer, or end of input writes nothing and exits non-zero with §3's
  guidance. After writing, **do not start serving**: print the next step
  and exit 0, so the operator can read and edit the file first.
- **Not a terminal** (a service unit, a script, CI): **never prompt, never
  wait.** Print §3's guidance and exit 1.
- **An explicit `--config PATH` that is missing:** never prompt (§6 answer
  3). Print §3's guidance naming that path, and exit 1.

**Every other command** that needs a configuration keeps printing the
guidance from `Config::load`, unchanged in shape.

## §3 — the guidance names what now exists

`Config::load`'s not-found message (`crates/sui-id/src/runtime/config.rs:240-248`,
N1's) still tells the reader to run `sui-id --print-sample-config >
sui-id.toml`, and says the production template is *"in a source checkout"*.
Both are out of date: `init` writes either profile from any installed
binary. Make it RFC 148 §4's:

```text
error: no configuration found at ./sui-id.toml.
  Create one:  sui-id init                (a local trial)
               sui-id init --production   (a production template)
  Reference:   <the configuration reference, pinned to this release>
```

Keep its three parts and their order (N1's tests assert them; update those
tests to the new text, not away).

## §4 — C1: the help overview is a map that reads

Measured, `sui-id help` on `ff1a9f5`: 37 lines, but **lines run to about 170
characters**, so on an 80-column terminal most wrap. The description column
starts at a different place in each group, and even within one (*serve*,
*upgrade preview*, *config*). And usage detail (`--admin-username
<ADMIN_USERNAME>`, `[OPTIONS]`) crowds the map.

- **One line per command: its path, then a short purpose**, in **one
  column aligned across every group**.
- **No usage detail in the overview**: options belong to `sui-id help
  COMMAND`, and to each command's own `--help`.
- **Every overview line is at most 80 columns.** Give each command a short
  purpose (`about`) that fits, and keep the full description as its
  `long_about`, which its own help shows.
- **The overview still fits one screen**, as now.

**Test:** every line of the rendered overview is at most 80 columns, and
every command line's purpose starts at the same column. **Mutation:** lengthen
one `about`; red.

## §5 — C2: the documentation teaches the new forms

O2a's return listed the pages that still name old forms: `docs/src/guides/operators.md`,
`docs/src/guides/upgrade.md`, `docs/src/guides/deployment.md`,
`docs/src/reference/configuration.md`, `docs/src/reference/oidc-api.md`,
`README.md`.
- **Where the reader is told to type a command, use the new form.**
  Readers of the operator guide should meet no notice.
- **Leave a name where it identifies a past action** (an audit event's
  cause, a historical note): those pages name a command, not instruct.
  List what you left, with why, in the return.
- **`configuration.md`'s hand-kept CLI table** (its *Subcommands* section,
  from `:126`) becomes a
  short paragraph linking the generated `reference/cli.md`, so there is one
  list, not two.
- **The documented service unit's `ExecStart=… --config …` stays.** It is
  the silent, supported form.

**Test:** a scan of `docs/src/guides/` and `README.md` for the old forms
(`--print-sample-config`, `verify-backup`, `preview-upgrade`, `admin
unlock-user`, `admin rotate-key`, and the other old `admin` words) inside
code blocks, failing on any it finds. Its allowed list is empty unless the
return names an entry and why.

## §6 — C3: the reference page regenerates through its own test

The hidden `sui-id generate-cli-reference` command ships maintainer tooling
in the operator's binary. **Delete it.** The drift test
(`cli::reference::tests::the_committed_page_matches_a_fresh_render`) instead
**writes** the page when an environment variable is set (for example
`SUI_ID_REGENERATE_CLI_REFERENCE=1`), and otherwise compares. Its failure
message names that command line.

## §7 — tests, through the binary, each mutated

- **`init` never overwrites**: run it twice in an empty directory. The second
  run exits non-zero, names the path, and the file is byte-identical.
  **Mutation:** open without `create_new`; red.
- **`init` and `config sample` agree**, for both profiles, byte for byte.
- **No terminal, no prompt**: `sui-id` in an empty directory with stdin
  closed (or `/dev/null`) exits 1 with §3's guidance **promptly**, never
  waiting. Bound the test by a timeout, so a hang fails rather than stalls.
- **Explicit `--config` missing**: exits 1 naming that path, with no prompt,
  even when run in a pseudo-terminal (if you cannot allocate one in the test
  environment, say so and test the decision function directly).
- **The prompt in a terminal**: test the decision (terminal, explicit path,
  file present) as one pure function, all its cases; and drive the prompt
  itself through a pseudo-terminal if the environment allows, answering `l`,
  then `n`.
