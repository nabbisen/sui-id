## 0 — what the plan got wrong, and what this wave actually is

The plan called this *"sealing what is already atomic… no defect to
close… cheap because it is already correct."* **That was wrong**, and it
was mine: I read `change_hibp_mode`, saw `append_within_tx`, and
generalised without tracing which function production calls.

`server_settings` has **pairs** — an atomic `change_*` and a bare
`update_*`. The inventory names the **bare** one as each row's mutation
surface, and the admin settings page calls the bare one. The atomic pair
is reached only from the first-time setup wizard.

| | Production caller | Audit today |
|---|---|---|
| **S01** default language | `handlers/settings.rs:93` → `update_default_lang` | **none** — `settings.default_language.changed` is emitted only from `setup.rs:392` |
| **S02** HIBP mode | setup only; **not settable from the admin page** | atomic already |
| **S03** idle timeout | `handlers/settings.rs:183` | **none** |
| **S04** max concurrent sessions | `handlers/settings.rs:214` | **none** |
| **S05** metrics token | `cli.rs:883` | **none** |
| **S06** SMTP configuration | `handlers/settings.rs` | best-effort, `:507` |

`settings.idle_timeout.changed`, `settings.max_sessions.changed` and
`settings.metrics_token.rotated` are named in the inventory as those
rows' rationale and **have no emission site anywhere in the workspace.**
Grep them; you will find the inventory and nothing else.

**So an administrator can change the session limits or rotate the metrics
token and leave no record at all.** Not a record that might be lost on a
failing write — no record, ever. That is what this stage closes, and it
is why it is not the cheap one.

## 1 — what to build

Six sealed Class-A commands, stages 1 and 2's seam, `_within_tx` repo
functions where they do not exist.

**Use the event names the inventory already gives**, including the three
that have never been emitted — they were chosen when the rows were
written and nothing has depended on them since, so there is no stream to
disturb and no reason to invent new ones. S06's is `auth.smtp_config.changed`,
which *is* in use; keep it exactly.

**S02 is the odd one.** It is already atomic and has no admin path. Seal
it anyway — the inventory lists it and M2b requires every Class-A row
converted — and **say in the package that it had no defect to close**, so
the next reader does not infer from six conversions that six things were
broken.

## 2 — the decision this stage owes

**What the setup wizard does.** `setup.rs:392` and `:446` call the atomic
`change_default_lang`/`change_hibp_mode`, which are *not* the inventory's
named surfaces and which already append inside their transaction.

Three options and you must choose one and justify it:

- Route setup through the new sealed commands too, and delete the
  `change_*` pair.
- Leave setup on `change_*` and seal only the `update_*` path, accepting
  two ways to change the same setting.
- Something else you can defend.

**I am not choosing for you**, because the answer depends on whether
setup's actor and the admin's actor can satisfy the same
`ActorRequirement` — setup runs before an administrator session exists in
the ordinary sense, which is exactly the kind of thing that decides this
and that you will see while building it. Say what you found and what you
chose.

## 3 — what must not change

- **No new event names** except where none exists, and there use the
  inventory's.
- **No behaviour change on success.** The settings still change; what
  changes is that the change is recorded, atomically.
- **Nothing sensitive in an attribute.** S06's payload includes SMTP
  credentials and S05's is a token hash. The existing best-effort note at
  `:507` carries host, port and TLS mode — those are fine; the password
  and the token are not, and neither is the hash.
- **S07–S09 untouched.** Stages 1 and 2 are done and this stage does not
  revisit them.

## 4 — evidence

**Per command, through G20's recorders:** rollback and exactly-once, as
stages 1 and 2 did. Six commands, twelve records; G20's declared count
should move 28 → 34.

**And the one this wave specifically needs:** for each of S01, S03, S04
and S05, a test that the production path now **produces a record where it
previously produced none**. Assert the action name and the count, not
merely that some row appeared.

**Mutation evidence, two, not twelve.** (a) Drop the audit event from one
command's transaction and show its exactly-once test fail. (b) Move one
command's append outside the transaction and show its rollback test fail.
The six share one shape; stage 1 established that one mutation per
criterion is what this buys.
