## 1 — the defect, which is larger than the audit gap

`pending_change::apply` consumes the pending row — committing — and
returns the payload. `handlers/settings.rs:671-710`, the **only** caller,
then parses `tls_mode` and **returns `BadRequest` if it is unknown**,
reads the existing config, seals the password, and only then writes.

So today a pending change can be **consumed with the setting never
applied**. The row is one-shot: the administrator's queued change is gone,
nothing was changed, and the message says *"expired or no longer valid"*.

Three commits for one logical operation, in this order: consume, then a
best-effort audit, then the setting write. Any failure after the first
loses the change silently.

## 2 — Decision A: validate and seal before the transaction, write inside it

RFC 094 keeps crypto outside the transaction, so the order is forced:

1. **Read-only.** Fetch the pending row **without deleting it**. There is
   no such function today — `get_summary` returns only summary and expiry,
   `consume` deletes. Add a read-only fetch.
2. **Outside the transaction.** Decrypt the payload, parse it, validate
   `tls_mode`, read the existing `smtp_config`, seal the new password.
   `smtp_config::seal_password` already exists for the last of those.
   Every failure here happens with the pending row **still intact**, so
   the administrator can correct and retry — which is the defect in §1,
   fixed.
3. **One transaction.** Re-read the row, check the binding, delete it,
   write `smtp_config`, emit the event. The delete inside the transaction
   is still the one-shot guard: two concurrent applies race and exactly
   one wins.

**Step 1's read is not a TOCTOU hole and you should be able to say why.**
Nothing between step 1 and step 3 is trusted: step 3 re-reads and the
delete is what authorises the write. Step 1 exists only to get the
plaintext out for validation.

**Concrete, not generic.** `apply` is `apply<T: Deserialize>` today
because it was written for an open set of intents. **Measured: one intent
exists**, `"smtp_password_update"` (`handlers/settings.rs:473`), and it is
the only `create` call site. Build S08 as a concrete command for that
intent. A generic command that takes a mutation closure to run inside the
transaction is the alternative, and it is worse: it puts caller-supplied
code inside a Class-A transaction, which is precisely the boundary RFC 094
exists to narrow. When a second intent arrives, a second command is
cheaper than a general mechanism built for one.

## 3 — Decision B: a binding failure must **not** consume the row

Today it does — `consume` runs first and the binding check follows. That
is a consequence of the ordering, not a decision, and the restructure
forces the choice.

**It must not.** The binding is session, actor and CSRF token. An attacker
who holds the pending id but none of those cannot use the row — but under
today's behaviour their failed attempt **burns it**, denying the
administrator a change they queued. That is the shape RFC 123 D3 refuses
by name: an identifier that is not fully secret becoming a free denial of
a named thing.

**It does not enable brute force**, which is the obvious objection and the
reason to say it out loud: the CSRF token is bound to the attacker's own
session, so retrying cannot converge on the right value. There is nothing
to guess at.

**The denial is still audited**, and that constrains the implementation:
the event must **commit**. A closure returning `Err` rolls the audit row
back with everything else, so the binding failure is an `Ok` outcome
carrying a denied event — two event variants, `Applied` and
`BindingFailed`, the second with `AuditResult::Failure` — and the command
returns an outcome the caller maps to its error. **Do not** express the
denial as a transaction error.

**The caller's message does not change.** `"This pending change has
expired or is no longer valid."` stays, for binding failure and for
absence alike: P3's non-disclosure. What changes is that the row survives.

## 4 — a comment that becomes false, and must be fixed with the change

`repos/pending_settings_change.rs:165-168` (measured after stage 1's
additions shifted it) says the caller *"must
additionally verify `session_id` and `actor_id` … binding checks belong at
the domain layer."* After this stage the binding check is inside the
store's transaction, because it must be atomic with the delete.

Rewrite it. It described a split that was correct when the delete and the
check could not be atomic; leaving it would be prose contradicting the
code directly beneath it, which this project keeps paying for.

## 5 — what to build

A sealed S08 in `commands.rs` following stage 1's seam, with a
`_within_tx` read-and-conditionally-delete in the repo, plus the
`smtp_config` write inside the same transaction. Core's
`settings::pending_change::apply` becomes the orchestration of §2's three
steps; the handler keeps its validation but performs it **before** the
command rather than after.

Keep the action names: `settings.pending_change.applied` and
`settings.pending_change.binding_failed`.

**Attributes:** `intent` on both; `id` is `target()`. **Nothing from the
payload, and not `summary`** — same rule as stage 1, and here it matters
more because the payload is an SMTP password.

## 6 — evidence

Stage 1's two criteria, per command, through G20's recorders:
**rollback** (inject a failure before the append; the row must still exist
*and* `smtp_config` must be unchanged) and **exactly-once**.

**Then the three this stage adds, which are the point of it:**

- **A validation failure leaves the row intact.** Drive an apply whose
  payload has an unknown `tls_mode`; assert the pending row is **still
  there** and `smtp_config` unchanged. This is §1's defect, as a test.
- **A binding failure leaves the row intact and records a denial.**
  Assert the row survives, `smtp_config` is unchanged, and exactly one
  audit row exists with `result = "failure"`.
- **A successful apply writes both in one transaction.** The row is gone,
  `smtp_config` holds the new values, exactly one `applied` record.

**Mutation evidence, three.** (a) Move the `smtp_config` write back
outside the transaction and show the rollback test fail. (b) Make the
binding failure an `Err` from the closure and show the denial-is-recorded
test fail — this is the one that catches the subtle version of Decision B.
(c) Consume the row on binding failure and show the row-survives test
fail.

## 7 — what to return

The usual package, plus: what the read-only fetch is called and why it is
not a TOCTOU hole in your own words; the two event variants and their
`AuditResult`; what you added to `smtp_config` — measured, it has
**no** `_within_tx` form today, so one is part of this stage; all three mutations; the full matrix, local; and
`hunk-hashes.py` against the tip.

**`CHANGELOG`: `### Fixed` and `### Changed`.** Fixed: a pending settings
change could be consumed without being applied, losing it. Changed: a
failed binding no longer consumes the pending change. **Lead the Fixed
entry with what an administrator would have seen** — the change vanished
and the message said it had expired. Not `### Security`.

## 8 — what this stage does not do

Not S01–S06 (stage 3). Not a second intent. Not the generic mechanism §2
rejects. It does not close `0.84.0` and does not close M2b.

Leave the working tree uncommitted. One open dispatch at a time; this is it.
