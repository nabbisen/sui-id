## A — a correction to the scope document, before the stages

The scope document described wave 4 as *"the same shape, nine times"*:
nine `let _ = audit::append(...)` calls after a committed write. That is
true of the audit appends and it is **not the whole defect** for three of
the fourteen commands. Measured today in
`crates/sui-id-core/src/identity/admin/clients.rs`:

`set_client_disabled` (`:266-300`) and `delete_client` (`:303-331`) each
perform **two durable writes in sequence, neither in a transaction**, and
then a best-effort audit append:

```
set_client_disabled:  clients::set_disabled      → commits
                      refresh_tokens::revoke_all_for_client   ?        ← separate write
                      audit_with_note                                   ← best-effort
delete_client:        clients::soft_delete       → commits
                      caches.redirect_origins.rebuild
                      refresh_tokens::revoke_all_for_client   ?        ← separate write
                      audit_with_note                                   ← best-effort
```

The `?` on the revocation returns an error **after the client row has
already committed**, and before the audit append is reached. The
consequence is stated in the held dispatch rather than here; `0.85.0`
closes it, and the public record will carry it in the `CHANGELOG` once it
is closed rather than while it is open — `.github/SECURITY.md` reserves
that sequencing.

`contracts/write-commands.toml`'s C06 row already describes the mutation
surface as *"`clients::soft_delete` plus token revocation"*, so the
compound shape is not a new fact; what is new is that nothing makes the
two halves atomic, and that the ordering determines what an operator is
told.

**`crates/sui-id-store/src/repos/refresh_tokens.rs` has
`revoke_all_for_user_within_tx` (`:179`) but no client equivalent** —
`revoke_all_for_client` (`:191`) is `db`-taking only. Stage 1 therefore
builds the seam it needs rather than finding it.

## B — stage 1: the compound transition (C05, C21, C06)

Disable, enable, soft-delete. Three commands, two of which carry the
second write.

**Why first.** It is the only stage with a correctness defect beyond the
audit durability one, it is the stage that needs a new store-side seam,
and it is the stage where a wrong conversion is worst — these are the
commands an operator reaches for *because* something is already wrong.

**G20's declared set: 34 → 37.**

**Dispatched** — see §E.

## C — stage 2: credentials and authorization (C07, C08, C22, K02, K03)

Secret rotation, dev secret, registration-token revocation, signing-key
retire and delete. Five commands, uniform shape: one write, one
best-effort append.

These are the records with the highest evidentiary value — if an audit
trail is ever read in anger, "who rotated this secret and when" is near
the top of the list — so they are second rather than last, ahead of
metadata.

`signing_keys.rs:94` is the one site outside `clients.rs`; it uses the
same `audit_with_note` helper and converts the same way.

**G20's declared set: 37 → 42.**

## D — stage 3: create and metadata (C01, C02, C03, C04, C09, C10)

Create, basic metadata, allowed scopes, post-logout URIs, consent policy,
app identity. Six commands, the same uniform shape as stage 2.

Two of them (`:205`, `:315`) also rebuild the redirect-origins cache after
the write. **The cache rebuild is post-commit and must stay post-commit**
— it is not durable state and it must not be inside the transaction. The
dispatch will say so, because the natural reading of "make this atomic" is
to sweep it in.

**G20's declared set: 42 → 48**, which is every Class-A row wave 4 owns.

## E — the stage 1 dispatch is held outside git

`.git-exclude/staging/m2b-0.85.0-stage1-c05-c21-c06-2026-10-25.md`
