## 1 — what is there today, measured

`crates/sui-id/src/http/handlers/admin/clients.rs`, `clients_update_post`
at `:415-426`. One admin form submission, **three durable writes in
sequence, none of them coordinated**:

```rust
admin_uc::set_client_allowed_scopes(&app.db, admin_actor, target, …).await?;   // C03, commits
admin_uc::set_client_post_logout_redirect_uris(&app.db, admin_actor, …).await?; // C04, commits
let policy = ConsentPolicy::parse(form.consent_policy.trim());
sui_id_store::repos::clients::update_consent_policy(&app.db, target, policy, app.clock.now())
    .await …?;                                                                  // C09, commits
```

Three things are wrong and they are not the same thing:

1. **The three writes are independent commits.** A failure at the second
   leaves the scopes replaced and the post-logout URIs not — both
   security-relevant fields, both edited on one form, and the operator
   sees one error for a change that half happened.
2. **C03 and C04 append best-effort** (`core clients.rs:144`, `:171`,
   through `audit_ok`), so a successful change can leave no record.
3. **C09 emits nothing at all.** `client.consent_policy_changed` is in
   the inventory and `git grep` finds it **emitted nowhere in
   `crates/`**. This is the wave-1 shape — not a record that can be lost,
   a record that was never written — and it is why C09 is in this stage
   rather than filed with the metadata writes.

**C09 is also called straight from the handler**, bypassing
`sui-id-core`'s use-case layer that C03 and C04 go through. That is why
it was missed: a reader checking `identity/admin/clients.rs` for wave 4's
call sites does not see it.

## 2 — what to build

### 2a — one transaction for the form

The three writes and their audit events commit together or not at all.
Follow stage 1's pattern exactly — read `commands::disable_client`
(`commands.rs`, C05) first; it is the two-write case and this is the
three-write case, nothing else differs.

**A design question you must answer in your return, not guess at:**
whether this is **one sealed command with three writes** or **three
sealed commands the handler runs inside one transaction**. The inventory
has three rows (C03, C04, C09) and I am not collapsing them. My reading
is three commands cannot share one `class_a` transaction as the runner is
built today — each `class_a` call opens its own. **Measure that before
designing around it.** If it holds, the honest shape is one sealed
command whose event records all three field changes, and the three
inventory rows point at it. If you find a supported way to compose them,
say so and use it.

Either way: **state in your return which shape you built and why**, with
the runner code you measured it against.

### 2b — C09 moves behind the use-case layer

Add the `sui-id-core` use-case function C09 lacks, so the handler calls
`admin_uc::…` like the other two rather than reaching into
`sui_id_store::repos` directly. Handlers calling repos directly is how
this one escaped the wave-4 survey.

### 2c — the event

C03 and C04 already have event names (`client.set_allowed_scopes`,
`client.set_post_logout_redirect_uris`); C09's is
`client.consent_policy_changed`, declared in the inventory and emitted by
nothing. Add the `AuditEventKind` variants that do not exist yet —
`registry.rs` had only `ClientDynamicRegister` before stage 1 added three.

**Attributes:** record the **new** value for each field changed, and for
the scopes and URI lists record the count, not the full list — a list of
redirect URIs in a note field is unbounded caller-influenced data in a
hash-chained record. If you disagree, say so rather than deciding it.

### 2d — the inventory and the matrix

`contracts/write-commands.toml`: `sealed = false → true` for C03, C04,
C09; `rationale`, `mutation_surface`, `files` by hand; `event` and
`descriptor` by `check-write-commands.py --fix`, as stage 1 did. **G17
checks both directions** — a declared command with `sealed = false`
fails, and a flipped row with no declaration fails.

`contracts/audit-coverage-matrix.md`: the three rows move to class `A`,
with their note fields. **Two gates read that file differently** —
`check-audit-matrix.sh` compares names, and
`check-audit-matrix-columns.py` parses table rows for `class` and
`actor`. Get both right in one pass.

## 3 — tests, and the three this stage owes beyond its own

Same rule as stage 1, which you followed well: **for each test, delete
the thing it guards, confirm it fails, revert, and report the mutation
with the assertion failure it produced.**

1. **Rollback across the compound.** Inject a failure at the third write
   and assert **all three fields are unchanged** and **no audit row
   exists**. The scopes must not survive.
2. **Exactly-once**, per event, counted — not "at least one".
3. **An e2e assertion through the real admin path**, asserting the audit
   record and not only the field values. Stage 1's
   `r094_m2b_wave4_stage1_client_lifecycle.rs` is the model; go through
   the HTTP handler if you can, since C09's whole problem was a handler
   that bypassed the layer the survey checked.

**And three carried from stage 1's review, which are my omissions, not
yours:**

4. **A `NotFound` test for every `_within_tx` primitive this stage adds**,
   **and a back-fill for stage 1's** `set_disabled_within_tx` and
   `soft_delete_within_tx`. Measured on `05e0050`: deleting
   `if n == 0 { return Err(StoreError::NotFound) }` leaves all 567 store
   tests green, and a disable of a client that does not exist then
   returns `Ok` **and writes an audit record for it**. A sealed command
   that fabricates a record is worse than a bare write that loses one,
   and the authority gate will not catch it — that gate finds bare
   writes, not missing guards.
5. **Do not title the gate summary "Level B", and do not claim Level B.**
   Stage 1's did both; `0.84.0`'s preparation got it right with a summary
   headed *"NOT Level B"*. A local 30/30 on a throwaway clone's commit is
   the **local matrix**. Level B is every `[gates]` lane green via
   `workflow_dispatch` on the exact commit, and obtaining it is mine.
   Carry the `+stable` caveat too: those lanes are confirmable locally
   only to the extent your toolchain matches CI's.
6. **Report any public signature change by name** in your return, not
   only in the diff. Stage 1 added a `clock` parameter to
   `sui-id-core`'s `delete_client` — correct, and a breaking change to a
   published crate — and it appeared in the hunk hashes but in none of
   the prose.
