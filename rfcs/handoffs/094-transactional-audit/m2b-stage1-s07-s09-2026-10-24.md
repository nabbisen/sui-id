## 0 — what this stage is actually for

Two commands, and **the seam every later M2b wave will copy.** That is the
deliverable; S07 and S09 are the material.

M2a's conversions had their mutation and their audit already adjacent.
**These do not.** The mutation is `pending_settings_change::insert` /
`::cancel` in `sui-id-store`; the audit is a best-effort
`let _ = audit::append(...)` in `sui-id-core`'s
`settings/pending_change.rs` (`:121`, `:242`), *after* the mutation has
committed. The sealed command must live in the store crate, where
`declare_write_command!` and `class_a` are, and core must call it.

**If the seam you build here is awkward, four more waves inherit the
awkwardness.** Spend the time on it.

## 1 — the two commands

| | Today | After |
|---|---|---|
| **S07** `create` | `insert` commits, then `let _ = append` (`:121`) | One Class-A transaction: insert + `settings.pending_change.created` |
| **S09** `cancel` | `cancel` commits, then `let _ = append` (`:242`) | One Class-A transaction: cancel + `settings.pending_change.cancelled` |

**Keep the existing action names.** `settings.pending_change.created` and
`settings.pending_change.cancelled` are what an operator's audit view
already shows; a conversion that renames them changes the operator-visible
stream for no reason, and this release's point is that the record stops
being droppable, not that it reads differently.

**The template is `K01`** (`commands.rs:147-188`): descriptor static,
`declare_write_command!`, `impl SealedCommandEvent`, then a `pub async fn`
running `db.class_a`. Follow its shape rather than inventing one.

## 2 — three decisions this stage owes, and must state

**The actor requirement.** `K01` is `system_principal: forbidden` because
only an administrator rotates a key. Both of these are administrator
actions through `AdminActor` — say which `ActorRequirement` you chose and
why it matches who can actually reach the call.

**What becomes an attribute, and what does not.** Today's notes are
`format!("id={id}")` and the created one's equivalent. A typed attribute
set is not a free upgrade: `AuditAttributes` is a closed, bounded thing,
and RFC 102's step-up invariant constrains which descriptors may carry
what. **Do not put the payload, the summary, or anything from the sealed
blob into an attribute** — the whole reason that row is encrypted is that
its contents are sensitive. The `intent` string and the id are the
candidates; argue for what you include.

**Where the `PendingChange` return value comes from.** `create` returns a
`PendingChange` to its caller. A `class_a` closure returns
`(value, event)`, so this should fall out — but check it rather than
assume, and say if the shape forces a change in what core returns.

## 3 — the inventory, which is a gate not a note

`contracts/write-commands.toml`'s S07 and S09 rows become
`sealed = true`, and gain `event` and `descriptor`. **Those two fields are
derived, never hand-written** — the file's own header says so: run

```
python3.14 scripts/check-write-commands.py --root . --inventory contracts/write-commands.toml --fix
```

and commit what it writes. G17 fails if the row and the code disagree, so
a hand-edited guess is caught, but the point is not to make the gate pass;
it is that the inventory is derived from the code rather than describing
an intention.

**Leave S08's row alone.** It stays `sealed = false` until stage 2, and
its `mutation_surface` already says *"`consume` and setting mutation"*,
which is the shape stage 2 has to build. Do not adjust it to match
today's narrower behaviour.

## 4 — what must not change

- **No behaviour change for a caller that succeeds.** A successful create
  or cancel does what it does today; what changes is that the audit row
  can no longer be lost.
- **No new action names**, per §1.
- **Nothing from the encrypted payload reaches an attribute**, per §2.
- **S08 untouched.** `apply` keeps its current shape until stage 2, best-effort
  append and all. It is the next stage's subject and splitting it across
  two rounds is how a half-converted command ships.

## 5 — evidence

**Rollback, per command.** RFC 094's M2a criterion (2) is that an injected
append failure rolls back the mutation. The same must hold here: inject a
failure in the audit append and show the pending row is **not** inserted
(S07) and **not** cancelled (S09).

**`scripts/check-m2a-rollback-coverage.sh` does not cover these two** —
measured, zero occurrences of `S07` or `S09` in it. G20 runs that script
(`contracts/gate-inputs.toml:106`, `cargo +stable test -p sui-id-store
--lib` then the checker), so **extend it** rather than proving rollback in
a test the coverage gate cannot see. A converted command whose rollback is
asserted somewhere G20 does not read is how the next wave's conversion
quietly loses the property.

**Exactly-once, per command.** Criterion (3): on the success path,
precisely one audit record. Not zero, not two. Assert the count, not the
presence.

**The best-effort append is gone.** Grep the module and show it: no
`let _ = audit::append` remains in `settings/pending_change.rs` for these
two paths. §A of the plan counts four in that file today; two should
remain after this stage, both S08's.

**Mutation evidence, two.** (a) Remove the audit event from one command's
transaction and show the exactly-once test fail. (b) Make the audit append
fall outside the transaction again and show the rollback test fail. One
each — the two criteria are different properties and a single mutation
does not exercise both.

The usual package, plus:

  and anything that fought you. The next four waves read this.
- The three §2 decisions and their reasoning.
- What you added to `check-m2a-rollback-coverage.sh`, and confirmation
  that G20 reads the new rows.
- Both mutations.
- The full matrix; Level B scope. Report it local.
- `python3.14 scripts/hunk-hashes.py --baseline <sha>`.

**`CHANGELOG`: `### Changed`**, not `### Security`. Two audit records that
could previously be dropped on a failing write are now committed with the
change itself. That is a durability fix in the audit trail, and it is
operator-visible — say so plainly. **Not `### Security`**: nothing was
exploitable, the window was a failing database write, and calling it
security would spend a word this project needs for the real thing.
