## First: my own ROADMAP sentence was wrong, and it is worth saying so

The condition says *"the eight commands RFCs 102 and 103 converted."* **There is no

## The one finding that is actionable today

`crates/sui-id/Cargo.toml` declares **`rusqlite` under `[dependencies]`**, not
`[dev-dependencies]`. The clause requires it be depended on by no crate but
`sui-id-store`.

**But no production code uses it.** Every use in `crates/sui-id` is a test:
`src/runtime/database/tests.rs` and nine files under `tests/e2e/`. Measured — zero
non-test files under `crates/sui-id/src` reference it.

So the clause is **literally false and substantively true**, and the gap is one
line: move the declaration to `[dev-dependencies]`, as `sui-id-store` already does
for its own test-only use of the same crate. That makes the clause true *and*
assertable — and the clause requires it to be **gate-asserted**, which it is not
today, so the gate is a second piece of work beyond the move.

**This is the cheapest real progress available on M2a and it is not blocked on
anything.**

## What changed under the handoff since 2026-08-27

The handoff is not stale in its substance — Stage 0 and Stage 1 are still where to
start, and `migration-checklist.md` still governs. Four things moved beneath it:

1. **`ci/` became `contracts/`** (RFC 116, stage 7). Any path the checklist gives
   as `ci/…` is now `contracts/…`. The G18 contract records
   `former_directories = ["ci"]`, so this is checked rather than remembered.
2. **The Gate Matrix gained lanes and a scope mechanism.** G16–G18 did not exist;
   RFC 130 added per-gate `paths` and a `changes` job, so a push touching only
   `contracts/write-commands.toml` now runs the full Rust matrix (that file is in
   the declared Rust scope), while a docs-only push runs 13 lanes in ~2 minutes.
3. **Level B is now defined** (RFC 131 D1/D2): a claim about the shipped system
   requires every gate on the exact commit it cites. **M2a's closure will need
   that**, not a local run.
4. **Condition 9c exists** (RFC 133 D2): a design review must be filed under its
   own RFC's handoff. RFC 094's field cites the shared 094-095-096 review and is
   allowlisted; 095 and 096 likewise. Nothing to do, but the allowlist entries are
   now load-bearing and must not be removed when M2a touches these RFCs.

**Nothing found in the handoff contradicts the current tree.** The entry gate it
withheld on closed in August, and its §3 "where to start" still reads correctly.

## Proposed window, for `@nabbisen` to authorize

ROADMAP asks the architect to propose dates. **M2a: 2026-10-27 → 2026-11-21.**

**The basis, stated so he can judge it rather than take it:**

| Piece | Why it sits where it does |
|---|---|
| The `rusqlite` move and its gate | **Can start now**, ahead of the window — one line plus an assertion, blocked on nothing |
| C15's atomicity | A single command, but the one the prerequisite names, so it is the first conversion rather than one among 44 |
| Verifying the 23 sealed paths use the seam, and injected-failure rollback for each | **The bulk.** Twenty-three commands, each needing a fault-injection test that proves mutation rolls back when the append fails |
| Level B on the closing commit | A release-grade run, after the above |

**What I am not confident about:** the rollback verification is twenty-three
independent pieces of work and I have no measured basis for how long one takes.
Four weeks is an estimate from the shape of the work, not from data. **If the first
three commands take materially longer than a day each, the window is wrong and I
will say so rather than compress the work to fit it.**

**M2b is not in this window.** The remaining 44 commands minus C15 are M2b's, and
proposing dates for them before M2a has produced one measured conversion would be
the same unfounded confidence I have just criticised in my own ROADMAP sentence.
