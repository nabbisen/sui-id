# RFC 094 M2a — C15 is atomic

**Dispatched 2026-10-02** by `@nabbisen`: *"Dispatch."* **This document is a
dispatch. Start.**
**Governing RFC.** [RFC 094](../../accepted/094-transactional-audit-registry.md),
Accepted. M2a's closure prerequisite names C15 explicitly.
**Scope.** C15 only. Not the other 43 unsealed Class-A commands, and not the
seam-usage or rollback verification for the 23 already sealed.

## What C15 is

`contracts/write-commands.toml`, row `C15` — dynamic client registration.
`sealed = false`, `status = implemented`. Its declared mutation surface is three
writes that must share **one** RFC 094 transaction:
`client_registration_token::consume`, `clients::create`, and `set_registered_via`.

## The defect is larger than the inventory row says, and it is ordering

Measured in `crates/sui-id/src/http/handlers/dynamic_register.rs`:

| Line | What happens |
|---|---|
| **123** | `client_registration_token::consume(&app.db, …)` — the token is spent, committed immediately |
| 141–214 | the request body is validated: `redirect_uris` non-empty, each URI valid, `client_name` present, application-identity URIs |
| **221** | `clients::create(&app.db, &row)` |

**The token is consumed ninety-eight lines before the body is validated, and
nothing restores it.** There is no `uses_remaining` restore, no compensating
write, no unconsume path — checked.

So **a registration request carrying a valid token and a malformed body burns the
token and creates no client.** A caller with a typo in `redirect_uris` loses their
registration token. That is not a transaction-boundary nicety; it is a live
behavioural defect, and it is the one C15's prerequisite exists to remove.

**This has not reached users** — `@nabbisen` has confirmed no production use, and
dynamic registration requires a token an administrator issues. It is not urgent.
It is also not merely theoretical, and the fix is the work already scheduled.

## What to build

**Validate first, then transact.** The ordering change is as much of the fix as
the transaction is:

1. **Move all body validation ahead of the token consumption.** A request that
   cannot succeed must not spend anything.
2. **Seal C15 with `declare_write_command!`**, putting `consume`, `create` and
   `set_registered_via` plus the audit append inside **one** RFC 094 transaction
   through the approved seam — so a failure at any point rolls back all of it,
   including the token spend.
3. The inventory row flips to `sealed = true` and gains its `event` and
   `descriptor`, derived by `check-write-commands.py --fix`, never hand-written.

## What the tests must show

`test_id` in the inventory is `a_c15_dynamic_register`. Beyond it:

- **The burn is gone:** a valid token plus an invalid body leaves the token
  **unspent** — assert the token still works on a subsequent well-formed request,
  not merely that an error was returned.
- **Injected append failure rolls back the whole thing:** with the audit append
  forced to fail, the token is unspent *and* no client row exists. This is the
  clause M2a states for every converted row, and C15 is the first.
- **The happy path still works end to end**, and the audit row is written.

**Write the burn test against the current code first and watch it fail**, as you
did for the `rusqlite` clause. A test that has never failed has not been shown to
test anything.

## What this does not touch

The other 43 unsealed Class-A commands, the 23 sealed ones' seam-usage and
rollback verification, and M2b. If the work suggests a change to the seam itself
rather than to C15's use of it, **stop and report** — the seam is shared by 23
commands and changing it is not inside this dispatch.
