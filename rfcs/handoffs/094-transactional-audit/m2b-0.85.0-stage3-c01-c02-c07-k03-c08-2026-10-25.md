## 2 — the one design question, to measure rather than guess

**What event does C08 emit?**

`contracts/write-commands.toml`'s C08 row says
*"`client.rotate_secret` with dev-source attribute"* — the same event
name C07 emits. Before building to that, measure whether two sealed
commands may share one event name: read how `EventDescriptor.name` is
consumed, what `scripts/check-audit-matrix.sh` does with two rows
claiming one name, and whether `check-write-commands.py`'s derived
`event`/`descriptor` fields tolerate it. **Report what you find.**

**My lean, which you may overturn with a measurement:** give C08 its own
event name rather than overloading `client.rotate_secret`. An operator
reading the audit log sees "rotate_secret" and reasonably concludes an
administrator rotated a secret. Nobody did — dev-mode seeding patched a
configured value in at startup. A name that invites that reading is the
kind of thing this project treats as a defect even when the data behind
it is correct. If you agree, `client.dev_secret_set` and update the C08
row's rationale to say why it no longer matches what the row used to
claim.

**If you disagree, say so with the reason** and build what you argue for.

## 3 — what to build

Five sealed commands on the stage 1 and 2 pattern — `declare_write_command!`,
an `EventDescriptor` static, `impl SealedCommandEvent`, and a
`pub async fn` running `db.class_a`. Read `commands::update_client_form`
(C03, stage 2) and `commands::disable_client` (C05, stage 1) first.

- **`_within_tx` primitives** for `clients::create`, `update_basic`,
  `set_secret_hash`, `set_dev_secret_hash` and `signing_keys::delete`.
  Each must carry the **same `NotFound`/`Conflict` semantics as the async
  original** — `signing_keys::delete` maps `Conflict` to *"cannot delete
  the active signing key; rotate first"*, and that must survive. Take
  `now` as a parameter.
- **Keep or remove each async original by survey**, as before. `K03`'s
  core function already has a `let _ = clock;` placeholder, so threading
  `now` costs nothing there.
- **The two cache rebuilds stay post-commit** — `caches.redirect_origins`
  after C01/C02, `caches.jwks` after K03. They are not durable state.
- **C08 goes behind the use-case layer** if you can do it without
  dragging dev-mode seeding into `sui-id-core`; if that is the wrong
  shape, say why and leave the call in `dev_mode.rs` with the sealed
  command called directly.

**Attributes.** C07 and C08 must carry **no secret material and no
hash** — the event records that a secret was set, never any part of it.
C01 records the new client id as target. K03 keeps its `reason`.

## 6 — tests

Per command, and **for each, delete the thing it guards, confirm it
fails, revert, and report the mutation with the assertion failure**:

1. **Rollback** — injected failure before the append leaves the write
   undone and **no audit row**.
2. **Exactly-once** on the success path, counted.
3. **`NotFound`** — and for K03 also **`Conflict`**: deleting the active
   signing key must still be refused with that message, and must write no
   record. That is the one error path in this stage that is not just
   "row missing".
4. **One e2e assertion** through the real admin path asserting the audit
   record, not only the value. C08's path is dev-mode seeding rather than
   an HTTP route — assert it at whatever layer actually runs, and say in
   your return which layer that was and why.
