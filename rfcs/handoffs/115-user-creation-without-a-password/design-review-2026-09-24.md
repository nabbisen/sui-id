# RFC 115 — independent design review

**Date:** 2026-09-24
**RFC:** [RFC 115 — Creating a user without choosing their password](../../proposed/115-user-creation-without-a-password.md)
**Request:** [`design-review-request.md`](design-review-request.md)
**Reviewer:** Mid-capability model, implementation role. Authored neither the RFC nor its handoff.
**Baseline read:** `f33c7e5` (working tree clean). Read-only: no code and no RFC text changed.
**Outcome:** The design is **buildable, and the core idea is right.** It is **not yet sufficient to meet its own closure prerequisite.** One blocker and two high findings, all stated in §2. Every one of them has a small, concrete fix that fits the existing seams. Two of the RFC's factual premises are wrong in detail (§1, claims 2 and 5); neither changes the conclusion.

## 2. Findings

### BLOCKER

**B1 — An administrator-typed email address is a second way for an administrator to choose a new user's password. The design as written leaves it open.**

The chain, all read:
1. Creation is the *only* place an administrator sets a local user's email: `CreateUserForm.email` → `identity/admin/users.rs:50-60` (stored, `email_verified_at: None` at `:60`). `users::update_email` (`repos/users.rs:476`) has **no production caller** (I re-checked; only tests), so nothing else changes it.
2. `request_reset` finds the user **by that email and never consults `email_verified_at`** (`account/forgot_password.rs:99`; the filters that follow are `source == Local`, disabled/deleted, and the outstanding-token cap). Grep for `email_verified_at` finds readers only in OIDC claims, none in the reset path.
3. `POST /forgot-password` is unauthenticated. `/reset-password` completes with no SMTP requirement of its own (RFC 103 stage 4), and completion **upserts** the credential (`credentials.rs:47`, `ON CONFLICT DO UPDATE`), so it works for an account with no row (proved end to end: `crates/sui-id/tests/e2e/r103_stage4.rs`, `on_disk()`, inserts users with no credential row and the test completes a link and signs in).

So: any administrator session creates a password-less account whose email is an address *they* control, submits `/forgot-password` for it, receives the link by mail, and chooses the password. With SMTP off this is closed; SMTP is an ordinary configuration. **No step-up and no second factor is involved at any point**, because U01 is ungated (M2). This is *weaker* than the recovery-link path RFC 115 routes creation through, so the RFC's "one rule, no exceptions" and its closure prerequisite are false as designed.

**Fix (small, and it fits the existing seam).** Make `request_reset` treat a local user **with no credential row** exactly as it already treats a non-local one: the same neutral response, the same Class-B event with no user, no token, no mail (`forgot_password.rs:99-115`, the block RFC 103 D13 added). Reasoning: a never-activated account can then be activated only by an administrator-issued link, which is the audited, step-up-gated, second-factor-gated, throttled path. It costs one indexed lookup. It does not touch any account that has ever had a password. RFC 101's verified-email requirement is the durable fix and can supersede it later; it does not exist yet, so do not wait for it. Add the evidence the handoff already asks for: a test that a created user with an email gets **no** mail from `/forgot-password`, plus a mutation removing the check.

### HIGH

**H1 — The closure prerequisite cannot be met by any design that issues the link to the administrator.** Closure prerequisite 1 of RFC 115 copies RFC 103's prerequisite 4 verbatim: "no code path lets anyone other than the account holder choose or learn a password". Under this design the issuing administrator **receives the plaintext token** (`recovery_link::issue_as_admin`, `crates/sui-id-core/src/account/recovery_link.rs:81`; the page shows it once) and can open `/reset-password` themself and choose the password. That is not a bug; it is exactly the residual RFC 103's own threat-model entry states, and it is *unavoidable* while the administrator is the courier. RFC 103 assessed prerequisite 4 "met" on the structural ground that the administrator "sees only the link"; that reading is only right for the *password*, not for the *choice*.

This does not sink the RFC: what it buys is real and sufficient — no silent, indefinite knowledge of a working password; every administrator-side activation is one audited, step-up-gated, throttled, second-factor-gated event whose completion is recorded with `origin=web`; and B1 closed. **But the RFC must state the property it actually delivers.** Suggested wording for the closure prerequisite: *"No path lets an administrator set or learn a user's password except by issuing a recovery link through U37 (audited, fresh-step-up, second factor, throttled); the administrator's ability to complete the link they issued is a stated residual (RFC 103 threat model)."* Update `docs/threat-model.md`'s RFC 103 entry to say the residual now covers every account an administrator creates, not only existing ones.

**H2 — `must_change` cannot be "enforced" by a change at the session-extractor layer alone.** See item 14. Not a defect in the RFC's design goal, but the RFC and handoff price it as "the smaller change", and it is not. Ranked high because a half-done gate is worse than the current honest absence: it would read as a control (the handoff's own point) while OIDC `/authorize` walks around it.

### MEDIUM

**M1 — Remove the `credential` parameter from `commands::create_user` instead of passing `None`.** With `Option<CredentialRow>` left in place, the store can still express "an administrator sets a password at creation", and nothing but review keeps it from reappearing. Remove the parameter (and `CreateUserSpec.password`, `min_password_len`, `hibp_*`, `commands.rs:430-441`, `identity/admin/users.rs:12-100`). Then a password at creation is a *compile error*, which is what RFC 102 stage 9 did for the raw step-up write. Pair it with a structural test that enumerates the writers of `credentials` against an allowlist (`setup`, U09, U10, and `--dev`), so a fifth writer fails CI rather than review. (The earlier design review already noted the first-run wizard writes outside any transaction and must be allowed by name.)

**M2 — U01 has no step-up, no second-factor requirement and no confirm screen.** `users_create` (`admin/users.rs:107`) has CSRF only; it can create an *administrator* (`is_admin` checkbox, `identity/admin/users.rs:64-65`). Today that is the same power as the password; after this RFC it is the first half of a two-step activation, so it matters less, but it should carry RFC 102 B4's `step_up` evidence like the other five sealed admin commands. Related, pre-existing and **out of scope but adjacent**: `users_set_role` (`admin/users.rs:689-745`) promotes any user to administrator with no step-up and no confirm either.

**M3 — A never-activated account is a state the sign-in path handles worse than the state it replaces.** See item 8: it skips the Argon2 dummy verify and writes no `auth.login.failure`. Cheap to fix in the same change.

**M4 — The HIBP `warn` outcome becomes unrecorded.** See item 10. `user.create_warned_hibp` becomes unreachable, and at the point the user *does* choose a password (U10) a `warn`-mode hit is silently discarded (`forgot_password.rs:320` tests only for `Blocked`). Decide whether U10 gains a `hibp_warned` attribute; do not just delete the event.

**M5 — Thirty callers use U01 with a password, and the RFC does not say what happens to them.** Core `authn/step_up.rs` tests (9 call sites), store `runner/user_admin.rs` (5), e2e `mfa.rs`, `r102_stage3.rs`, `r102_stage7.rs`, `r103_reset_mfa.rs`, `r103_stage3.rs`, `r103_stage4.rs`, `rfc030_033_035.rs`, and `--dev` seeding `dev_mode.rs:424`. Removing the parameter (M1) breaks all of them. Tests need a store-side constructor compiled only for tests (the A4 precedent: `sessions::insert` is `pub(crate)` and `#[cfg(test)]`). `--dev` is a **runtime** flag in the production binary, so it cannot use a cfg-gated helper: it is a real, named exception to "no exceptions". Say so in the RFC, and scope the closure prerequisite "outside `--dev`" (dev seeding prints its passwords to stderr by design, `dev_mode.rs:296-298`).

**M6 — 30-minute links are short for onboarding.** RFC 103 fixed the TTL at `DEFAULT_TOKEN_TTL = 30 min` (`forgot_password.rs:53`) for recovery, where the person is on the phone. Provisioning a new hire is a different shape: the person is not there. `recovery_link::issue_as_admin` computes `expires_at` itself (`recovery_link.rs:81`), so an activation-purpose issuance can carry a longer TTL without touching the store. Owner's call; a longer TTL for an account that has never held a credential does not enlarge what a stolen link can reach.

### LOW

**L1 — Orphaned, never-activated accounts have no lifecycle.** They never expire, cannot be re-created under the same name (claim 7), show as **Active** in `/admin/users` (`sui-id-web/src/pages/users.rs`; the detail page's status badge has no "awaiting activation"), count in `count_admins` (`repos/users.rs:727`, `role='admin' AND is_deleted=0`), and appear in the dashboard's admins-without-MFA warning (`:541`). A never-activated **admin** therefore makes `users_set_role`'s last-admin guard (`admin/users.rs:710-717`, `count_admins() <= 1`) pass when the only usable administrator is demoted. Recovery exists (`sui-id admin issue-recovery-link` works for administrators, so it is not a lock-out), but state it, and consider a derived "awaiting activation" label (`NOT EXISTS credentials`) in the list.

**L2 — `me_security.rs:82-86` says a missing credential row "shouldn't happen in practice".** After this RFC it is the ordinary state. Update the comment; the code (refuse like a wrong password) is right.

**L3 — Docs to touch:** `docs/src/reference/audit-events.md:50-51`, `ci/audit-coverage-matrix.md:45-46`, `ci/write-commands.toml:28` (rationale names both events), `docs/src/getting-started/overview.md:56`, `docs/threat-model.md` (the paragraph at `:112-118` that points at this RFC), the pinned event list in `crates/sui-id-store/src/commands/tests.rs`, and G13's count (56 → 55 if `create_warned_hibp` goes).

## 3. Answers to items 8–16

**8. Can a user with no credential row exist end to end?** Yes, and it mostly works, with one real defect.
- **Sign-in.** `login_with_mfa` finds the user, passes the disabled/deleted and lock checks, then `credentials::get` returns `NotFound`, mapped to `InvalidCredentials` (`authn/session.rs:190-193`) and returned. **Two problems, both new in scale though not in kind (LDAP/federated shadow rows already have no row):** the return happens *before* `verify_password`, whereas every other refusal in this function first runs a dummy Argon2 verify precisely for timing equivalence (`:154`, `:162`, `:175`); so a password-less local account answers measurably faster than a wrong password and is enumerable by timing. And no `record_login_failure` runs, so **no `auth.login.failure`, no counter, no lockout** is recorded for it (the handler adds nothing: `admin/auth.rs:164-168`). Fix: run the dummy verify and `record_login_failure(..., "no credential")` on that branch.
- **Reset.** `request_reset` works today for such a user with an email on file (that is B1). Completion works: U10 upserts the row (`credentials.rs:47`; `r103_stage4.rs` proves it end to end).
- **Admin list and detail.** `users::list` selects `users` only (`repos/users.rs:236`); no join, no `expect`, no page renders "password set". Nothing panics.
- **Other readers of `credentials::get`:** `me_security.rs:87` and `step_up.rs:409` both map `NotFound` to a refusal, not a panic. A password-less user cannot hold a session, so neither is reachable.

**9. What dies with the password field?** `check_password_policy` (`users.rs:38`), `enforce_hibp` (`:40`), `hash_password` (`:79`) and `min_password_len` leave the creation path. **They still run on the password the user chooses:** `consume_and_reset_password` calls `check_password_policy(new_password, min_password_len)` at `forgot_password.rs:315` and `enforce_hibp(hibp_mode, …)` at `:320`; the handler passes `password_min_len(&app)` and the stored `hibp_mode` (`handlers/forgot_password.rs`, `reset_password_post`). Both run before the token is looked up, so a refusal re-shows the form with the link still valid (RFC 103 stage 1 ruling). Confirmed by reading; the e2e reset tests exercise it.

**10. Does U01's audit event change?** `user.create` stays valid: its descriptor has `attributes: &[]` (`commands.rs:368`) and never described the credential. **`user.create_warned_hibp` becomes unreachable** — its only producer is the `hibp_warned` bool computed at `identity/admin/users.rs:41`. Removing it touches `registry.rs:171-172`, `commands.rs:371-380,399,407,444`, the pinned list in `commands/tests.rs`, the matrix row (`audit-coverage-matrix.md:46`), the reference row (`audit-events.md:51`) and the manifest rationale (`write-commands.toml:28`). Historical rows keep the name. See M4 for the warn outcome itself, which is what actually gets lost.

**11. Two commands or one?** **Two, in sequence, joined by a redirect — not one transaction.** Reasons:
- The runner appends **exactly one** registered event per Class-A command (`class_a` closures return `(value, one_event)`; RFC 102's invariant). One transaction would need a *new* sealed command (a "U38") that re-implements U37's D5/D6/D8 checks and B4 evidence. Two copies of that logic is how the RFC 103 controls would drift.
- The token is generated outside the transaction and returned to the caller by design (`recovery_link.rs`); a combined command changes that contract.
- The failure mode of two commands is benign: if the second fails after the first commits (throttle refusal, lapsed step-up, append failure) there is a user with no credential, no token, no session, and nothing that can sign in. The administrator retries from the user's page; the button exists (`admin/users.rs:349`, `can_issue_recovery`). Nothing is exposed. The only cost is the orphan in L1.
- Sequence it as: create (U01) → redirect to `/admin/users/{id}/recovery-link-confirm`, which already demands fresh step-up, a required reason and a confirm marker. The audit trail is two events, `user.create` then `user.recovery_link.issued`, each carrying what it did.
- **One dependency:** the `can_issue_recovery` flag (`admin/users.rs:349`) hides the button for an administrator target, so a password-less *administrator* would have no web route to activation. It must change in lockstep with the Q12 ruling.

**12. Creating a second administrator.** **View: option 3 is expressible and safe, if B1 is fixed first; option 2 already works today and needs no change.**
- What D5 checks: `check_recovery_target` (`commands.rs:1490`) refuses, in order, unknown, the issuer (`:1501`), an administrator target (`:1504`), deleted, disabled, non-local — all inside U37's transaction on a fresh read (`recovery_target_within_tx`, `repos/users.rs`).
- The relaxation: refuse an administrator target only when it **has** a credentials row, i.e. `if t.role.is_admin() && t.has_credential`. `RecoveryTarget` gains one field read in the same statement. Live accounts are unaffected: credentials rows are never deleted (claim 2), so a live administrator always has one. Non-local targets (LDAP and federated shadow rows also have no credential row) are refused earlier in the same function, so they cannot be reached through the relaxation. Add `last_login_at IS NULL` to the predicate as defence in depth: it keeps the rule correct if a later RFC introduces passwordless local accounts, where "no row" would stop meaning "never activated".
- The residual it creates is the one in H1, plus: whoever holds the link *becomes* the new administrator. That is inherent in "an administrator creates an administrator"; it is no worse than today (where they know the password), and it is now gated by step-up and a second factor, which creation is not (M2).
- **Option 2** (create on the web, activate with `sui-id admin issue-recovery-link`) needs no change to D5: the CLI does not apply the admin refusal (`commands.rs`, `issue_recovery_link_as_operator`). It requires host access for every second administrator, which is rare and arguably right. If the owner prefers minimum change, this is the option that adds nothing to the attack surface.
- **Option 1** (a web password field for that one case) reintroduces exactly the defect. I recommend against it.

**13. The throttle against provisioning.** **Expressible without an unthrottled path, with three conditions.**
- Today the count is `password_reset_tokens WHERE issued_by = ? AND issued_via = 'web' AND issued_at > ?`, every state (`repos/password_reset_tokens.rs:200-211`), against `RECOVERY_LINKS_PER_HOUR = 5` (`commands.rs:1362`, checked at `:1590`).
- Mark exempt issuances with a new column, `provisioning INTEGER NOT NULL DEFAULT 0 CHECK (provisioning IN (0,1))` (an `ALTER TABLE … ADD COLUMN`, as migration 0041 did; `issued_via` cannot gain a value without a table rebuild because of its CHECK). Count only `provisioning = 0` against the five.
- **The exemption predicate must be evaluated in U37's transaction, on the target:** the target is local, has **no credential row**, and has **no earlier token of any kind**. The "create a user in order to get an unthrottled issuance" attack then yields a link to the account just created, which the attacker already controls, and to nothing else: existing accounts always have a credential row, so they can never qualify. This is the property to test and mutate.
- **Two conditions beyond the architect's recommendation.** (a) Do **not** exempt administrator targets: an unthrottled stream of new administrator accounts is the persistence primitive a stolen session with a fresh step-up would want. They count against the normal five. (b) Do not make exempt issuances free: give provisioning its own, larger ceiling (say 100 an hour per issuer, counted from the database the same way), so a bulk import is possible and a runaway is not.
- The CLI's own five is unchanged; `sui-id admin issue-recovery-link` is the escape hatch for genuine bulk.

**14. `must_change`: enforce it or delete it.** **View: delete it, unless the owner values forcing rotation of `sui-id setup`'s printed password; if enforced, it is the largest item in this RFC and needs its own package.**
- *Where a check must go.* The obvious point is `session::resolve` (`authn/session.rs:302`), which the five extractors share (`handlers.rs:147,184,219,253,290`). **That is not enough.** `oidc.rs:~258-275` (`/authorize`'s session lookup) and `metrics.rs:~78-95` call `sessions::get` directly and never touch `resolve`. A forced-change account would therefore complete OIDC authorisation and be issued codes and tokens for relying parties while "forced to change". Also `admin/auth.rs:86` (already-signed-in redirect) and the raw-cookie readers in `me_security/*` need a defined behaviour.
- *What the screen must not allow:* any other page; `/authorize`; `/oauth2/token` for a code minted before the flag was seen; step-up, passkey and TOTP enrolment (they would let the holder of a known password add a factor); and skipping (the only exits are the change and sign-out). The change itself must require the *current* password (U09 does), so a session hijack cannot use it to set a new one.
- *Storage.* Read the flag once at sign-in and store it on the session row (a `sessions` column, snapshotted by L01–L04), so `resolve` does not add a query per request and a change of password clears it for that session only through U09/U10, which already write `must_change: false`.
- *Audit.* No new event is needed: U09's `auth.password.changed_self` already records the change; add the fact to L01's note (`must_change=1`) so the forced state is visible at sign-in.
- *Why delete is attractive.* After this RFC the only writer of `true` is `sui-id setup` with a generated password (claim 3), for an operator's *own* account; the column, `CredentialRow.must_change`, three function parameters (`setup.rs:86,146`) and one test become removable with one migration (`DROP COLUMN` is permitted for a column whose own CHECK is its only reference; verify on the pinned SQLite). The doc comment at `cli.rs:471` then says what is true: a printed password to change after first sign-in.
- *Why it might still be worth enforcing:* the generated password is printed to stdout, which Ansible, cloud-init and Docker capture into logs (the very use RFC 077 names). Forcing rotation limits how long that log line is a working credential. That is a real benefit, but it is the operator's exposure, not RFC 115's threat, so it can wait for its own RFC.

**15. Threats the design introduces or misses.** B1 (email), H1 (the administrator can complete the link), M2 (creation is ungated), M3 (timing and audit gap), L1 (lifecycle). Additionally: (a) **federation email collision** blocks provisioning when a local user already has the same email (`handlers/federation.rs`, P2 collision check), so an administrator pre-creating a colleague's address can block that colleague's first federated sign-in; a nuisance, not a takeover, and it exists today. (b) **OIDC and the session cap**: a never-activated account has no session and issues no tokens, so neither is affected. (c) **`count_admins` and the dashboard** count it (L1).

**16. What cannot be built as described, or would be better built another way.** (a) "One rule, no exceptions" is untrue for `--dev` (M5) and for `sui-id setup` (the operator's own account, which is fine, but say so). (b) The RFC lists only the `Debug` derives on password forms; a redaction rule should be **type-level**: use `secrecy::SecretString` for every field named in claim 5, with `Debug` redacted by the type and one test that formats each form. That also covers the dead DTOs, which should simply be deleted. (c) The handoff's evidence list has no test for B1, for the sign-in timing/audit gap, or for the throttle predicate; add them. (d) RFC 115 touches `crates/sui-id-store/src/commands.rs` and `repos/`; if the throttle column (item 13) is chosen it needs a migration, which the `Touches` line does not list.
