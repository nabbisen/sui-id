# RFC 128 D2 — the fourteen live G11 conditions, traced to their source

**Date:** 2026-10-01

**Scope.** Enumeration only, as instructed — no judgement about whether a condition is good, only where it comes from.

## Method

Each row: what the condition checks (from `scripts/check-rfc-integrity.py`'s own docstring, lines 7–42), the live document that requires it, and the `file:line` where that document says so. A condition whose only source is `rfcs/archive/018-rfc-lifecycle-policy.md`, or which has no source at all, is named as such — explicitly, below.

**Corrected 2026-10-01 (D7/D8 of the review).** This package and the D1/D3/D5 package landed in the same delivery, and D1/D3's own amendment to `rfcs/done/093-build-toolchain-release-gates.md` shifted every line number this table cited into it — the citations below were originally measured against `d031438` and have been re-measured directly against the post-amendment tree (`9381347` and later) rather than computed by applying the shift arithmetic, to avoid compounding one arithmetic error with another. Row 10's citation was also simply wrong under either version (D8) and is corrected to the right bullet, not just the right line number.

## What this confirms and what it finds

**Nothing here traces only to the archived RFC 018.** Every one of the fourteen live conditions has a source in RFC 000, RFC 093, or RFC 110 — all live documents. The dispatch's concern that "condition 9 is unlikely to be the only inheritance" (RFC 128, "Why this is worth an RFC") does not hold on this measurement: condition 9 was the only place RFC 018's vocabulary ("independent," implicitly an N/A prohibition) leaked into how the gate's *behaviour* was **described** — not into the gate's actual code, which this trace found never implemented either.

**Condition 7's open question is closed**: its owning document is RFC 093, cited by both RFC 093's own prose and `contracts/rfc-policy.toml`'s comment. No further action needed there.

**One adjacent imprecision, named but out of scope**: condition 10's RFC 093 description also says "independent closure metadata," which has the same loose relationship to the actual (unlabelled-as-independent) field names that condition 9's description had. The dispatch names condition 9 specifically as "D1's subject"; I have not touched condition 10's wording, and flag it here rather than silently fixing or silently leaving it unmentioned.
