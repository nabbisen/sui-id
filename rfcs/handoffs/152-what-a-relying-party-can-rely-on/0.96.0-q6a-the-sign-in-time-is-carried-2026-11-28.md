## §0: what is there today (measured at `64e7b04`)

- **No sign-in time is stored anywhere.** `SessionRow` (`crates/sui-id-store/src/models.rs:543`) has `created_at` and
  `last_step_up_at`. No ID token carries `auth_time`. The only `auth_time` code validates a *provider's* token
  (`crates/sui-id/src/http/optional_claims.rs:350`).
- **Sessions are inserted in exactly six places**, all in `crates/sui-id-store/src/commands.rs`:
  - L01 `sign_in_with_password` (`:2047`);
  - L03 `sign_in_from_directory` (`:2112`);
  - L04 `sign_in_federated` (`:2337`);
  - `provision_federated_user` (`:2448`);
  - `promote` (`:3243`, a federated sign-in that completed a local second factor);
  - L02 `complete_second_factor` (`:3488`, which also covers a passkey or a recovery code used as the second factor).

  `repos::sessions::insert_within_tx` is crate-private (RFC 102 A4), so there is no seventh.
- **`acr`/`amr` already travel the path `auth_time` must take.** The session's `auth_methods` go into the code
  (`complete_authorization`, `crates/sui-id-core/src/oidc/authorize.rs:340`, and the consent POST,
  `crates/sui-id/src/http/handlers/oidc.rs:916`). From the code they go into the refresh token (`exchange_code`, `:477`),
  and from one refresh token to the next (`exchange_refresh`, `:657`). `issue_token_set`
  (`crates/sui-id-core/src/oidc/tokens.rs:117`) turns them into `acr`/`amr`. Migration 0006 added the columns.
- **Step-up** writes `last_step_up_at` through `repos::sessions::record_step_up_within_tx`
  (`crates/sui-id-store/src/repos/sessions.rs`), under L05 (`commands.rs:3728`). **B7's `first_factor_proof`**
  (`crates/sui-id-core/src/authn/step_up.rs:388`) writes nothing to the session.
- **Neither a code nor a refresh token names its session.** `auth_codes` (migration 0019) and `refresh_tokens` have no
  session column. So **a row issued before this stage has no knowable sign-in time**. Refresh tokens rotate on every use
  (`refresh_lifetime_secs`, default 14 days, per token), so such a family can live indefinitely.
- **The empty scope list.** `clients.allowed_scopes TEXT NOT NULL DEFAULT ''` (migration 0002). `enforce_scope_policy`
  (`authorize.rs:309`) returns `Ok(())` when the list trims to empty. The defined scopes are the rows of
  `scope_definition` (migration 0036, seeded with the four standard ones). Nothing deletes from it.
- **Migrations are SQL only.** `apply_migration` (`crates/sui-id-store/src/migrations.rs:668`) runs each in its own
  `IMMEDIATE` transaction (`tx.execute_batch(m.sql)`, `:697`). A file starting with `-- MIGRATION:FK_DISABLE_REQUIRED`
  (`:638`) has foreign keys turned off before the transaction, and checked after it (0022 rebuilt `clients` this way).
- **Audit rows come from one place.** The only production caller of `repos::audit::append_within_tx` is the Class-A runner
  (`crates/sui-id-store/src/registry.rs:1174`, `class_a_in`). That runner is async and opens its own transaction from a
  `Database`, which does not exist while migrations run. Its body is already a closure over `&rusqlite::Transaction`.

## §1: the sign-in time

**The rule, D2: *`auth_time` may be older than the truth, never newer.*** This stage stores and carries it. Q6 uses it.

- **`sessions.authenticated_at`**: the moment the session's user last presented a credential to it.
  - **Set to the insert's own `now`** by all six inserts of §0. For L04 and `provision_federated_user`, that is the moment
    sui-id accepted the federated sign-in. Q6b refines those two.
  - **Moved to `now` by L05**, a completed step-up with a TOTP code or a passkey, in the same write as `last_step_up_at`.
  - **Not moved by B7** (`first_factor_proof`).
  - The Rust field is `authenticated_at: DateTime<Utc>`, not an `Option`. A row read with it missing is
    `StoreError::Integrity`.
- **`auth_codes.auth_time`**: the session's `authenticated_at` when the code is issued, by both paths of §0 (direct and
  consent).
- **`refresh_tokens.auth_time`**: the code's `auth_time` at exchange, and the predecessor's `auth_time` at refresh.
  **Never `now`.**
- **`auth_time` in every ID token**, as a NumericDate (integer seconds), from the code at exchange and from the refresh token
  at refresh. A refresh's ID token therefore repeats the original sign-in time, as it repeats `acr` and `amr`.
- **Read side, fail closed**: a code or an unrevoked refresh token whose `auth_time` is missing is refused with
  `invalid_grant`. §3 means none exists. This is the guard if one ever does.

## §2: D9, the empty scope list ends

- **Each app whose `allowed_scopes` trims to empty** gets an explicit list: `openid` first, then every other name in
  `scope_definition`, by name. That covers the four standard scopes and every defined custom one.
- **Each converted app gets one audit record**, naming the list it was given.
- **A `CHECK (trim(allowed_scopes) <> '')`** then refuses an empty list, on insert and on update. The `DEFAULT ''` goes.
- **`enforce_scope_policy` loses its empty branch.** An empty list, if one ever reached it, refuses every scope (fail
  closed). It must never permit one.
- Apps with a non-empty list are untouched, and get no record.

## §3: the rows that have no sign-in time

On the owner's decision (above), **the migration revokes every refresh token with `revoked_at IS NULL` and deletes every
row of `auth_codes`.**
- **One audit record** gives both counts.
- Each relying party's next refresh fails with `invalid_grant`, and each user signs in once per app after the upgrade.
- Then every ID token carries a true `auth_time`, with no exception in the code.

## §4: the migration, `0056`, one transaction

**One migration**, so that RFC 152's schema change is all or nothing: `0056_rfc152_sign_in_time_and_scope_lists.sql`, with
the FK-disable marker, because it rebuilds `clients`.

**A migration may now carry a Rust step**, run inside the migration's own transaction **before** its SQL:
- `Migration` gains `before_sql: Option<fn(&rusqlite::Transaction<'_>) -> StoreResult<()>>`. Only `0056` uses it. Document
  the field where `Migration` is declared.
- **The step writes audit records only through sealed Class-A commands**, never by calling `append_within_tx` itself.
- **The registry gains a synchronous entry that runs a command inside a transaction it is given.** The body that today
  lives in `class_a_in`'s closure is factored into one function, which both `class_a_in` and the new entry call. **One copy
  of that body, never two**: the comment above `class_a_in` explains why.
- **Two new commands**, both `system_principal: permitted`, built with `AuthorizedCommandContext::for_system_actor`
  (`registry.rs:1038`), like C25 and C26:
  - **`C27`**: an app's empty scope list made explicit. Its target is the client id, and its required attribute `scopes`
    is the list given.
  - **`T05`**: tokens with no sign-in time ended at upgrade. Its required attributes are `refresh_tokens_revoked` and
    `codes_deleted`.
  - Each goes into the event registry, `contracts/audit-coverage-matrix.md` and `docs/src/reference/audit-events.md`,
    under RFC 094's contract.

**The order inside the transaction**:
1. the Rust step: C27 for each empty list, then T05;
2. the SQL:
   - add `sessions.authenticated_at`, backfilled to `created_at` (older than or equal to the truth: D2's safe direction);
   - add `auth_codes.auth_time` and `refresh_tokens.auth_time`;
   - rebuild `clients` with the `CHECK`.

**The rebuild keeps everything else exactly**: every column, its type, default and constraint, every index and every
trigger. Copy them from the live schema, not from older migration files.

## §6: the record

- **CHANGELOG `Unreleased`, *Changed***:
  - every ID token carries `auth_time`, and a refresh repeats the original;
  - an app's empty scope list, which permitted any scope, is replaced at upgrade by an explicit list, and can no longer
    be stored;
  - refresh tokens issued before the upgrade are revoked, so each user signs in again once per app.
- **The upgrade note**: a new `### v0.96.x` section in `docs/src/guides/upgrade.md`, marked as describing the unreleased
  `0.96.0`. It is for both readers:
  - **the operator**:
    - the two queries to run first: `SELECT id, name FROM clients WHERE trim(allowed_scopes) = '';` (the apps that will be
      converted) and `SELECT count(*) FROM refresh_tokens WHERE revoked_at IS NULL;` (the tokens that will be revoked);
    - what each converted app is given;
    - where the records appear;
  - **the relying-party developer**:
    - one `invalid_grant` per user after the upgrade, then a normal sign-in;
    - from then on, `auth_time` is in every ID token.
- **Not in this stage**: the reference's parameter table and `auth_time` text (D7, Q8), and anything about `prompt` or
  `max_age` (Q6).
