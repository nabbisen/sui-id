## §1 — the defect

`POST /oauth2/introspect` answers `active: true` for an unexpired access token **whose user is disabled or deleted**.
- `active_from_access` (`crates/sui-id-core/src/oidc/oauth_token.rs`) reads the user only for the `username` courtesy
  field, with `.ok()`. It never reads `is_disabled` or `is_deleted`.
- Its comment says this is deliberate for a deleted user. That was a decision about `username`, and it was extended to
  `active` without anyone deciding that.
- **userinfo refuses the same token** (`handlers/oidc.rs`: `if row.is_disabled || row.is_deleted`). So two endpoints of
  one provider disagree about the same user at the same moment.
- Disabling (U02) and deleting a user revoke sessions, refresh tokens and codes in one transaction, but not the outstanding
  access tokens. The window is `tokens.access_lifetime_secs`, which nothing caps.

## §2 — the fix

- **`active_from_access` answers inactive** when:
  - the token's `sub` does not parse as a user id;
  - the user cannot be read (a read error, or not found);
  - the user is disabled or deleted.

  **Fail closed**: RFC 7662 lets every "no" be `active: false`, which the code already does for a bad audience. The
  username stays a field of an *active* answer only.
- **Delete the comment** that calls reporting a deleted user's token active deliberate. Replace it with one line stating the
  rule: an active answer requires an enabled, existing user, as userinfo does.
- **No other change of behaviour**: the audience check, the deny-list and the refresh-token branch stay as they are.
  **Report what the refresh-token branch does for a disabled user**, measured in a test: its tokens are revoked by the
  disable, so it should already answer inactive. State that in the return; don't assume it.
- **Check the other places that accept an access token.** The architect found two, userinfo and introspection, by grepping
  `verify_access_token`. Re-grep, and list every caller in the return with what each does for a disabled user.

## §3 — tests, each with a mutation

| Test | Mutation it must catch |
|---|---|
| e2e: issue an access token, disable the user (through the real admin command), introspect it: `active: false` | the user check removed |
| The same after the user is **deleted** | the check reads `is_disabled` only |
| The same token **before** the disable is `active: true` (so the test proves the change, not a broken token) | — |
| A user who is re-enabled after a disable: introspection is `active: true` again for a token issued **after** re-enabling | — |
| userinfo and introspection agree for each of the states above: one test walks enabled, disabled and deleted, and asserts both endpoints together | introspection made to ignore the state again |

**Name the tests by the rule they hold**, for example
`introspection_and_userinfo_agree_on_whether_a_user_can_be_served`, **not by the hole they close**.
