## §2: weakening is a dangerous action; strengthening is not

RFC 058 defines a dangerous action as one that *"meaningfully reduce[s] the security or availability of a principal"*.
Lowering the breach check weakens every account's next password. So:
- **Strengthening** (`off` to `warn`, `off` to `block`, `warn` to `block`) saves directly, like P5's form.
- **Weakening** (`block` to `warn`, `block` to `off`, `warn` to `off`) carries RFC 058's three obligations:
  1. **a confirmation screen**, saying what changes (passwords found in a breach will be accepted, or no longer checked at
     all) and that it applies to every password set from then on, not to existing ones;
  2. **step-up immediately before**, `require_fresh_step_up`, as the other dangerous actions do;
  3. **an audit record with its `note` populated**, saying it was a weakening.
     - Measure S02's event first. If it has no `note`, or adding one changes the audit event's schema (RFC 094's
       contract: its registry, the coverage matrix, the event reference), **stop and return**, with what the change
       would be.
- **The direction is decided on the server**, from the stored mode and the submitted one, inside the same request. **It is
  never decided from anything the form sends about itself.** A request that claims to strengthen while it weakens must still
  require the confirmation and the step-up.
- Saving the mode that is already stored writes nothing, and records nothing.

## §7: amended 2026-11-27, after the first return stopped at §5

The return stopped correctly: S02's note can carry nothing but its own attributes. That holds for both writers, and
`render_note` is the only place a note is built (`registry.rs:880`). **The premise was the dispatch's, and it was wrong.**

**1. No schema change. §2's third obligation is already met.**
- RFC 058 asks for an audit record *"with `note` populated"*. S02's note is always populated: `old=<mode> new=<mode>`, both
  required. A weakening is legible in the record itself (`old=block new=off`).
- The other dangerous actions record no more than this. `user.delete` and `signing_key.rotate` carry their own attributes
  (`reason`, `algorithm`), and none records a word like "weakening", or that step-up happened.
- So §2's item 3 now reads: **the S02 record names the old and the new mode, as it does today.**
- What this stage adds for a weakening is RFC 058's other two obligations: the confirmation screen, and step-up immediately
  before it. Test 3 asserts the record's `old` and `new`, not a new attribute.

**2. The two contract sentences this stage makes untrue**, found by the return. Update them with the code:
- `contracts/write-commands.toml`, S02's `rationale` (*"only the setup wizard calls it"*);
- `contracts/audit-coverage-matrix.md`, the `settings.hibp_mode.changed` rows' note (*"from the setup wizard only"*).

Both callers are named: the setup wizard, and Sign-in settings.

**3. Dev mode said HIBP was off, and it was not.** Measured by the return and re-measured here:
- `apply_seed` never writes `hibp_mode`, so it stays at the column's default, `warn` (migration `0017_hibp_mode.sql`);
- dev mode installs the real HIBP client (`cli/handlers.rs:1536`), so `sui-id dev` sends live breach-check requests.

Three places say otherwise:
- the terminal banner (`runtime/dev_mode.rs:286`, *"HIBP off, cookie_secure off."*);
- the page banner (`sui-id-web/src/layout.rs:240`, *"cookie_secure=false, HIBP off."*);
- the Quick Start (`docs/src/getting-started/quick-start.md:179`, *"Disables `cookie_secure` and HIBP checking."*).

**Make the code do what all three say.** Dev mode stores `off` when it seeds, in the same seeding. The documented intent is
consistent, and a local trial should not reach an outside service unannounced.
- Sign-in settings, in dev mode, says that dev mode starts with the check off. It can still be changed until the next start,
  since the dev database is fresh each start.
- **Test**: after dev mode's seeding, the stored mode is `off`. **Mutation**: remove that write.
- If seeding cannot write it through S02, say how it is written instead. A seed is not an administrator's action, so a direct
  settings write may be right. Measured here, the seed writes no setting today, so this is the first one. Say which write
  you chose, and why.
