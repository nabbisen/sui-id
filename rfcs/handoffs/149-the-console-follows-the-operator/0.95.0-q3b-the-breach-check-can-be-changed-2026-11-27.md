## §0: what is there today (measured at `420001b`)

- **The mode** is `server_settings.hibp_mode`: `off`, `warn` or `block` (`HibpMode`,
  `crates/sui-id-store/src/models.rs:840`).
  - `off` makes no check and no outbound request. It is the right setting offline.
  - `warn` checks, records a hit as an audit event, and accepts the password. It is the default at installation.
  - `block` checks, and refuses a password found in a breach.
- **Only the setup wizard can choose it.** `sui_id_store::commands::change_hibp_mode` is already a Class-A command with its
  audit event (S02, `commands.rs:5336`). Its only caller is `handlers/setup.rs:451`.
- **Since Q3**, the dashboard's warning for `off` and the operator's guide (setup, step 4) both say it *"cannot yet be
  changed"* after setup. This stage makes that untrue, so both change with it.
- **The shape to follow** is P5's minimum-length form on the same page:
  - `password_min_len_post` (`handlers/settings.rs:298`): `CurrentAdmin`, CSRF, the Class-A command, a redirect, and a flash
    on refusal;
  - the auditor sees the value and no form.

## §2: weakening is a dangerous action; strengthening is not

RFC 058 defines a dangerous action as one that *"meaningfully reduce[s] the security or availability of a principal"*.
Lowering the breach check weakens every account's next password. So:
- **Strengthening** (`off` to `warn`, `off` to `block`, `warn` to `block`) saves directly, like P5's form.
- **Weakening** (`block` to `warn`, `block` to `off`, `warn` to `off`) carries RFC 058's three obligations:
  1. **a confirmation screen**, saying what changes (passwords found in a breach will be accepted, or no longer checked at
     all) and that it applies to every password set from then on, not to existing ones;
  2. **step-up immediately before**, `require_fresh_step_up`, as the other dangerous actions do;
  3. **an audit record with its `note` populated**, saying it was a weakening.
     - Measure S02's event first. If it has no `note`, or adding one changes the audit event's schema (RFC 094's
       contract: its registry, the coverage matrix, the event reference), **stop and return**, with what the change
       would be.
- **The direction is decided on the server**, from the stored mode and the submitted one, inside the same request. **It is
  never decided from anything the form sends about itself.** A request that claims to strengthen while it weakens must still
  require the confirmation and the step-up.
- Saving the mode that is already stored writes nothing, and records nothing.
