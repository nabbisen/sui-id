## §1: the navigation, generated from one list

**One typed list is the single source.** Replace the `current: Option<String>` key with an enum, for example `NavItem`, with
one variant per destination below.
- **The sidebar is rendered from that enum's list**, and each item's group comes from an exhaustive `match`. A new variant
  cannot compile without a group, and it cannot be left out of the sidebar.
- **Every page that renders the console's chrome names its item by type**, so a typo cannot compile. Shape the type so that a
  `/admin` page cannot render the console chrome without naming one.
  - The `/me` pages, shown with the console's chrome to an administrator, name no item. They belong to the account menu.
  - Choose the shape, and say why in the return.

**The groups and items, in this order** (RFC 149 §1). Labels are given in English; write all four locales (`en`, `ja`,
`zh_hans`, `zh_hant`).

| Group | Item | Pages (every URL kept) |
|---|---|---|
| **Overview** | Dashboard | `/admin` |
| **People** | Users | `/admin/users`, `/admin/users/new`, `/admin/users/{id}`, and each user's confirmation pages, including the federation unlink confirmation |
| **Applications** | Apps | `/admin/clients`, `/new`, `/{id}/edit`, and their confirmation and result pages |
| **Sign-in** | Federation providers | `/admin/federation-providers`, and its confirmation pages |
| | Sign-in settings | `/admin/settings/authentication` |
| **Security** | Signing keys | `/admin/signing-keys`, and its confirmation pages |
| | Sessions and lockout | `/admin/settings/security` |
| | Audit log | `/admin/audit` |
| **System** | General | `/admin/settings/basic` |
| | Email | `/admin/settings/email`, and its confirmation page |
| | Logs | `/admin/settings/logs` |
| | About this server | `/admin/settings/other` |

**Why these labels.** Each names what is on the page, so that no one can misread where a setting lives:
- **General**, not *Language*: `/admin/settings/basic` holds the default language, and also the issuer, the listen address,
  `cookie_secure`, the trusted proxies, and the discovery and JWKS URLs.
- **About this server**, not *Other*: the page shows the version, the schema, the storage paths and the server's time. *Other*
  names nothing.
- **Sessions and lockout** matches RFC 149 §1 and the mockup. The page also shows the security headers and CORS. Its purpose
  line (below) names them, so they are not hidden behind the label.

**The settings tabs go.** The sidebar now says which settings page is open, so the tab strip would repeat it, across groups.
Delete `settings_tabs` and `SettingsTab` if nothing else uses them. The `/me` pages keep their own tabs: they are the
account's own pages, outside RFC 149.

**Each page's heading names its item.**
- Today the seven settings pages share the `<h1>` *Settings*. Each now has its item's name as its `<h1>` and `<title>`, with
  its group's name above it in small text.
- Each settings page keeps a one-line purpose line (`page-header__lede`), saying what is on it. For *Sessions and lockout*,
  it names the headers and CORS too.
- **Exactly one `<h1>` per page.** The brand becomes text, not a heading.

**`/admin/settings` still redirects**, to *General*. `/admin/profile` still redirects as it does today. §7: no URL changes.

## §2: the layout, with JavaScript off

**Wide screens** (choose the breakpoint, and say which):
- **The sidebar** is about 248px wide (the design review's figure), following `mockups/navigation.html`, option 1:
  - the brand;
  - the six group headings, each with its items;
  - the current item marked with `aria-current="page"`;
  - **the account menu at the sidebar's foot, set apart**;
  - the version, below the account menu.
- **At 1280px of viewport, the audit log's five columns fit without horizontal scrolling** (the design review's measure).

**Narrow screens.** The sidebar folds into one **Menu** button at the top, which opens the same list, with no JavaScript.
- **The recommended shape:** render the list twice from the same function. One copy is the sidebar. The other is inside a
  `<details>` whose `<summary>` is *Menu*.
- A media query gives each copy `display: none` at the other width. **So at any width, exactly one copy is in the
  accessibility tree and the tab order.**
- **Why not one copy:** a `<details>` cannot be held open on wide screens without a script, or without a pseudo-element
  that not every supported browser has.
- If you find a single-copy shape that meets the same conditions in every browser the project supports, propose it in the
  return, with the measurement. Do not build it without the architect's agreement.

**The skip link stays first** in the page, before the navigation.

**At 375px, nothing scrolls the page horizontally.** That holds for the console and for the account chrome.

## §3: the account menu

Today's `<details>` dropdown, holding:
1. **My account**: `/me/security/overview`, as today.
2. **Language**: `/me/security/language`, the person's own language (not the server default, which is System → General).
3. **Theme**: today's three buttons, moved here from the footer.
   - Keep their labels *Light*, *Auto* and *Dark*.
   - **Do not relabel *Auto* as *System***. *System* is now a group in the sidebar, and the two would be confused.
   - **Drop their `title=` attributes.** The visible label is the name, and a `title` is a hover-only tooltip (RFC 149 §3).
   - With JavaScript off, show today's note instead of the buttons: the theme follows the device.
4. **Sign out**, separated from the rest, as a form `POST`, as today.

**Drop `role="menu"` and `role="menuitem"`.** A menu role promises arrow-key navigation, and no script provides it. Use plain
links and buttons in a list.

**Where it appears.**
- With the console's chrome (`Chrome::Console`), it sits at the sidebar's foot.
- With the account chrome (`Chrome::Account`), it sits in a slim top bar at the far end, as today.
- **Signed-out pages have no account menu, and so no theme selector.** Those are `Chrome::Bare` and `AuthShell`: sign-in,
  setup, errors and step-up. They follow the saved theme, or the device's.
- That is a deliberate change: an operator changes the theme where their other personal settings are. Name it in the
  CHANGELOG.

## §4: the footer goes; the version stays, inside the console

- **Delete the footer**: the tagline, the three self-claims and their `title=`s, and the theme toggle, which moves (§3).
- **The version is shown only with the console's chrome**, below the account menu, as `sui-id v<version>`.
- **No version on any other page.** Signed-out pages and the account chrome show none.
- **Why:**
  - The owner found the footer to be noise on every page (RFC 149's handoff, 2026-11-22).
  - The version is wanted by an administrator reporting a problem, and no one else.
  - On the sign-in page, it told any visitor which release to look up advisories for.
  - *About this server* still shows it.
- Delete the strings that only the footer used, in all four locales. `sui-id-i18n`'s `Strings` is public, so name each
  removed field in the return's API list (§7).
