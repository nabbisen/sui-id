## §1 — the DNS answer cap: 8 is wrong, 32 in total

**Measured live.** `www.googleapis.com`, Google's `jwks_uri` host, answers
with 8 A and 8 AAAA records. `runtime/resolver.rs:564` sets
`MAX_ANSWERS = 8`, and `validate_answer` (`:587`) rejects the whole
answer, so preflight fails with *"signing keys were refused"*. Every
Google sign-in fails the same way.

- Set `MAX_ANSWERS` to **32**. Derive the error message (`:551`, today a
  literal `"must be 1-8"`) from the constant, so the two can't drift.
- Nothing else in `validate_answer` changes. Every address must still pass
  `denied_by`, a mixed answer still rejects the whole answer, and one
  address is still returned. That is the security property (RFC 134, Q3).
- **Tests** (`resolver/tests.rs`, today `:239` and `:248`):
  - the over-limit test uses 33;
  - the at-limit test uses 32;
  - add **`googles_answer_shape_eight_a_and_eight_aaaa_is_accepted`**, with 16
    ordinary public addresses, 8 v4 and 8 v6. Take them from a real public
    range, not a documentation prefix, since `denied_by` refuses those;
  - add a mixed answer at 16, one private address among them, which still
    rejects the whole answer.

  **Mutation:** the cap back to 8 fails the Google-shape test.

## §2 — a log line RFC 096 forbids

RFC 096's telemetry rule: logs *"must not contain full URLs"*. The live
run logged:

```
preflight: JWKS failed … error=JWKS transport: transport error: error sending request for url (https://www.googleapis.com/oauth2/v3/certs)
```

The URL comes from `reqwest::Error`'s `Display`. Measure every place a
`reqwest::Error` reaches a log or an error string on the federation
paths: discovery, JWKS, token, and the preflight. Strip the URL there
(`reqwest::Error::without_url` exists for this). Log the phase, the host
and a closed reason instead.

**Test:** a transport failure's error string contains no `://` followed by
a path, made with a request to a port nothing listens on. **Mutation:**
drop the `without_url`, and the test fails.

## §3 — a refusal names its cause, for the administrator

**Today.** `CheckAndEnableError::Discovery` and `::Jwks`
(`http/handlers/admin/federation_providers.rs:70-71` and `:92-93`)
flatten every cause to two fixed strings:

> *"The upstream's discovery document was refused. Check the server log for
> the reason."*

An administrator without access to the server log can't act on that. The
cause is two log lines away, and they had to ask the architect to read it.

**Change.** Carry the typed cause through to the page, and say in one or two
sentences **what failed and what the administrator can do**. The causes are
closed: `DiscoveryError` (`http/discovery.rs:150`), `JwksError`
(`http/jwks.rs`), and the transport classes (DNS rejected, TLS, timeout,
unreachable). For example:
- **`OriginNotAllowed { field, origin }`**: *"Google's discovery document puts
  its token endpoint on https://oauth2.googleapis.com, which this provider's
  `allowed_origins` does not list. If you trust that origin, add it to
  `allowed_origins` and restart sui-id."*
- **DNS over the cap**: *"www.googleapis.com answered with 40 addresses;
  sui-id accepts at most 32."*
- **DNS denied**: *"www.example.com resolves to an address sui-id never
  connects to (a private or special-purpose range)."* Name the range's
  class, never the address.

**What a page may show, and what it may not.** The page may show:
- field names (`token_endpoint`, `jwks_uri`, …);
- an **origin or host that sui-id has parsed and validated**, bounded to 255
  bytes and elided beyond;
- a count;
- the provider's display name.

It must **never** show a path, a query, an upstream-supplied string
(`NotAbsolute.value`, `DuplicateMember`, `DuplicateKid`, any `InvalidIssuer`
text), a response body, or an address. RFC 096's *"browser responses …
do not echo …"* rule governs the sign-in flow's four outcomes. This is an
administrator's page, but the same caution applies to anything the
upstream controls. A cause with no safe detail still gets a sentence
saying what failed. **No refusal ends at "check the server log"**; the log
may be offered *in addition*. All three locales.

**Tests:**
- one rendered page per cause class, asserting its sentence;
- **every** variant reaches a sentence (an exhaustive match: a new variant
  fails to compile until it has one);
- no rendered refusal contains `://` followed by `/`, `?` or `#`;
- an `InvalidIssuer` carrying hostile text renders none of it.

## §4 — a destructive page states its consequence plainly

**The root, measured.** `ConfirmScreenData.impact` is rendered as
**`<p class="muted">`** (`sui-id-web/src/pages/confirm.rs:150`), on
**every** confirm page. The most important sentence on a destructive page
is styled to be skipped. The owner's two observations are this one cause:
- **The delete-provider count.** `@nabbisen`: *"The number was not easy to
  distinguish. It is very important information and should be impacted."*
  It's one digit inside a sentence (`confirm_delete_federation_provider_impact`,
  `sui-id-i18n/src/locale/en.rs:947`), and at zero it reads *"0 users will
  no longer be able to sign in"*.
- **The unlink page's sessions note** (*"Sessions already open, and tokens
  already issued to applications, stay valid"*) is a second muted paragraph,
  below the action (`pages/users.rs:553`). Asked whether he saw it, the
  owner answered: *"No, I missed it."*

**Change:**
1. **The impact is the page's lead consequence, not muted.** Render it in
   body text at full contrast, under RFC 144's tokens and type scale,
   visually tied to the action it describes. Every caller benefits; list
   them in the return (`grep "impact: Some(" sui-id-web/src`).
2. **A count is its own element.** Add a structured count to
   `ConfirmScreenData`: a number and an i18n noun, with plural forms from
   the locale and never built in Rust. Render the number as a distinct,
   prominent figure. **Zero has its own wording**: *"No user signs in
   through this provider."*, not *"0 users …"*. Apply it to every confirm
   page whose impact carries a count. Today those are deleting a federation
   provider (linked users) and rotating the signing key (active keys).
   Measure for others.
3. **The signing-key rotation page builds its count in English, in Rust**
   (`confirm.rs:485`: `"({} active key{} will become retired)"`), so a
   Japanese or Chinese administrator reads an English fragment. Point 2
   replaces it with locale strings.
4. **Unlink:** the sessions consequence, with its link to disable the
   account, joins the impact. It is part of what the action does, not a
   footnote.

**Tests:**
- each confirm page's impact is not inside `.muted`;
- the count renders in its own element;
- zero renders the zero wording, in all three locales;
- the rotation page renders no English in `ja` or `zh-Hans`;
- the unlink page's sessions sentence is inside the impact.

**Mutations:** restore `class="muted"` on the impact, and restore `"0
users …"` for zero; each fails a test.
