## §1 — R1: the refusal message claims what the provider did not say

**Today** (`crates/sui-id-i18n/src/locale/en.rs:167`, `login_fed_unverified_email`,
shown via `handlers/federation.rs:1901`):

> *"Your identity provider reports that your email address is not verified.
> Verify it with your identity provider, then try again."*

The live run reached this with a provider that sent **no email in the ID
token at all**. The provider reported nothing about verification, and
*"verify it with your identity provider"* sends the person on an errand that
cannot help. The capability keeps only `verified_email: Option<…>`
(`http/identity_capability.rs:86`), so at this point sui-id cannot tell
*absent* from *unverified*. **The message must be true in both cases.**

**Becomes**, as a guide (keep its two parts: what happened, what to do):
- en: *"Your identity provider did not send a verified email address, which
  is needed to create your account here. Contact your administrator."*
- ja: *"ID プロバイダーから確認済みのメールアドレスが届かなかったため、ここでアカウントを作成できませんでした。管理者にお問い合わせください。"*
- zh-Hans: *"身份提供方未发送已验证的电子邮箱，因此无法在此创建您的账户。请联系管理员。"*

(zh-Hant delegates to zh-Hans.) **Rename the key** to
`login_fed_no_verified_email`, so the name does not repeat the claim the
text drops. `FedErrorBucket::UnverifiedEmail` and the audit reason stay.

**Test:** the rendered login page for this bucket, in each locale, contains
the new text, and the English does not contain *"reports"* or *"Verify it"*.
**Mutation:** the old English text back; red.

## §2 — R2: the requirement is undocumented where an operator looks

Two places say provisioning *"requires `email_verified = true`"* from the
upstream, and neither says **where**:
- `docs/src/reference/configuration.md:256` (`provision_mode`);
- `docs/src/guides/operators.md:1736` (`provision_on_first_login`).

Add to each, in one or two sentences: the `email` and `email_verified`
claims must be **in the ID token**; sui-id does not read the userinfo
endpoint (RFC 096). Some providers send them only from userinfo by default;
**Duende IdentityServer** is one, unless the client includes user claims in
the ID token. Without them, every first sign-in is refused, with this
message and the audit reason `unverified_email`.

**Name no provider setting you have not checked in that provider's own
documentation.** If you name one (IdentityServer's
`AlwaysIncludeUserClaimsInIdToken`), cite the page in the return.
