# A linked federated account could be given a local password (RFC 103 T10)

> **Held outside git until the fix landed (2026-11-22)**, as
> `.github/SECURITY.md` requires; published with it. Fixed by
> [O7](0.93.0-o7-an-unlink-that-tells-the-truth-2026-11-22.md) §0, and
> disclosed under CHANGELOG *Security*.

**Found.** 2026-11-22, by the architect. It surfaced while answering the
owner's question about the account left behind by an unlink, in the M4-B
Google record run on `67f1140`.
**Status.** Fixed in `0.93.0` (O7 §0). Held outside git until then.

## The defect

RFC 103 threat **T10**: *"An external-source (LDAP or federated) account
gets a local password, bypassing the directory"*. It is controlled by
D5/D13, implemented as *"a user whose source is not local"* is refused.

RFC 096-B1 stage 7 (F04) stores a provisioned federated user with
**`source = Local`** (`sui-id/src/http/handlers/federation.rs:1393`). The
legacy writer it replaced used `Ldap`. So the T10 check no longer covers
federated users:

- **issuing:** the recovery-link eligibility checks only `source`
  (`sui-id-store/src/commands.rs:1594`), and passes a linked federated
  user;
- **completion:** D13's re-check uses the same rule;
- **sign-in:** `login_with_mfa` (`sui-id-core/src/authn/session.rs:149`)
  checks only disabled/deleted and the credential row, never the
  federation link.

The code base already names the cause: `authn/step_up.rs:382` reads the
link first, *"whatever `source` says"*, because `source` *"is not the
thing to key on"*. Step-up was fixed in that way; the recovery path was not.

**Consequence.** An administrator can issue a recovery link to a user who
is still linked to an upstream; issuing needs a fresh step-up and a second
factor, and is audited and throttled. The holder then sets a local
password, and signs in with it **without the upstream**. Revoking the
person upstream no longer removes their access.

**Not reachable without an administrator.** Forgot-password excludes any
account that has never held a password (RFC 115 D1,
`sui-id-core/src/account/forgot_password.rs:121-135`). A federated account
has none, unless a recovery link gave it one.

## The fix (to dispatch, held)

- **Eligibility:** a user with **any** `federation_link` is refused, with
  `TargetNonLocal` or a new, explicit `TargetFederated`. This applies at
  issue (U37) and at completion (D13), in the same transaction read.
- **Defence in depth:** password sign-in refuses a user with a federation
  link, as step-up already does. Decide whether that is wanted: it also
  blocks an account that has both a link and a password, which today
  cannot arise except through this defect.
- **Unlinked accounts stay eligible.** After an unlink, no upstream binds
  the account, so a local password bypasses nothing. The recovery link
  is then the intended way back in (RFC 115's activation path). O7's
  "no other way to sign in" sentence relies on this.
- **Tests:**
  - a linked federated user: refused at issue, and refused at completion
    when the link is added after issue;
  - an unlinked one: eligible;
  - password sign-in for a linked user: refused, if that part is adopted.
  - **Mutation:** drop the link check, and the first test fails.
