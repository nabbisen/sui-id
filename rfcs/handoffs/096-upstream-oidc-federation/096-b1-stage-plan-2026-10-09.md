## The stages

**Stage 0 — `ReadConn`.** The typed read-only wrapper, the per-statement
`sqlite3_stmt_readonly` interrogation, and the assertion that `rusqlite`'s
`functions`, `vtab` and `load_extension` features stay disabled. Preceded by the
read-path audit below, whose output names the call sites to convert.

**Stage 1 — migration 0046, `federation_login_attempt`.** The schema at
`:577-589` exactly: `state_sha256 UNIQUE`, `nonce_sha256`,
`browser_binding_sha256`, `pkce_verifier_sealed`, `exact_redirect_uri`,
`next_path`, the four lifecycle timestamps, `status(pending|exchanging|completed|failed)`,
`claimed_at`. Latest migration is `0045`, so this is `0046`. Migration evidence
is a `:23` closure item, so it is produced here rather than reconstructed later.

**Stage 2 — durable attempt start.** *(Correction, 2026-10-10: this read
"(F01, F02; Class P)" and that was wrong. Read from the manifest before
dispatching, F01/F02/F04 are all `exchanging -> completed` completion commands
and belong to stage 6; F03 is federated MFA submission, not nonce consumption;
F05 is terminal failure, not identity mapping. Only F04-as-Class-A was right.
**And none of the 101 registered commands creates an attempt row or performs the
`pending -> exchanging` claim**, so stage 2 and stage 3 each need a manifest row
that does not exist — G17 fails without one. The stage **order** below is
unaffected and stands as authorized; only the command mapping was wrong, and it
was the architect's error.)* Create the row; seal
the PKCE verifier with a fresh nonce and AAD binding attempt ID, provider ID,
config version and activation generation (`:586-587`); 600-second lifetime with
`expires_at <= now` expired; **wall-clock access injected and clock regression
fails closed** (`:588-589`) — 096-A stage 6b already proved what an in-function
clock read does to a boundary test.

**Stage 3 — one-time nonce consumption.** *(Not F03; see the stage 2 correction.)* Claim the attempt
`pending → exchanging` with `claimed_at`, single-use enforced by
`state_sha256 UNIQUE` plus the status transition, not by application check
alone. Then wire stage 7's `validate_nonce` against the stored `nonce_sha256`.
**This is where "the rule" becomes "genuinely one-time"** — the split `:67-68`
describes.

**Stage 4 — code exchange, and 096-A stops being dormant.** *(Correction,
2026-10-10: stages 1–3 were each told `handlers/federation.rs` was "forbidden
until stage 7". The constraint is **096-A's** — `:63-66` forbids 096-A durable
mutation and that file holds the live callback — not a stage gate. 096-B1's
purpose is the opposite (`:72-73`: "the live callback is routed through that
verification"), so **this stage edits it**, and stage 7 is the removal of the old
paths rather than the unlocking of the file. The architect's error, found before
dispatching this stage.)* Route the callback
through `validate_identity_claims`, `validate_time_claims`, `validate_nonce`,
`validate_optional_claims` and `construct_identity_capability`, supplying the
expected issuer, client ID, `created_at` and nonce digest from the attempt row.
Also the token-response envelope row the corpus left to this stage. **Every
validator gains its first production caller here**, so this stage needs the
heaviest review of the nine.

**Stage 5 — verified-identity mapping.** *(Not F05; see the stage 2 correction.)* `(provider_id, sub)` as
the sole lookup key (`:695`); `link_only` and `provision_on_first_login` per
`:699-711`, including the takeover-collision denial and that an absent or
unverified email simply denies.

**Stage 6a — the two retention items. Landed `3c76c6c`.** `:604-605`'s
24-hour purge of completed/failed/expired attempts, registered in
`runtime/gc.rs` beside the existing six, and `:600-601`'s cookie expiry on
every terminal path — the latter made structural by a `Terminal` newtype whose
only constructor removes both federation cookies, so a terminal path that
forgets them does not compile. Level B 24/24 plus A3.2 and A3.4.

**Stage 6b — `emit_must_attempt`. Landed `2c92e46`.** RFC 094 `:292-298`'s Class-B emission path,
which does not exist: `AuditClass::MustAttempt` is declared and unimplemented,
and F01, F03 and F05 all specify a post-commit Class-B event. Built here for
the reason recorded in
[`emit-must-attempt-prerequisite-decision-2026-10-11.md`](emit-must-attempt-prerequisite-decision-2026-10-11.md)
— the same shape as stage 0 building `ReadConn`. The mechanism and **one**
converted call site; the other 20 best-effort appends are M2b's.

**Stage 6c — the attempt state machine, and F05. Landed `87a52aa`.** *(Widened 2026-10-11, before
dispatching: the plan read "F05" alone, and `:597-599` turned out to require two
things of the claim that the code does not do — both from the architect's own
stage 3 and 4 dispatches.)* The claim is **split** from nonce consumption and
moves **before** the token exchange, where `:597-599` puts it; `:598`'s
**constant-time browser binding** comparison joins it, closing a limitation that
has been on the closure list since stage 4 (`browser_binding_sha256` has been
stored since stage 1 and compared against nothing); and then F05 — the guarded
`pending|exchanging -> failed` transition with its closed reason enum, wired
into every failure path, because `:601-603` requires every one of them to leave
the row reconcilable as `failed` and today none of them does, plus `:603-604`'s
error response consuming the attempt without a token exchange. No link, user,
session or last-seen mutation. The three go together because moving the claim
earlier widens the window in which a failure leaves a row `exchanging`, so
terminalization must land with it rather than after it.

**Stage 6d — F01, as Class A folded into L04. Dispatched 2026-10-15** —
[`stage6d-f01-folded-into-l04-2026-10-15.md`](stage6d-f01-folded-into-l04-2026-10-15.md).
Moved after stage 11 on 2026-10-12, with the RFC 094 amendment taken before it;
that amendment landed `93b4b3e` on 2026-10-15, so the record question is settled. The existing-link,
no-local-MFA completion: the guarded `exchanging -> completed` transition and

L04's existing `db.class_a` transaction, so the attempt completion becomes
atomic with the session it authorises and nothing about

**Stage 6e — federation failure surfacing. Landed `92b903e`; `0.80.0` cut from `7aecd98`.**
No handler or template reads the `fed_error` query parameter, so every
federation failure lands a user on an unexplained login page. A bounded map
onto a small set of user-visible messages, **not** a rendering of the internal
value — every collision-adjacent value collapses into the same message — plus
the operator guide saying plainly what `link_only` does and does not do in this
release. **This is `0.80.0`'s last precondition.** (Was stage 13; moved
2026-10-12.)

**Stage 7 — F04, the Class-A one. Landed `e9d5001`.** First federated provisioning and direct
login in one `WriteTx<AtomicAudit>` transaction: guarded attempt completion,
recheck of absent link, verified unique email and username uniqueness, a
passwordless non-admin user, exactly one provider/sub link, a `[Fed]` session,
the cap, and the sole `auth.federation.provisioned` intent event, per
`:706-711`. Federation's first use of the Class-A runner, so this stage needs
the heaviest review of the remainder. Carries three items from stage 5's
review: `L04`'s audit event's upstream `sub` attribute and the new event's own,
`operators.md`'s `provision_on_first_login` sentence becoming true, and the
duplicate `federation_link::find_by_sub` per callback collapsed.

**Stage 8 — migration `0047`. Dispatched 2026-10-13: `federation_mfa_pending` and
`federation_webauthn_ceremony`.** Schema only, `:728-738` exactly. Migration
evidence is a `:23` closure item, so it is produced here rather than

**Stage 9 — F02. Landed `f5b4035`**, Level B 24/24, CI run `38491673983`,
after one fix round. Existing link, local MFA required:
guarded attempt completion plus exactly one pending row sealed as `Fed`

**Stage 10a — the `FederatedMfaVerifier`, its binding gate and its
candidates. Dispatched 2026-10-14; landed the same day after one fix
round.** The binding-before-anything entry point
and the sealed candidates (`:752-762`), TOTP and recovery proof checking, and

construct an F03 input or touch the row". Its first question is where the

The verifier and the candidates live in `sui-id-core`, on the measured
ground that recovery-code matching needs `password::verify_password` and
cannot move down as cheaply as TOTP arithmetic. The first package was
returned on three blocking items, the first of which was that migration
0047's own CHECK forces `continuation_sealed IS NULL` on a terminal row
while the row type held a `Vec<u8>`, so `find_by_id` could not read one —
measured, not argued. All three are fixed.

**That placement choice gives stage 10b a question the plan did not have
before, and it belongs to the architect and to `@nabbisen`, not to the
implementation role.** `sui-id-store` cannot name a `sui-id-core` type, so F03 cannot take
a candidate as a parameter: it will be a `pub` store command taking plain
primitives, and `sui-id` handlers already call `sui_id_store::commands::*`

that the second half of "handlers can neither" is held by a test rather than
by the type system. **Stage 10b is still not dispatched**, for a reason the

## Controlled removal of `target/`

Approved on 2026-10-09 to leave `target/` (388 GB) until the release boundary,
with removal **controlled** rather than at my discretion. The control:

- **Trigger:** the 096-B1 release boundary, when a cold rebuild costs nothing
  extra because a full matrix runs anyway.
- **Procedure:** measure `du -sh target` and `df -h /home` first, ask for a
  go-ahead at that moment, remove only `target/` and nothing else beside it,
  then re-measure and report both numbers.
- **Not a standing licence.** No removal before the trigger, and no removal at
  the trigger without asking. `/home` is btrfs, so reclaimed space and `du`'s
  figure diverge — clearing 187 GB of gate clones on 2026-10-09 returned about
  59 GB, and the report will give the measured number, not the apparent one.
