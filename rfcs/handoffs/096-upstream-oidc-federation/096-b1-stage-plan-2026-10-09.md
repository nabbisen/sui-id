## The stages

**Stage 0 — `ReadConn`.** The typed read-only wrapper, the per-statement
`sqlite3_stmt_readonly` interrogation, and the assertion that `rusqlite`'s
`functions`, `vtab` and `load_extension` features stay disabled. Preceded by the
read-path audit below, whose output names the call sites to convert.

**Stage 1 — migration 0046, `federation_login_attempt`.** The schema at
`:577-589` exactly: `state_sha256 UNIQUE`, `nonce_sha256`,
`browser_binding_sha256`, `pkce_verifier_sealed`, `exact_redirect_uri`,
`next_path`, the four lifecycle timestamps, `status(pending|exchanging|completed|failed)`,
`claimed_at`. Latest migration is `0045`, so this is `0046`. Migration evidence
is a `:23` closure item, so it is produced here rather than reconstructed later.

**Stage 2 — durable attempt start (F01, F02; Class P).** Create the row; seal
the PKCE verifier with a fresh nonce and AAD binding attempt ID, provider ID,
config version and activation generation (`:586-587`); 600-second lifetime with
`expires_at <= now` expired; **wall-clock access injected and clock regression
fails closed** (`:588-589`) — 096-A stage 6b already proved what an in-function
clock read does to a boundary test.

**Stage 3 — one-time nonce consumption (F03; Class P).** Claim the attempt
`pending → exchanging` with `claimed_at`, single-use enforced by
`state_sha256 UNIQUE` plus the status transition, not by application check
alone. Then wire stage 7's `validate_nonce` against the stored `nonce_sha256`.
**This is where "the rule" becomes "genuinely one-time"** — the split `:67-68`
describes.

**Stage 4 — code exchange, and 096-A stops being dormant.** Route the callback
through `validate_identity_claims`, `validate_time_claims`, `validate_nonce`,
`validate_optional_claims` and `construct_identity_capability`, supplying the
expected issuer, client ID, `created_at` and nonce digest from the attempt row.
Also the token-response envelope row the corpus left to this stage. **Every
validator gains its first production caller here**, so this stage needs the
heaviest review of the nine.

**Stage 5 — verified-identity mapping (F05; Class P).** `(provider_id, sub)` as
the sole lookup key (`:695`); `link_only` and `provision_on_first_login` per
`:699-711`, including the takeover-collision denial and that an absent or
unverified email simply denies.

**Stage 6 — session establishment (F04; Class A).** The one Class-A command of
the six, on the `WriteTx<AtomicAudit>` runner: link, `[Fed]` session and cap,
and the `auth.federation.provisioned` commit in **one** transaction, per
`:706-711`.

**Stage 7 — remove the shipped defect's two paths.** The trust-on-TLS decode
(`decode_id_token_claims`, reached at `handlers/federation.rs:404`) and the
cookie-replay path (sealed state in a cookie,
`handlers/federation.rs:223-224`). **Also the two
discovery items 096-A could not wire** — the configured-value cross-checks and
`validate_discovery_bytes`'s tightened bounds — because both need
`fetch_discovery`, which 096-A was forbidden to touch and this stage is not.

**Stage 8 — representative live-integration evidence.** One public upstream,
your test credentials, outside CI, secrets absent from artifacts
(`:1021`). A `:23` closure item. **A live happy path is not a substitute
for hostile-provider evidence** (`:1027`) — 096-A's corpus carries that, and
this stage does not re-prove it.

## Two tasks beside the stages

**The read-path audit** — authorized as its own task. Does anything reached from
a read-shaped call site write? Scope is every `with_conn` / `with_conn_sync`
call site in the workspace. **Sequenced before stage 0**, because its output is
what stage 0 converts. Only the ordering is mine; it remains a separate task.

**RFC 094's prose-versus-criteria reconciliation** — a **proposal, not a

RFC. Amending RFC 094 is yours to authorize. I recommend it after 096-B1 stage
0, when the concrete example is fresh and the control exists.

## Controlled removal of `target/`

Approved on 2026-10-09 to leave `target/` (388 GB) until the release boundary,
with removal **controlled** rather than at my discretion. The control:

- **Trigger:** the 096-B1 release boundary, when a cold rebuild costs nothing
  extra because a full matrix runs anyway.
- **Procedure:** measure `du -sh target` and `df -h /home` first, ask for a
  go-ahead at that moment, remove only `target/` and nothing else beside it,
  then re-measure and report both numbers.
- **Not a standing licence.** No removal before the trigger, and no removal at
  the trigger without asking. `/home` is btrfs, so reclaimed space and `du`'s
  figure diverge — clearing 187 GB of gate clones on 2026-10-09 returned about
  59 GB, and the report will give the measured number, not the apparent one.

The stage order above is authorized. Dispatches go out **one at a time**, which
is how all fifteen of 096-A's stages ran and is what keeps each package
reviewable:

   schedule, but held until the audit returns rather than run beside it. One
   open dispatch at a time.
