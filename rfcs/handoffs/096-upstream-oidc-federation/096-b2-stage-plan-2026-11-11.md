## 2 — four gaps the accepted design leaves open: yours to settle

RFC 096 is Accepted, and these change its text, so each is an amendment.
**The architect wrote them and is not independent of them**: precedent
(2026-10-14) is that you approve such an amendment as the approver.

**A1 — C19, "administrative link create": recommended *not* to build it.**
RFC 096 says only *"link create/delete"* (`:133`), and C19 has no design
anywhere: the contract reserves it with no event. Today a link comes into
being **only through a verified upstream sign-in**: F04 provisioning, or
linking at first login, where the upstream proves control of the identity.
An administrator asserting a link *without* that proof could bind any upstream
identity to any local account. That is a takeover path the current model
deliberately does not have. **Recommended:** RFC 096-B2 drops C19, and links
stay proof-based. A real need for administrative linking would get its own
RFC, which defines the proof.

**A2 — a provider removed from configuration: recommended *disable, keep
links*.** The design is silent. Today removal fails closed at the callback
(`ConfigDrift`, `federation.rs:1122-1139`), but the login screen still offers
the provider. **Recommended:** at startup, a provider whose block is gone is
disabled, through a C23-shaped transaction with its own event, and keeps its
links. It then drops off the login screen. Nothing is deleted implicitly,
because deletion destroys links (§1, cascade).

**A3 — C18 delete: recommended *admin UI only, with fresh step-up, and the
cost stated*.** Deletion ends federated sign-in for every linked user, through
the cascade. **Recommended:** C18 is reachable only from the admin UI, behind
`require_fresh_step_up`. The confirmation states **how many users' federated
sign-in it ends**, and the event records that count. The provider must also be
disabled first, so a delete is never the first action against a live provider.

> **A4 below is superseded (2026-11-11).** The accepted design already defines
> trust policy as the policy digest's nine fields (RFC 096 `:424-435`), and C24
> folds into C23. See
> [`096-b2-a4-correction-2026-11-11.md`](096-b2-a4-correction-2026-11-11.md).
> The text is kept as it was accepted.

**A4 — which configuration fields are "trust policy" for C23: recommended
classification.** RFC 094 says C23 replaces *"the complete typed trust
policy"* (`:547-549`) but does not list the fields.
**Recommended:**
- **trust**: `issuer`, `client_id`, the client secret, `scopes`,
  `provision_mode`. A change goes through C23 and disables the provider until
  it is re-enabled.
- **not trust**: `display_name`. It is updated without disabling.
- **`allowed_origins`** keeps RFC 134's own ruling (C24, no disable).

`scopes` and `provision_mode` are classed as trust because they change what
the upstream asserts and what sui-id does with it.

## 4 — sizing, honestly

096-B1 was planned in nine stages and took fifteen. **This plan is seven, and
should be expected to grow the same way**: S4 and S5 each carry enough
surface to split. The cycle has no window, and scope is never cut to hold a
date (the 2026-07-16 rule).

## 6 — why S2 split (added 2026-11-11, after S1)

Measuring for S2 against the corrected A4 found that **S1's schema stores
only part of the trust policy**. Both this plan's S1 row and the S1 dispatch
left it out, and both are the architect's. RFC 096 `:1016` says the migration
adds *"typed/versioned provider trust fields"*, and `architecture.md` `:239`
says *"provider policy"*. Of the digest's nine fields:

| Field | Durable today | Source |
|---|---|---|
| issuer, client ID, scopes, provision mode | yes | `0037` |
| sealed client secret | yes | `0037`, `client_secret_enc` |
| endpoint origins | yes | `0045`, `allowed_origins` |
| **ID-token algorithms** | **no**: the config file only, read by slug at the callback | `federation.rs:1084-1108` |
| token-auth method | derived, not stored: a secret means `client_secret_basic`, otherwise `none` | `federation.rs:949-954` |
| HTTPS ports | derived, not stored: each origin carries its own port, and an endpoint must match an origin exactly | `discovery.rs:476-501` |

So **changing `id_token_algs` in the config file changes what an enabled
provider accepts, with no review**. That is exactly what the corrected A4
forbids. The same measurement found three more gaps:
- **C16 creates a provider with `enabled` copied from the config file**
  (`startup.rs:421`), and the login path checks only `enabled`
  (`federation.rs:439, :742`). RFC 096 `:1034-1035` makes an unvalidated row
  runtime-ineligible.
- **`ProvisionMode::parse` maps any unrecognised value to `link_only`**
  (`models.rs:162-166`). RFC 096 `:363` says *"Exactly"* those two values.
- **S1's upgrade warning names only the slug.** `architecture.md` `:306-307`
  also asks for the internal ID, whether a link exists, and the missing policy
  fields.

C23 needs a complete stored policy to compare against. So S2a makes the policy
durable and typed first, and S2b builds C23 on it.

**The two derived fields are the architect's reading, not an amendment.**
RFC 096's table gives each field's rules, not where its value comes from.
Deriving the method from whether a secret is present, and the ports from the
origins, meets every rule the table states. A separate `https_ports` setting
would be a second knob that enforces nothing the origin set does not already
enforce, and an operator could misread it.

**Not in S2a: the issuer's host rule** (RFC 096 `:355`: no IP literal and no
reserved name). Enforcing it breaks every e2e test that mocks its upstream at
`https://127.0.0.1:PORT`, the cost `discovery.rs:81-115` already recorded once.
S2a measures that cost, and the rule gets its own stage, planned from those
numbers. **096-B2 does not close without it.** S2a's package counted 41 tests
in 8 files. The review's count of files using the IP-literal mock is 13 files
and 66 tests. That stage starts with a per-test count.
