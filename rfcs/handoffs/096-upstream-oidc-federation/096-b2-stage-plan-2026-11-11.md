## 2 — four gaps the accepted design leaves open: yours to settle

RFC 096 is Accepted, and these change its text, so each is an amendment.
**The architect wrote them and is not independent of them**: precedent
(2026-10-14) is that you approve such an amendment as the approver.

**A1 — C19, "administrative link create": recommended *not* to build it.**
RFC 096 says only *"link create/delete"* (`:133`), and C19 has no design
anywhere: the contract reserves it with no event. Today a link comes into
being **only through a verified upstream sign-in**: F04 provisioning, or
linking at first login, where the upstream proves control of the identity.
An administrator asserting a link *without* that proof could bind any upstream
identity to any local account. That is a takeover path the current model
deliberately does not have. **Recommended:** RFC 096-B2 drops C19, and links
stay proof-based. A real need for administrative linking would get its own
RFC, which defines the proof.

**A2 — a provider removed from configuration: recommended *disable, keep
links*.** The design is silent. Today removal fails closed at the callback
(`ConfigDrift`, `federation.rs:1122-1139`), but the login screen still offers
the provider. **Recommended:** at startup, a provider whose block is gone is
disabled, through a C23-shaped transaction with its own event, and keeps its
links. It then drops off the login screen. Nothing is deleted implicitly,
because deletion destroys links (§1, cascade).

**A3 — C18 delete: recommended *admin UI only, with fresh step-up, and the
cost stated*.** Deletion ends federated sign-in for every linked user, through
the cascade. **Recommended:** C18 is reachable only from the admin UI, behind
`require_fresh_step_up`. The confirmation states **how many users' federated
sign-in it ends**, and the event records that count. The provider must also be
disabled first, so a delete is never the first action against a live provider.

**A4 — which configuration fields are "trust policy" for C23: recommended
classification.** RFC 094 says C23 replaces *"the complete typed trust
policy"* (`:547-549`) but does not list the fields.
**Recommended:**
- **trust**: `issuer`, `client_id`, the client secret, `scopes`,
  `provision_mode`. A change goes through C23 and disables the provider until
  it is re-enabled.
- **not trust**: `display_name`. It is updated without disabling.
- **`allowed_origins`** keeps RFC 134's own ruling (C24, no disable).

`scopes` and `provision_mode` are classed as trust because they change what
the upstream asserts and what sui-id does with it.

## 3 — the stages

Every stage carries its contract rows (`write-commands.toml`,
`write-authority.toml`, the registry, `audit-coverage-matrix.md`), and G23 stays
green. Every Class-A command gets **rollback evidence through the failure
injector**, which is 096-B2's closure clause (RFC 096 `:45`). And every
admin-facing handler gets an **e2e assertion on its audit record**, not only
on its value.

## 4 — sizing, honestly

096-B1 was planned in nine stages and took fifteen. **This plan is seven, and
should be expected to grow the same way**: S4 and S5 each carry enough
surface to split. The cycle has no window, and scope is never cut to hold a
date (the 2026-07-16 rule).
