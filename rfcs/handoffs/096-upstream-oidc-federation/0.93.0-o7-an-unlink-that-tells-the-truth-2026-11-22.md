## §0 — first: a linked federated account never receives a local password

The held finding has the measurement:
- the recovery-link eligibility (`sui-id-store/src/commands.rs:1594`)
  checks only `source`;
- a federated user is stored with `source = Local`
  (`handlers/federation.rs:1393`);
- password sign-in never looks at the federation link
  (`sui-id-core/src/authn/session.rs:149`).

So a user still linked to an upstream can be given a local password, and
use it without the upstream (RFC 103 T10).

- **Eligibility, at issue (U37) and at completion (D13), in the same
  transaction read:** a user with **any** `federation_link` is refused,
  with an explicit `TargetFederated` (add the variant, its page text in
  three locales, and its HTTP status beside `TargetNonLocal`). Read the
  link, as `authn/step_up.rs:388` does, **whatever `source` says**.
- **Password sign-in refuses a user with a federation link**, as step-up
  already does. Today no such user can hold a password except through
  this defect, so the refusal also covers anything this defect already
  produced.
- **An unlinked account stays eligible**: no upstream binds it any more,
  so a local password bypasses nothing. §2's "no other way in" case
  depends on it.
- **Tests:**
  - linked: refused at issue;
  - linked after issue: refused at completion;
  - unlinked: eligible, and completes;
  - linked with a password row (constructed directly): password sign-in
    refused.

  **Mutations:** drop each check in turn; each one's test fails.
- **CHANGELOG:** nothing until the architect discloses it at landing.
  Then a *Security* entry, which the architect writes.

**Baseline.** The tip of `main` when you start (O6 landed as `67f1140`).
**Record `git log -1`.**

## §1 — what the page must know, measured on `67f1140`

`users_unlink_federation_confirm_get`
(`sui-id/src/http/handlers/admin/users.rs:858`) builds
`ConfirmUnlinkFederationData` (`sui-id-web/src/pages/users.rs:489`) from
the user and the provider alone. The same data is built again on a
refused POST (`users.rs:947`). Neither knows whether the user has any
**other way to sign in**. A user still has one after the unlink if any of
these holds:

1. **a password**: a `credentials` row for the user;
2. **a passkey**: a `user_webauthn_credentials` row. A passkey signs in by
   itself; the login page has "Sign in with passkey"
   (`login_passkey_primary`);
3. **another federation link**: a `federation_link` row for another
   provider;
4. **a directory identity**: `source` not local (an LDAP user signs in
   through the directory).

Compute this **once, in the store**, as one read-only function. For
example: `users::other_sign_in_methods(user_id, except_provider) ->
SignInMethods { password, passkeys, other_links, directory }`. The page
needs no other logic. Measure whether the store already has pieces of
this (credential presence, passkey count, link listing) and reuse them.

## §2 — what the page says

- **The user keeps at least one way in:** keep the impact as today, but
  **name what remains**, so the administrator doesn't have to take it on
  trust. For example: *"…their account remains, and they can still sign
  in with their password and a passkey."* All three locales, with the
  method list built from locale strings, never in Rust.
- **None remains:** say so plainly, in the impact, at full contrast (O6's
  `confirm-impact`):

  > *"{user} has no other way to sign in. After this, they cannot sign in
  > at all. To give them access again, issue a recovery link from their
  > page."*

  Then **offer the follow-up actions** (the third decision above), each a link
  to its own existing confirm page. Nothing happens automatically:
  - **Disable this user**: ends open sessions and the tokens already
    issued to applications;
  - **Delete this user**: removes the account and its personal data;
  - **Issue a recovery link**: gives them access again, with a password
    they choose.

  Each states its consequence in a few words, so the administrator
  chooses knowingly. Link to the existing pages; don't add new POSTs.

  **Measured:** a federated user is stored with `source = Local`
  (`handlers/federation.rs:1393`), and the recovery link refuses only a
  non-local source (`sui-id-store/src/commands.rs:1594`). So a recovery
  link is available for this user. State that only if it stays true:
  - a test pins that a federation-provisioned user is eligible for a
    recovery link;
  - if the eligibility rule ever excludes such a user, the sentence must
    change with it.
- **The open-sessions sentence** O6 placed in the impact stays as it is.
- The badge, the button and the reversibility note are unchanged.

## §3 — tests

**Pages:**
- **password only**, **passkey only**, **another link only** and
  **directory**: each renders the "can still sign in with …" form,
  naming exactly what remains;
- **none**: renders the "no other way to sign in" sentence and the link to
  the user's page, inside `confirm-impact`. The old "their other sign-in
  methods remain" does not appear;
- all three locales for the "none" case, and no English left in `ja` or
  `zh-Hans`;
- **the refused POST re-render** (`users.rs:947`) carries the same
  sentence as the GET: a test that refuses the POST, for example on a
  stale CSRF token, and checks it.

**The store function:**
- each method's presence and absence;
- `except_provider` really excludes the link being removed: a user whose
  *only* link is this provider has `other_links == 0`.

**Eligibility:** a user created by
`commands::provision_federated_user` (`sui-id-store/src/commands.rs:2441`)
passes the recovery-link precondition, so the sentence's promise holds.

**Mutations, each run and reverted, each caught:**
- the page always renders the "remain" form;
- `except_provider` ignored;
- the recovery-link rule refusing `Local` federated users.
