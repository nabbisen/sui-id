## §0 — what is there today, measured on `8d8a81f`

- **One reader:** `handlers::password_min_len` (`crates/sui-id/src/http/handlers.rs:974`),
  which returns `app.security_level().password_min_len()`: 12, or 8 in
  dev mode. Two enforcing callers:
  - the reset completion (`handlers/forgot_password.rs:216`). An
    administrator's recovery link lands on the same completion;
  - the self-service change (`handlers/me_security/password.rs:122`).
- **Two other uses**, which stay as they are: setup's first administrator
  (`sui-id-core/src/setup.rs:153`, `SecurityLevel::Standard`, 12) and dev
  mode's seeded users (`runtime/dev_mode.rs:458`, 8).
- **One display:** the *Authentication* tab (`handlers/settings.rs:238`),
  read-only.
- **The hints state 12 as a literal**, in every locale:
  `reset_password_new_hint`, `password_change_new_hint` and
  `setup_admin_password_hint` (`"12 characters or more"`, `"12 文字以上"`, …).
  **This is already false in dev mode** (8), and would be false for every
  user the moment an administrator raised the minimum.
- **The refusal is English only.** `check_password_policy`
  (`sui-id-core/src/authn/password.rs:121`) returns
  `BadRequest("password must be at least {min_len} characters long")`,
  and `friendly` (`forgot_password.rs:289`) shows that string as-is, in a
  Japanese page too.
- **The model command is S03**, `change_idle_session_timeout`
  (`sui-id-store/src/commands.rs:5407`). **Its HTTP refusal is not a
  model.** An out-of-range value gets an error page reading
  `idle_session_timeout_secs out of range` (`handlers/settings.rs:187`).
- **The next free command id is S11.** The newest migration is 0054.
- **The tab has a `GET` route only** (`router.rs:310`). The save needs a
  `POST`, for example `/admin/settings/authentication/password-min-len`,
  behind `CurrentAdmin` and the CSRF check, as S03's is.

## §1 — the setting, the floor, and the command

- **Migration `0055`:** `server_settings.password_min_len INTEGER NOT NULL
  DEFAULT 12 CHECK (password_min_len BETWEEN 12 AND 128)`. An upgrade
  changes nothing. The `CHECK` is the store's half of the floor: a direct
  `UPDATE … = 11` fails.
- **Two named constants**, `PASSWORD_MIN_LEN_FLOOR = 12` and
  `PASSWORD_MIN_LEN_CEILING = 128`, in one place. The command, the HTTP
  handler, the page's `min`/`max` attributes and every sentence that
  states the range **derive from them**. The migration's literals cannot,
  so a store test asserts that the `CHECK` refuses `FLOOR - 1` and
  `CEILING + 1` and accepts both ends.
- **S11, `settings.password_min_len.changed`**, Class A, in S03's shape.
  - The audit record carries `old` and `new`.
  - It refuses a value outside the range **before** the transaction, so
    the floor holds even if the `CHECK` were missing.
  - Register it everywhere S03 is: `registry.rs`,
    `contracts/write-commands.toml`, `contracts/audit-coverage-matrix.md`
    and `docs/src/reference/audit-events.md`.
- **Submitting the same value:** do what S03 does, and say in the return
  what that is.

## §2 — every new password meets it

- **`handlers::password_min_len` reads the setting.**
  - In dev mode it returns 8, as now (RFC 151 §3).
  - Otherwise it returns `server_settings.password_min_len`.
  - **A read failure refuses the password change.** It does not fall back
    to 12: 12 is weaker than a raised minimum, and a fallback would
    quietly lower it.
- **Nothing else enforces a minimum** except setup (`Standard`, 12) and
  dev mode's seeding (8). The *Authentication* tab displays the value that
  function returns, not `security_level()`'s.
- **Existing passwords are not checked** (RFC 151 §3). Sign-in never
  reads the minimum.

## §3 — what a user and an administrator read

The value changes at run time now, so **every sentence that states it
takes it as an argument**. No translation may write a number.

1. **The hints** on the reset page and the self-service change page:
   *"At least {n} characters."*, and on the change page, *"At least {n}
   characters. A long random passphrase is safer than a short complicated
   one."* `n` is the value `handlers::password_min_len` returns for that
   request, so it is 8 in dev mode and 16 after a raise. Setup's hint
   takes `n` from the floor constant.
2. **The refusal** is in the user's language, and names the same `n`:
   *"The password must be at least {n} characters."* Replace the English
   `BadRequest` string with something the handler can localize; a typed
   error is one way. Do the same for the 256-character ceiling's refusal,
   which is the same kind of sentence.
3. **The *Authentication* tab.** For an administrator, the *Minimum
   length* row becomes a number field (`min` and `max` from the
   constants), with a save button. For an auditor it stays a static row
   (`can_write`, as now). Under the field, always shown:
   *"Applies to every new password: a reset, a change, a recovery link.
   Existing passwords keep working, and meet the new minimum at their next
   change. It cannot be set below {floor}."*
   - In dev mode, add a line saying that dev mode uses 8, whatever this
     says.
   - **A refused save re-renders the tab** with a plain flash, *"The
     minimum must be between {floor} and {ceiling} characters."* It is
     never an error page, and never a raw field name. That includes a
     value that is not a number: take the form value as text and parse it,
     so axum's 422 never reaches the administrator.
   - A successful save returns to the tab, which shows the new value.
