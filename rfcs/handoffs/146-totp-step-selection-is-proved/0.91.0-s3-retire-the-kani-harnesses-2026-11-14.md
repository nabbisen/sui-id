## Why

`crates/sui-id-core/src/identity/authz.rs:186-283` holds five Kani harnesses
(RFC 086, Pilot K), under `#[cfg(kani)]`.
- **No workflow, script or gate runs them.**
- They call `kani::any()` for `Role` and `Action` (`:205-206`), which needs a
  `kani::Arbitrary` impl that neither type has (`authz.rs:36`;
  `sui-id-store/src/models.rs:18`). So **they probably do not even compile
  under Kani**.

The properties they claim, P1–P5, are already checked by
`crates/sui-id-core/src/identity/authz/tests.rs`, in every CI run, over
`all_actions()` × `all_roles()`.

**The gap is the lists.** `all_actions()` (`tests.rs:27`) and `all_roles()`
(`tests.rs:68`) are hand-kept. Add an `Action` variant and forget the list,
and every P1–P5 test still passes, without checking the new variant.

## A — remove the harnesses

1. Delete `authz.rs:186-283`: the doc comment `/// Kani verification
   harnesses (RFC 086, Pilot K).` through the closing `}` of `mod
   kani_proofs`. Leave one blank line before `#[cfg(test)]`.
2. Delete `Cargo.toml:210`: `unexpected_cfgs = { level = "warn", check-cfg =
   ['cfg(kani)'] }`. After step 1, nothing in the workspace uses `cfg(kani)`.
   Check that with `git grep -n 'cfg(kani)'` and quote the empty result.
3. **Do not edit** `rfcs/done/082-*`, `rfcs/done/086-*`,
   `rfcs/accepted/146-*`, the old CHANGELOG entries, or
   `docs/security-assurance-audit-v0.63.1.md`. Each is a record of its own
   time.

## B — make each list fail when a variant is missing from it

In `authz/tests.rs`, beside each list, one function with an exhaustive
`match` and **no wildcard arm**. It gives each value a unique index, with a
`const` count:

```rust
/// Every `Action` value, numbered. No wildcard arm, so a new variant fails to
/// compile here. Give it the next index, raise ACTION_VALUES, and add it to
/// `all_actions()` — a variant with a `bool` is two values.
const ACTION_VALUES: usize = 23;
fn action_index(a: Action) -> usize {
    use Action::*;
    match a {
        AdminReadUsers => 0,
        // … one arm per value, both `bool`s spelled out:
        AdminChangeUserRole { target_is_last_admin: false } => 13,
        AdminChangeUserRole { target_is_last_admin: true } => 14,
        // …
    }
}
```

Then one test per list: `all_actions()` maps onto `0..ACTION_VALUES` exactly.
That means every index is below the count, no index repeats, and the list's
length equals the count. Do the same for `Role`: `ROLE_VALUES = 3`,
`role_index`, `all_roles()`.

Before you write the counts, count the values in `authz.rs` yourself (23 and
3 on `3fd2281`). If either differs, stop and say so.

**Mutations, each run and recorded in the return with its failing output:**
1. delete one entry from `all_actions()`, and the new test fails;
2. add a variant to `Action` in a scratch copy, and the build fails at
   `action_index`. Name the error;
3. the same as 1, for `all_roles()`.

Revert each mutation, and say so.
