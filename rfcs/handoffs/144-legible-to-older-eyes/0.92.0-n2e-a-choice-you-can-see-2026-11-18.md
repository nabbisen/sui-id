## §1 — a chosen option is visible

**Measured, and it is not what it first looked like.** Every radio is already
inside its `<label>`, so clicking the label text checks it. The architect sent
**real pointer clicks** (Chromium, DevTools `Input.dispatchMouseEvent`) to the
label text on both wizard pages: the language name, the HIBP option's title
and its description. Every one checked its radio. **What fails is seeing it.**
Nothing styles a chosen option. A selected HIBP card looks exactly like the
others, and the only change is the browser's default 13×13 px radio dot
(rendered: `.git-exclude/tmp/walk-setup/hibp-block.png`). A click that changes
nothing visible reads as a click that did nothing.

**The three groups:**

| Page | Label | Where |
|---|---|---|
| Setup → language | `label.row-gap2-center-clickable` | `pages/setup/lang.rs:30`, `:35` |
| Setup → password security (HIBP) | `label.card.clickable-block` | `pages/setup/hibp.rs:30`, `:38`, `:46` |
| *My account* → language | `label.row.row-gap2-center` | `pages/me_security/language.rs:50-69` |

**The fix, CSS only, no script:**
- a label holding a checked radio (`:has(input[type="radio"]:checked)`) gets a
  `--border-accent` border and an `--accent-subtle` background; its text
  keeps `--fg-default`, which N2a's gate already holds at 7:1 on that tint;
- radios are drawn larger, `1.25rem`, in `accent-color: var(--accent-default)`;
- each of the three labels is itself at least `2.75rem` tall, because **the
  label is the target**, not the radio inside it;
- under `prefers-contrast: more`, the chosen label's border is drawn solid
  and thicker (RFC 144's rule 5).

**The 44 px gate** (`tokens/tests.rs`, `standalone_controls_reach_44px`) names
`input`, so a `1.25rem` radio would fail it. **Put radios on its named list,
with the reason** (the label is the target), as `.link-button` is, and **add
the assertion that replaces it**: each of the three label rules sets a
`min-height` of at least `2.75rem`.

**Tests:** `components_css()` holds a `:has(…:checked)` rule for each of the
three label classes; the contrast gate passes with the new pairs.
**Mutation:** remove the setup HIBP card's rule; red.

## §2 — a password match you can see, safely

**Where:** the three forms with a confirmation field, all of them:
`pages/setup/admin.rs:45`, `pages/auth.rs:362` (change password) and
`pages/auth.rs:544` (password reset).

**One static script, `crates/sui-id/static/password-match.js`.** Files there
are embedded and served at `/static/…` automatically (`http/assets.rs:11`).
- The confirmation input says which field it confirms, for example
  `data-confirms="password"`, and names its status element with
  `aria-describedby`. **The script reads only those attributes**: no page
  knowledge, one script for all three forms.
- **The status element is rendered by the server**, holding both messages
  in the page's language as `data-` attributes, and `hidden`. The script
  only switches which text shows. It holds no strings of its own, so every
  locale is right.
- On each `input` event in either field: if the confirmation is empty, the
  status stays hidden. Otherwise it shows *"The passwords match."* or
  *"The passwords do not match yet."*, in an `aria-live="polite"` element.
  The match state is also shown by a word, not colour alone (RFC 144's
  rule 2).

**Why this is safe, each point to be kept:**
- the comparison happens in the page; **nothing new is sent, stored or
  logged**, and no password text is written anywhere, not into the DOM, a
  `data-` attribute, the console or storage;
- loaded as a same-origin file under the existing `script-src 'self'`, with no
  inline script and no third-party code;
- it reveals only match or not, which the person typing already knows;
- **the server's own check stays** (`handlers/setup.rs:209`, and the
  equivalents for the other two forms). Without JavaScript, every form
  behaves exactly as today.

**Strings**, new, in en, ja and zh-Hans (zh-Hant delegates):
`password_match_yes`, *"The passwords match."*; `password_match_not_yet`,
*"The passwords do not match yet."*

**Tests:**
- each of the three pages loads `/static/password-match.js`, has the status
  element with both strings and `hidden`, and the confirmation input names
  it;
- e2e: `GET /static/password-match.js` is 200 with a JavaScript content type,
  and the page's CSP still holds `script-src 'self'`;
- a scan of the script that fails if it contains `fetch`, `XMLHttpRequest`,
  `sendBeacon`, `localStorage`, `sessionStorage`, `console.`, `innerHTML` or
  `.value =`. **Mutation:** add a `console.log`; red.
