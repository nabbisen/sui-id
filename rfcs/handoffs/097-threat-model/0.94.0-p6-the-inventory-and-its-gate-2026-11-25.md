## §1 — the contract: `contracts/threat-model.toml`

`schema_version = 1`, in the method's §2 shape. **Stage 1 fills `[[actor]]`,
`[[asset]]` and `[[boundary]]` only.** Controls and residuals are stage 2
and stage 4. The gate checks them already (§2), on fixtures.

**One field the method's example does not show.** Every boundary carries
`status = "inventoried"` or `"analysed"`. It is the architect's reading
of the stage split, and the review of this stage may change it.
- The method's gate requires every boundary to have a control and a
  filled STRIDE row. That cannot hold in stage 1.
- So the gate requires them only of an `analysed` boundary, and **lists
  every `inventoried` one in its summary**, as it lists pending residuals.
- Stage 2 moves boundaries to `analysed`, one at a time. Stage 5 adds the
  rule that none is left `inventoried`.

**What the inventory must contain**, at least:
- **The ten boundaries of the checklist's §2**, plus the **database
  writer** (S2's boundary, in the method's own example) and the
  **master-key** files. The master-key boundary covers `<key>`,
  `<key>.next`, `<key>.pre-rotation`, `<key>.rotation-lock`, the journal,
  and the `master_key_rotation` table. Its owner is RFC 100.
- **Every boundary's `owner`** is the RFC that owns its controls. Find it
  by grepping `rfcs/`, not from memory. A boundary with no identifiable
  owner is a **stop-and-return** (handoff).
- **Actors**, measured from the code. That means the roles (administrator
  and auditor, and the user), the unauthenticated visitor, a relying
  party, a dynamic-registration client, each upstream (OIDC provider,
  LDAP, SMTP, HIBP), the metrics scraper, the host operator who runs the
  CLI, and a database writer.
- **Assets**, each with a `classification` and a `stores` list naming where
  it lives (a table, or a file such as `file:<key_file>`). At least:
  - the master key and the kept backup key;
  - the signing keys;
  - password hashes, TOTP secrets, passkeys and recovery codes;
  - sessions and refresh tokens;
  - client secrets, registration tokens and recovery links;
  - the federation client secret, the SMTP password and the LDAP bind
    password;
  - the metrics token;
  - the audit chain;
  - personal data.

## §2 — the gate: `scripts/check-threat-model.py`, lane **G24**

G24 is the next free lane. G17 is retired, so don't reuse it. Check the
method's §2 and §3 rules: ids, references, owners, evidence links,
`accepted_by` only with `accepted_words`, and unevidenced and pending
listings. Then add **the three checks that make the inventory complete**.
They matter most in stage 1. The checklist's §1 says why: *"STRIDE over an
incomplete inventory produces confident coverage of the wrong system"*.
**A guard must generate the list it guards**, so each check derives the
list from the source of truth, not from the contract:

| Check | The list comes from | Fails when |
|---|---|---|
| **Every route belongs to a boundary** | the `.route(…)` calls in `crates/sui-id/src/http/router.rs` (`grep -c` finds 100 today; count the routes, not the matches), with their methods | a route is in no boundary's `entry_points`, or an `entry_points` entry names a route that does not exist |
| **Every table belongs to a boundary** | the tables `crates/sui-id-store/src/migrations/*.sql` leave in existence: created, minus dropped, after renames | a table is in no boundary's `stores`, or a `stores` entry names no table and no `file:` |
| **Every CLI command belongs to a boundary** | the leaf headings of `docs/src/reference/cli.md`, which `cli::reference::tests::the_committed_page_matches_a_fresh_render` holds equal to a fresh render | a command is in no boundary's `entry_points` (as `cli: sui-id backup create`), or one names a command the page does not have |

- **Fail closed on a line the parser cannot read.** A `.route(` call it
  cannot parse, or a `CREATE`/`DROP`/`ALTER … RENAME` it cannot parse, is
  a failure naming the file and line. It is never skipped.
- **Also check that every asset's `stores` entry is in some boundary's
  `stores`.** An asset kept somewhere no boundary covers is the same gap,
  seen from the other side.
- **Stop and return if** any of the three lists can only be produced by a
  parser that a plausible edit (a route built by a helper, a table created
  in Rust rather than SQL) would silently bypass. Say which, and what you
  measured.

**Registration**, as G21 was (`134e93b`):

## §3 — tests, each with a mutation

Python tests on fixtures, in the style of `scripts/tests/test_check_inline_tests.py`:

| Test | Mutation it must catch |
|---|---|
| A duplicate id; a control whose `boundary` does not resolve | — |
| An `analysed` boundary without a control fails; an `inventoried` one passes and is listed | `analysed` treated like `inventoried` |
| Each evidence form of the method's §3 resolves, and a missing file, heading, test or symbol fails; a control with `rfc:` evidence only is listed as unevidenced | the `test:` check made to accept any name |
| A residual with `accepted_by` and no `accepted_words` fails, and so does the reverse | the check dropped |
| A route added to a fixture `router.rs` and not to the contract fails, naming it | the route check reads the contract's list instead of the router |
| A table created in a fixture migration, and one dropped, both handled | `DROP` ignored |
| A CLI heading added to a fixture `cli.md` and not to the contract fails | — |
| An unparseable `.route(` line fails, naming file and line | the line skipped |

**And on the real tree:** G24 passes on your contract, and **adding one
route to `router.rs` turns it red.** Run that mutation on the real files,
then revert it, and say so in the return.
