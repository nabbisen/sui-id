## 1 — what changed since the checklist was written

The handoff lists the boundaries `docs/threat-model.md` omits (*current
only through v0.26.0*). Since then, these shipped or changed, and each is
in scope:
- federation **administration** (096-B2: preflight capability, enable,
  delete, unlink);
- **administrator-issued recovery links** (RFC 103);
- **users created without a password** (RFC 115);
- **step-up** (RFC 102);
- **the startup master-key check** and **rotation recovery** (RFC 100,
  stages 1–4);
- **the command system** (RFC 148: aliases, `init`, exit codes);
- the **consent policy** on clients.

**One lesson from 2026-11-22 belongs in the method itself.** RFC 103's T10
control was keyed on `source`. A later change, RFC 096-B1's F04, made
`source` mean something else for federated accounts, and the control
silently lapsed. No test failed, because the control's test used the
attribute's old meaning.

**So the inventory records, for each control, the attribute it keys on.**
A cross-boundary check, **classification consistency**, asks for every
attribute that classifies an account (`source`, `role`, a federation link,
a credential row): which controls read it, and does each still mean what
that control assumes? This becomes §4 of the checklist.

## 2 — the inventory: one versioned contract, checked by a gate

**`contracts/threat-model.toml`**, with `schema_version = 1`. The prose
document refers to its ids; it is the source of truth for what exists.

```toml
schema_version = 1

[[actor]]
id = "admin"           # stable id, referenced everywhere below
name = "Administrator (web console)"

[[asset]]
id = "master-key"
name = "The master key file"
classification = "secret"      # secret | personal | integrity | availability

[[boundary]]
id = "federation-upstream"
name = "sui-id <-> upstream OIDC provider"
owner = "RFC 096"              # the RFC that owns its controls
entry_points = ["GET /auth/federated/{slug}/start", "GET /auth/federated/callback"]
outbound = ["discovery", "jwks", "token"]
stores = ["federation_provider", "federation_link", "federation_login_attempt"]

[[control]]
id = "fed-dns-every-address"
boundary = "federation-upstream"
stride = ["S", "I"]            # which STRIDE threats it addresses
claim = "Every DNS answer address must be ordinary public unicast; one is dialled."
keys_on = ["resolved address"] # the attribute the control reads (§1)
evidence = [
  "rfc:134#d2",
  "test:sui-id::runtime::resolver::tests::a_mixed_answer_rejects_the_whole_answer_not_just_the_bad_address",
  "code:crates/sui-id/src/runtime/resolver.rs::validate_answer",
  "record:rfcs/handoffs/096-upstream-oidc-federation/096-b1-m4b-google-run-record-2026-11-22.md",
]

[[residual]]
id = "audit-chain-unanchored"
boundary = "database-writer"
risk = "The audit chain is unkeyed and unanchored (S2)."
rating = "medium"              # from §4's rubric
accepted_by = ""               # the accepter's handle, set only together with accepted_words; empty = pending
accepted_words = ""
revisit_when = "an external anchor is designed"
```

**The gate** (one new script, registered like every other) checks:
- **every id is unique**, and every reference resolves: a control's
  `boundary`, a residual's `boundary`;
- **every boundary has an owner, at least one control, and a filled
  STRIDE row** (§3);
- **every evidence link resolves** (the syntax below);
- **a residual marked accepted carries `accepted_words`**: the accepter's
  own words, verbatim. An empty `accepted_by` is *pending*, and pending residuals are
  listed in the gate's summary. **Anonymous acceptance is impossible by
  construction**, which is the checklist's §6 made mechanical. It is the
  same idea as G16, applied to risk.

## 3 — evidence links, and how each is checked

| Form | Means | Checked by |
|---|---|---|
| `rfc:NNN#anchor` | a section of an RFC | the file exists in `rfcs/`, and the anchor's heading exists |
| `test:<crate>::<path>::<name>` | a named test | a `fn <name>` exists in that crate's sources, inside `#[cfg(test)]` or `tests/` |
| `code:<path>::<symbol>` | a function or type | the path exists, and the symbol is defined in it |
| `record:<path>` | a run record, review or assessment | the file exists |
| `run:<ci-run-id>` | a CI run | recorded as cited; not checked offline |

**No line numbers.** They drift, and a symbol does not (the project's own
lesson: cite by `grep -n`, and better still by name). **A control whose
only evidence is `rfc:`** is a design claim, not evidence. The gate lists
it as **unevidenced**, and the checklist's rule applies: *a control claim
without an evidence link is a finding, not a control*.

## 4 — the STRIDE worksheet, and the risk rubric

**Per boundary**, one table: six rows, one per STRIDE letter. Each row
gives:
- the threat;
- the control ids that address it;
- each control's evidence status (evidenced / unevidenced);
- the residual id, if one remains.

A letter with no threat says *"not applicable"* and why, never a blank.

**The rubric** answers the RFC's open question on the scale: **3 × 3**,
with anchors, so two readers rate alike.

| Likelihood | Anchor: who can reach it |
|---|---|
| **High** | unauthenticated, remote |
| **Medium** | an authenticated user, or a compromised upstream |
| **Low** | an administrator with step-up and a second factor, or host access |

| Impact | Anchor |
|---|---|
| **High** | account takeover, key or secret disclosure, or a forged audit record |
| **Medium** | personal-data disclosure, a bypassed control with no takeover, or denial of service of sign-in |
| **Low** | information about the system, or a bounded nuisance |

**Rating** = the higher of the two, lowered by one step if both are
*Low* or one is *Low* and the other *Medium*. It is stated per residual,
with its two inputs, so the arithmetic can be checked.

A **finer scale (CVSS, OWASP) is not proposed.** It would add precision the
inputs don't have, for a self-hosted product whose operators need to know
*what to do*, not a number.

## 5 — diagrams

The RFC's other open question, the tooling, gets a proposed answer: **no
diagram tooling.**
- One **text diagram** per boundary class, in a fenced block, beside its
  table.
- mdBook builds with no Mermaid preprocessor here. A preprocessor would
  be a new build dependency, a supply-chain boundary of its own, for
  pictures that a table already carries.
- Text diffs review cleanly.

## 6 — the deliverable, and the stages

The deliverable is **`docs/threat-model.md`, rewritten**, with the banner
removed only in the change that makes it true. Every control and residual
is cited by its contract id.

| Stage | What | Who |
|---|---|---|
| 1 | the contract schema and its gate, with the inventory: actors, assets, boundaries | implementation role, from this method |
| 2 | controls with evidence, boundary by boundary: the STRIDE worksheets | implementation role; each boundary's evidence is measured, never recalled |
| 3 | cross-boundary compositions (checklist §4, with classification consistency), and failure and rollback (§5) | architect drafts; the implementation role measures |
| 4 | the residual register, put for acceptance **one decision at a time** | the accountable approver named in RFC 097's header |
| 5 | the document rewritten from the contract; the banner goes | implementation role; architect reviews |

**Not in scope** (the RFC's own rule): implementation changes. A gap found
on the way returns to the RFC that owns it, or gets a new RFC, and blocks
closure, as T10 did on 2026-11-22.

## 7 — what acceptance would decide

1. **This method**: a versioned TOML contract with a gate; evidence links
   by symbol, not line; a 3 × 3 rubric with anchors; text diagrams; five
   stages.
2. **The security reviewer.** RFC 097 says *Security review: required*. As
   for RFC 100, the architect wrote it and cannot review it, so a role
   that did not author it must. The owner named himself for RFC 100.
   Proposed: the same.
3. **When**: stage 1 in cycle P, beside RFC 149. Stages 2–5 follow,
   sequenced so that no stage rests on a boundary still changing; RFC 100
   stages 5–7 are the one that is.
