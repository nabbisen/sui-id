## 0. Verdict

**Part A is buildable on the existing runner** once its races and guards are specified precisely (H2, M1).

**Part B, and RFC 103's D6, rest on a premise the code does not support.**
- Factor *enrollment* is not step-up-gated (B1). A stolen session can therefore make itself fresh.
- Most gated actions are not Class-A commands (H1). B4 therefore has nothing to attach to.

Both must be settled before Part B or RFC 103 is accepted.

## 1. Findings, by severity

### Blocker

**B1 — [RFC 102 Part B; RFC 103 D6] A stolen session can enrol its own factor and then pass step-up.**
- `passkey_register_start` and `passkey_register_complete` (`crates/sui-id/src/http/handlers/me_security/passkey.rs`) require only a session and CSRF: no `require_fresh_step_up` and no current password. `mfa_regenerate_recovery` (`me_security/mfa.rs`) is the same.
- **Attack path today:** with a stolen session cookie, register the attacker's passkey, run `/me/security/step-up/webauthn/*` with it, and the session is now fresh for every gated action. Alternatively, regenerate recovery codes and step up with one (B-F3).
- Part B removes recovery codes (B3) but leaves passkey registration open. After Part B, step-up still does not stop a session thief.
- B4's `fresh` would faithfully record a freshness the thief manufactured. RFC 103 D6's "must hold a second factor and be fresh" is met by an attacker who added the factor minutes earlier.
- **Needed:** Part B must gate factor additions:
  - passkey registration;
  - recovery-code regeneration;
  - TOTP enrolment when any factor exists.

  It must also decide what re-authentication a user with **no** factor gives before enrolling the first one.
- By reading; not executed. It needs a WebAuthn authenticator simulation.

### High

**H1 — [RFC 102 Part B / B4; Security considerations] "A dangerous action is already a Class-A command" is false for most gated actions.**
- Only K01, T04, U01–U10 and U22 are declared with `declare_write_command!` (`crates/sui-id-store/src/commands.rs`).
- Of the 12 gated handlers that write (§4.1), only 4 are on the seam: `users_set_disabled` (U02/U03), `users_delete` (U04), `users_mfa_reset` (U07) and `signing_keys_rotate` (K01).
- The other 8 mutate first and then call `let _ = audit::append` / `audit_with_note` (`crates/sui-id-core/src/identity/admin.rs:35-54`), even though the manifest lists them as Class-A "implemented":
  - client disable, delete and rotate-secret (C05, C06, C07);
  - signing-key hard delete (no manifest row, L2);
  - self-service MFA disable (U13) and passkey delete (U16);
  - revoke-all-others (U19);
  - SMTP pending-change apply (S08).
- B4 ("a required attribute on the descriptor") cannot be implemented for them, and "cannot commit unaudited" does not hold.
- **Needed:** either RFC 094 M2b converts those commands before step 6, or B4 is scoped to the seam and says so.

**H2 — [RFC 102 Part A L02; Part B L05] Both replay races exist, and the recovery-code race is worse than described.**

Demonstrated by `review102_races.rs` on a multi-thread runtime (§3), with two pending-MFA rows submitted concurrently:
- one TOTP code gave **two sessions in 40/40 iterations**;
- one recovery code gave **two sessions in 10/10**, leaving 7 codes, so one code was consumed once but used twice.

Implementation consequences:
- **Recovery codes are a sealed JSON blob** (`user_totp.recovery_codes_enc`). "Remove the used hash with a guard that it is still present" cannot be written in SQL. The guard must be a compare-and-swap on the ciphertext (`UPDATE … SET recovery_codes_enc = ?new WHERE user_id = ? AND recovery_codes_enc = ?old`), with the Argon2 match done outside the transaction. The RFC should say this.
- **`set_last_used_step` can also move the step backwards** (`crates/sui-id-store/src/repos/user_totp.rs:133-142`). If concurrent verifications accept steps N+1 and N and write in that order, the stored step becomes N and the N+1 code verifies once more. The guarded update `WHERE last_used_step < ?step` fixes this as well; worth naming in the test plan.

**H3 — [RFC 102 Part A path 4] A returning external-source user cannot sign in, so L03 happens only once per user.**
- `review102_ldap_return.rs`, using `InMemoryUserSource`: first `POST /admin/login` gives 303 and a session cookie; the second gives **401 and no cookie**; bob has 1 session.
- **Cause:**
  - The shadow row takes the typed username (`crates/sui-id-store/src/ldap_source.rs:190`).
  - On the second attempt `login_with_mfa` finds it locally, `credentials::get` returns NotFound → `InvalidCredentials` (`crates/sui-id-core/src/authn/session.rs:167-170`).
  - `try_login_with_cascade` then treats the user as known locally and never consults the directory (`crates/sui-id/src/http/handlers/admin/auth.rs:146-154`).
- Outside RFC 102's scope, but L03's design and tests assume a path that works only once. It needs its own package.

**H4 — [RFC 102 Part A path 5] The federation callback fails open on an MFA read error and never checks the user's state.**
- `complete_federated_signin` computes `is_mfa_enabled(...).await.unwrap_or(false)` (`crates/sui-id/src/http/handlers/federation.rs:602-604`). A read failure skips local MFA and issues a session.
- `federation.rs` contains no `is_disabled` or `is_deleted` check. A disabled or deleted user with a federation link gets a session. It is refused at `/admin` (extractors `handlers.rs:238, 275`) and at `/oauth2/authorize` (`authorize.rs:445`), but `SessionContext` (`handlers.rs:189-212`) accepts it, so `/me/*` works.
- L04's "the user must still be active" re-read closes the second. The first needs an explicit fail-closed rule in L04: the MFA decision must come from a successful read.

**H5 — [RFC 103 T10] An external-source user can already get a local password through forgot-password.**
- `request_reset` looks the user up by email and checks only disabled/deleted (`crates/sui-id-core/src/account/forgot_password.rs:101-124`). Shadow rows carry the directory's email (`users::upsert_ldap_shadow`), and federation provisioning uses the same function.
- U10 completion (`commands.rs:1092-1110`) does not check `source` either. `login_with_mfa` does not check `source`, so the new local password then signs in, bypassing the directory.
- D5 covers only admin issuance. T10's control must move to U10 completion, and to `request_reset`, for every origin.

**H6 — [RFC 103 D10 / T9] "The link is never logged, at any level" cannot hold for the reused completion URL.**
- The link is `GET /reset-password?token=…` (`crates/sui-id/src/http/handlers/forgot_password.rs:10`, `:122-130`). The token sits in the query string, so it reaches:
  - the reverse proxy's access log (the deployment guide's Caddy and nginx defaults log it);
  - the user's browser history;
  - with `log.access_log = true`, `tower_http`'s `TraceLayer::new_for_http()` span (`crates/sui-id/src/http/router.rs:358`), whose default span records the full `uri` at debug level.
- Rendering the link in a POST response (D10) protects only the administrator's side.
- **Needed:** either the completion landing changes (for example, a fragment the page POSTs, or a POST form), or D10 states the residual and customises the trace span.

### Medium

**M1 — [RFC 102 A3/B5; test plan] "Byte-identical" responses are unattainable as written, and some paths map a store error to 500.**
- **Per-response values.** Error pages embed a per-request `request_id` (`HttpError::html` → `render_error(status, request_id, …)`), and challenge pages embed the CSRF token. Two failures are never byte-identical. The tests need a stated normalisation.
- **Status codes differ by error kind today:**
  - WebAuthn sign-in maps with `HttpError::html(err)` (`crates/sui-id/src/http/handlers/admin/webauthn.rs:120, 128`), so a store error gives 500 while a bad assertion gives 401.
  - The step-up TOTP handler returns `Err(other) => HttpError::html(other)` (`crates/sui-id/src/http/handlers/step_up.rs:188`), so 500 versus the 400 page.
  - Password and TOTP sign-in already map every `Err` to one 401 page (`auth.rs:344-365`, `:478-533`).
- The RFC should name, per step, the mapping from a transaction failure to that step's failure.

**M2 — [RFC 102 B4; Open question 1] Let the command compute the evidence, not the gate.**
- `require_fresh_step_up` returns `Result<(), Response>` (`handlers.rs:624-666`). Carrying a value to the command either requires a type handlers cannot forge or trusts them.
- A simpler design: the gated command re-reads the session row inside its own transaction (`last_step_up_at`, the new `last_step_up_method`) and derives `step_up` there.
  - No value crosses the handler, so there is nothing to forge.
  - It also closes the check-then-act gap: freshness expiring between the gate and the command.
  - It needs the session ID as a command input, which is not a secret inside the store. It never enters the event.

**M3 — [RFC 102 Part A L01] A session and success event are committed for a sign-in that delivers no session.**
- `login_post` builds the session first, then refuses a user without admin role when `next` is not `/oauth2/` or `/me/`, and sets no cookie (`crates/sui-id/src/http/handlers/admin/auth.rs:272-303`).
- Under L01 that is an Atomic `auth.login.success` for a session nobody holds. Either check the role before L01 (the role is readable before the transaction), or accept and document it.

**M4 — [RFC 102 Part A] Second-factor sign-in failures remain uncounted.**
- `auth.mfa.failure` is best-effort with `actor: None, target: None` (`auth.rs:485-496`). Nothing counts failures per pending row or per user; only the shared per-IP login bucket applies.
- Part B counts and revokes on step-up failures. Part A leaves the sign-in second factor, the same TOTP guess space, with neither. Worth a sentence: in scope, or an explicit non-goal.

**M5 — [RFC 103 T7, D3] U10's token consumption is unguarded, and completion re-checks nothing.**
- `mark_consumed_within_tx` runs `UPDATE … WHERE id = ?2` with no `consumed_at IS NULL` (`crates/sui-id-store/src/repos/password_reset_tokens.rs:108-122`).
- The token row is read outside the transaction (`forgot_password.rs:329-335`), so two concurrent completions with one token both commit. That breaks "single use" under concurrency; the planned test is sequential.
- U10 also does not re-read the user's disabled/deleted state or source.

**M6 — [manifest; RFC 102 L03] U26 is listed as an implemented Class-A command, but no such command exists.**
- `ci/write-commands.toml` U26 says class A, implemented, event `auth.user_source.shadow_upserted`. No code writes that event, and `users::upsert_ldap_shadow` is a raw repository function.
- L03's "U26 remains its own command" assumes a command that is not there.
- Federation provisioning reuses the function, so federated users are stored with `source = ldap` (`federation.rs:504-511`).

**M7 — [RFC 102 OQ3; RFC 103 OQ3] A sole administrator who loses every second factor has no path.**
- The CLI has `admin unlock-user` and `admin rotate-key` only; there is no MFA reset. RFC 103's CLI resets the password only (D4 keeps MFA).
- Today a user who kept recovery codes self-recovers only *through* B1: sign in with a code, register a passkey, step up, then disable TOTP.
- Once B1 is fixed, every lost-authenticator case goes through an administrator's MFA reset, and the last administrator has none. This needs an owner decision on a CLI MFA reset (§6).

**M8 — [RFC 103 D8, D3] Throttling across the CLI and the server needs database-backed counting.**
- The CLI is a separate process, so "the CLI at most 5" must count from the database, e.g. tokens with `issued_via = 'cli'` in the last hour.
- `request_reset` already caps outstanding tokens at `MAX_OUTSTANDING_TOKENS_PER_USER = 3` (`forgot_password.rs:61, 126-138`). D3's invalidate-on-issue interacts with it; the RFC should say whether admin-issued tokens count against it.

### Low

- **L1** `crates/sui-id-core/src/authn/step_up.rs:89-90` doc says "recovery-code verification does not touch [`last_step_up_at`]". `verify_totp_code` does (B-F3).
- **L2** Signing-key hard delete (`repos::signing_keys::delete`, handler `signing_keys_delete`) has no manifest row. K02 is "retire".
- **L3** `docs/src/reference/audit-events.md:40` and `ci/audit-coverage-matrix.md:37` present `user.reset_password` as a live event, although U06 is unreachable. RFC 103 step 5 covers the matrix; the book page should go with it.
- **L4** `try_login_with_cascade` treats *any* error from `find_by_username` as "unknown locally" and falls through to the directory (`auth.rs:146-149`).
- **L5** Migration 0032's comment says `payload_enc` is AES-GCM; `crypto::seal` is XChaCha20-Poly1305 (already reported in dispatch 15).
- **L6** (item 6, A4) `sessions::insert` has test-only callers (§2.6). Making it crate-private breaks them, and `commands::insert_session` (the U30 Protocol runner, `commands.rs:1305`) has no production caller and should be retired in the same step.

### 2.4 Item 4 — L01–L04 on the existing runner

**Runner shape.**
- `Database::class_a(context, build)` takes a **synchronous** `FnOnce(&mut ClassATx<C>)`, and `ClassATx::tx()` is `pub(crate)` (`crates/sui-id-store/src/registry.rs:564-622`).
- So every L command must be defined in `sui-id-store`, and every verification (Argon2, TOTP, WebAuthn, upstream) must be outside. That matches the RFC.
- Reads inside the closure use the same transaction, so a `server_settings` read inside is fine.

**Existing `*_within_tx`:** `sessions::insert_within_tx`, `revoke_all_for_user_within_tx`, `revoke_all_for_user_except_within_tx`; `users::get_role_within_tx`, `record_login_failure_within_tx`, `set_disabled_within_tx`; `user_totp::delete_within_tx`; `credentials::upsert_within_tx`.

**Needed:**

| Command | Functions needing a `_within_tx` variant (or a new guarded statement) |
|---|---|
| L01 | `users::clear_lockout`; `users::set_last_login`; an active-user re-read (`users::get` or `find_by_id_opt`; only `get_role_within_tx` exists); `server_settings::get`; `sessions::count_active_for_user`; `sessions::oldest_active_for_user`; `sessions::revoke` (single row) |
| L02 | L01's set, minus `clear_lockout`, plus: `login_pending_mfa::get` and a **guarded** `delete` (rows affected = 1); a guarded `user_totp::set_last_used_step` (`WHERE last_used_step < ?`); a CAS `user_totp::set_recovery_codes` (H2) |
| L03 | as L02, without the MFA rows; U26 is not a command (M6) |
| L04 | as L03 |
| L05 | `sessions::get` (re-read); a guarded `sessions::touch_step_up` plus the new columns; a guarded, kind-scoped `webauthn_pending::delete`; the guarded TOTP step |
| L06 | a new failure-count increment; `sessions::revoke` single row |

**`enforce_concurrent_session_cap`'s `server_settings` read inside the transaction:** yes. It is a plain `SELECT` on the singleton row; move it to a `*_within_tx` form.

### 4.3 Item 9 — can L05 and L06 be built?

**Migration.** Two nullable columns on `sessions` (`last_step_up_method TEXT`, `step_up_failure_count INTEGER NOT NULL DEFAULT 0`) are plain `ADD COLUMN`s. `SessionRow` and every `SessionRow { … }` literal gain the fields: 5 production and roughly 10 test sites.

**`finish_authentication` taking the expected kind.** Straightforward. It already checks `pending.kind != Authenticate` (`crates/sui-id-core/src/authn/webauthn.rs:249-254`).
- Pass the kind, and remove both swaps in `step_up.rs`.
- Its own best-effort `webauthn_pending::delete` (`webauthn.rs:279`) must move into L05 for step-up. For sign-in it moves into L02, or stays U33.
- The counter update (`update_passkey`, U29) stays outside, as the RFC says.

**B4 evidence from gate to command without forgery.** See M2: compute it inside the command from the session row. If a value must be passed instead, it needs a store-side sealed type whose constructor takes the session row read in the same transaction. That reduces to M2 anyway.

**The rate-limit bucket.** Add `RateLimitKey::StepUp` and a limiter. Mechanical.

**L06 revoking a session.** Needs `sessions::revoke_within_tx`, which exists only as `revoke_all_*`.

### 4.4 Item 10 — Open question 3: which self-service MFA actions are gated?

**Gated:** `mfa_disable`, `passkey_delete`, `revoke_all_others`.

**Not gated:**
- `mfa_enroll_start` and `mfa_enroll_confirm` (TOTP enrolment is refused only while TOTP is already enabled);
- `mfa_regenerate_recovery`;
- `passkey_register_start` and `passkey_register_complete`;
- `passkey_rename_post`;
- `password_change_post` (current password required);
- `revoke_one`, `language_post`, `me_apps_revoke`.

**Tracing both cases** (by reading):
- **A user who lost their only authenticator but kept recovery codes.** Sign in with a recovery code; today that grants freshness (`mfa.rs:250`). Even without freshness, they can register a passkey (ungated), step up with it, then disable TOTP. So **recovery works today only through B1**. Once B1 is fixed, they cannot pass the gate on `/me/security/mfa` and need an administrator's MFA reset (U07).
- **A sole administrator in the same position.** U07 is gated by step-up and targets another user through the admin panel. There is no second admin, and no CLI MFA reset (`--help`: `admin unlock-user`, `admin rotate-key`). Once B1 is fixed, **no path**. Without recovery codes, no path even today. → owner, together with RFC 103's CLI (M7).

### 5.5 Item 15 — threats

**Controls that would not stop their threat as designed:**
- **T1/T6 (D6):** a stolen session manufactures freshness by enrolling a passkey (B1).
- **T9 (D10):** the completion URL leaks the token regardless of how issuance renders it (H6).
- **T7 (D3):** single use fails under concurrent completion (M5).
- **T10 (D5):** the email origin already gives external-source users a local password, and completion does not check `source` (H5).

**Missing threats:**
- **Link for a user disabled after issuance, before D3 lands or in a race:** completion does not re-check state (M5).
- **Notice to an unverified address:** today's completion notice goes to any address, not only a verified one (§5.2). D7 should state the rule for both notices, not just issuance.
- **Freshness is not bound to the action:** one step-up authorizes up to D8's 5 issuances within 5 minutes. That is acceptable with D8, but it should be written down.
- **The sole administrator who lost MFA:** RFC 103's CLI recovers the password only (M7).

## 6. Item 16 — open questions

**RFC 102**
1. **Type-level proof.** Not needed for L01–L04: every caller is in-workspace, and the manifest plus the structural gate suffices, as for U22. **For B4, avoid the question** by deriving the evidence inside the command's transaction (M2). A sealed proof crossing crates can only be minted by whoever owns the type, and here that is not the verifier. The stronger design is outside what this role can adjudicate if the owner wants it anyway.
2. **A code stays usable after a failed commit.** Agree. With the guarded step update (H2) it still cannot be used twice. Burning a valid code on a server fault gains nothing.
3. **Recovery-code sign-in and freshness.** Agree with honouring RFC 089, **but only together with B1**. Without B1, honouring it changes nothing for an attacker, because passkey registration still yields freshness. With B1, lost-authenticator recovery becomes admin MFA reset. The sole-administrator case has no path (M7); that goes to `@nabbisen`.

**RFC 103**
1. **Expiry 30 minutes.** Agree. It matches the email path and suits a live handover.
2. **Five per administrator per hour.** Outside this role's adjudication for deployment size. Implementability note: the CLI limit must be database-counted (M8).
3. **Refuse admin targets on the web.** Agree on T3. The trade-off is sharper than stated: an administrator who lost their **second factor** has no CLI remedy either (M7). The owner should rule on both together.
